# 度量怎么报

`metrics.py` 能算出八项指标，但**把数字翻译成人能用的判断**才是这一步的产出。
用户问"我们最近交付得怎么样""哪里最卡"时读这一份。

---

## 什么时候用

这类问题问的不是某一单，是交付系统本身：

```bash
python3 "$CORE/scripts/metrics.py" --root .                    # 全部
python3 "$CORE/scripts/metrics.py" --root . --work-item WI-002 # 单个
```

它从已有文件里算出：**lead time**（created → release gate 的 `decided_at`）、**一次通过率**（Gate 首次即
PASS 的占比）、**返工**（notes 回退行数 + defects + amendments）、**缺陷逃逸**（`defects/` 下的条数）、
**Gate 等待**、**人工审批负担**、**上下文失败**（`boundary_stop` 与 `result: blocked`）、
**资产复用**（产物里引用过 LP-### 的次数）。原料一直都在，只是从来没人去加总。

**它同样是原料。** 翻译成人话，并且指出数字背后的机制——只报数字等于把解释工作推回给用户：

❌ `first_pass_rate: 0.6, rework_total: 4, gate_wait_days_avg: 3.2`

✅
```
最近 5 单：从开单到发布平均 11 天，其中 3.2 天是在等人签字——等待占了将近三成。
Gate 一次通过率 60%，4 次返工里有 3 次是 contract 批准之后才发现 criteria 说不清楚。
两个数指向同一件事：contract 环节收得不够紧，成本转移到了后面更贵的阶段。
```

**这些数字描述的是交付系统，不是某个人。** 返工多通常意味着 contract 没写清楚，那是上游问题；
Gate 等待长通常意味着批准人手上有别的事，那是排期问题。两者都不是"谁不行"。

- **不得用任何一项推导个人绩效**，也不得按人拆分这些数字。`metrics.py` 按 WI 聚合而不按 owner 聚合，这是有意的
- **不得用 token 消耗或 AI 使用率替代它们**。这两个数不衡量交付，只衡量用了多少工具；
  用它们做管理会立刻长出"多调几次工具好看一点"的行为，而那与交付质量毫无关系

用户直接要求按人排名时，说明这里为什么不给，并把问题换成可以回答的那个：哪个环节最慢、哪一类返工最多。

---

## 停滞怎么看

这类问题问的不是状态，是**停滞**。看四样东西：

1. `status: Held` 且 `since` 较久的
2. 缺批准超过几天的 Gate
3. `updated` 很旧但状态不是终态的 WI（有人开了单就没再动）
4. **依赖阻塞**——某个 WI 自己一切正常，但它 `dependencies` 里的前置 WI 停住了

第 4 类 `wi_status.py` 不输出，要自己读各 WI 的 `dependencies` 字段把链连起来。
漏掉它的后果是报账听起来一切健康，实际上一条链上的三个 WI 全在等同一个人。

把这四类连同"谁能解开"一起给出来。
