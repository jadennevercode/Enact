# EARS 语法完整指南

写 `contract.yaml` 的 `criteria` 时读这一份。

EARS（Easy Approach to Requirements Syntax）不是形式主义。它解决的是一个具体问题：**自然语言写的验收标准，读的人各有各的理解，而下游要照它做、照它测、照它签字。** 五个受限句式把"什么时候、什么前提、谁、必须做什么"四件事强制拆开，让一条标准只有一种读法。

## 1. 五种模式

关键词用英文大写（`WHEN` / `WHILE` / `WHERE` / `IF` / `THEN` / `SHALL`），描述部分用中文。`SHALL` 前面的主体统一写「系统」，或写具体的服务/模块名。

### 1.1 Ubiquitous —— 无条件

```
系统 SHALL <行为>
```

**用在**：任何时候都成立的属性与约束。数据格式、编码规范、恒定不变的业务规则。

```
✅ 系统 SHALL 以 UTC 存储所有时间戳
✅ 导出文件 SHALL 使用 UTF-8 with BOM 编码
✅ 系统 SHALL 对所有金额字段保留两位小数并向下取整
```

**注意**：Ubiquitous 是最容易被滥用的一种——一条标准找不到触发条件时，人会下意识写成 Ubiquitous。写之前问一句：这真的在任何时刻都成立吗？还是我只是没想清楚它什么时候生效？

### 1.2 Event-driven —— 事件驱动

```
WHEN <事件发生> THEN 系统 SHALL <响应>
```

**用在**：由一个离散事件触发的行为。用户点击、接口被调用、定时任务到点、消息到达。这是最常用的一种。

```
✅ WHEN 用户提交导出请求 THEN 系统 SHALL 在 3 秒内返回任务 ID
✅ WHEN 订单状态变为 refunded THEN 系统 SHALL 向对账队列发送一条退款事件
✅ WHEN 每月 1 日 00:00 UTC 到达 THEN 系统 SHALL 生成上月的对账报表
```

事件要写成**可观测的瞬时动作**，不是状态描述。

```
✅ WHEN 用户点击「导出」 THEN ...
❌ WHEN 用户想要导出数据 THEN ...   （"想要"不可观测）
```

### 1.3 State-driven —— 状态持续

```
WHILE <系统处于某状态> 系统 SHALL <行为>
```

**用在**：在某个状态**持续期间**一直成立的行为。区别于 WHEN 的关键是持续性——WHEN 是一次响应，WHILE 是一段时间内的持续约束。

```
✅ WHILE 导出任务处于 running 状态 系统 SHALL 每 5 秒更新一次进度百分比
✅ WHILE 用户会话未过期 系统 SHALL 允许其访问已授权的报表
✅ WHILE 数据库连接池已耗尽 系统 SHALL 拒绝新的导出请求并返回 503
```

判断方法：如果这个条件消失后行为就该停止，是 WHILE；如果这是一次性响应，是 WHEN。

### 1.4 Optional feature —— 可选特性

```
WHERE <某特性/配置存在> 系统 SHALL <行为>
```

**用在**：只在某个配置开启、某个套餐、某个部署形态、某种设备上才成立的行为。它明确地告诉 Build 和 QA：**这条不是所有环境都要满足的**。

```
✅ WHERE 项目启用了多币种配置 系统 SHALL 在报表中额外输出原币种金额列
✅ WHERE 客户处于企业版套餐 系统 SHALL 允许单次导出超过 10 万行
✅ WHERE 部署环境为私有化 系统 SHALL 从本地配置读取汇率而不调用外部服务
```

没有 WHERE 而把可选特性写成 Ubiquitous，会让 QA 在没开这个特性的环境里测出一堆"失败"。

### 1.5 Unwanted behaviour —— 异常路径

```
IF <异常前置条件> THEN 系统 SHALL <处理方式>
```

**用在**：错误、非法输入、超限、依赖不可用、竞态。**这一类最容易被整体遗漏**——大多数需求文档只写快乐路径，而线上事故几乎全部发生在这一类里。

```
✅ IF 导出请求的时间范围超过 12 个月 THEN 系统 SHALL 拒绝并返回可读的错误说明
✅ IF 汇率服务在 2 秒内未响应 THEN 系统 SHALL 使用最近一次缓存汇率并在报表页脚标注取数时间
✅ IF 某订单无退款记录 THEN 系统 SHALL 输出 0 而不是空值
✅ IF 同一用户已有 3 个导出任务在排队 THEN 系统 SHALL 拒绝第 4 个请求并说明原因
```

写完一组 WHEN 之后，逐条问：这个事件的失败版本是什么？依赖挂了怎么办？输入越界怎么办？并发发生怎么办？每个答案都是一条 IF。

## 2. 选哪种模式

| 这条标准描述的是…… | 用 |
|---|---|
| 永远成立的属性、格式、恒定规则 | `系统 SHALL` |
| 某件事发生后的一次响应 | `WHEN … THEN … SHALL` |
| 某个状态持续期间的持续行为 | `WHILE … SHALL` |
| 只在某配置/套餐/环境下成立 | `WHERE … SHALL` |
| 错误、越界、依赖失败、非法输入 | `IF … THEN … SHALL` |

一条标准同时含事件与异常前提时，选**决定行为的那一个**，把另一个写进事件描述里：

```
✅ WHEN 用户提交时间范围超过 12 个月的导出请求 THEN 系统 SHALL 拒绝并返回可读的错误说明
✅ IF 导出请求的时间范围超过 12 个月 THEN 系统 SHALL 拒绝并返回可读的错误说明
❌ WHEN 用户提交导出请求 IF 时间范围超过 12 个月 THEN 系统 SHALL 拒绝
   （两个关键词叠用，读法不唯一）
```

## 2b. 与 Given/When/Then 的对应

主规格 §22 的验收标准用的是 Given/When/Then，本套件统一用 EARS 替代。这是一次有意的替换，
不是两套并存——所以这里把映射说清楚，否则每个读者都得自己在心里换算一遍，而各人算出来的还不一样。

| Given/When/Then | EARS 里的对应 |
|---|---|
| **Given**（前置条件） | `WHILE <状态>` 或 `WHERE <特性存在>`；也可以写成事件里的限定语。契约层面的长期前提落在 `criteria.notes` 与 `policies` |
| **When**（触发事件） | `WHEN <事件>` |
| **Then**（预期结果） | `THEN 系统 SHALL <响应>` |
| （GWT 没有专门位置的异常路径） | `IF <异常前置> THEN 系统 SHALL <处理>`（Unwanted behaviour） |

对照一段常见的 GWT：

```
Given 用户具备 report:export 权限
And   导出时间范围超过 12 个月
When  用户提交导出请求
Then  系统拒绝并返回可读的错误说明
```

写成 EARS 是两条，不是一条：

```
2.1  IF 请求导出的用户不具备 report:export 权限 THEN 系统 SHALL 返回 403 且不返回任何数据行
1.5  IF 导出请求的时间范围超过 12 个月 THEN 系统 SHALL 拒绝并返回可读的错误说明
```

**这次替换的实质是更严，不是更松**，两处：

1. **一条只能有一个 SHALL。** GWT 的一个场景块里堆三个 Then 完全合法，而 EARS 逼着你拆开（见 §4.3）。
   拆开之后 QA 才能给出逐条结论——一个塞了三个预期的场景，测出两过一不过时，没人说得清它算不算过。
2. **异常路径有了专门的句式。** GWT 只能靠写作者自觉多补几个场景，补没补看不出来；
   EARS 把它做成五模式之一的 `IF-THEN`，**清单上少了这一类是看得见的**，`coverage_stats.py` 也按条统计。

反过来，EARS 丢掉了 GWT 的一样东西：GWT 的场景块天然把"同一个业务流程的连续几步"聚在一起。
EARS 靠层级编号承担这件事——同一个 requirement 下的 `1.1`–`1.4` 就是那个场景块（见 §5）。
需要把整条流程画出来给人看时，那属于 contract 的 `design.diagrams`（mermaid，用 `relates_to` 指回这些编号），不属于 criteria。

## 3. 从模糊需求到 EARS：成对例子

左边是探索阶段常见的原话，右边是它该被写成的样子。注意每一次改写都做了同一件事：**把隐含的触发条件、判定阈值、可观测结果显式化**。

### 3.1 性能

| 模糊需求 | EARS 改写 |
|---|---|
| 导出要快 | `WHEN 用户提交行数不超过 5 万行的导出请求 THEN 系统 SHALL 在 10 秒内产出可下载文件` |
| 页面不能卡 | `WHEN 用户打开报表列表页 THEN 系统 SHALL 在 1.5 秒内完成首屏渲染（P95，标准办公网络）` |
| 支持大数据量 | `WHERE 客户处于企业版套餐 系统 SHALL 支持单次导出至多 50 万行`<br>`IF 单次导出请求超过 50 万行 THEN 系统 SHALL 拒绝并提示按时间范围拆分` |
| 高并发下要稳定 | `WHILE 同时进行的导出任务达到 20 个 系统 SHALL 将新请求排队而不是拒绝`<br>`IF 排队长度超过 100 THEN 系统 SHALL 拒绝新请求并返回预计恢复时间` |

性能标准必须带**数字 + 测量口径**（P95 还是平均？什么网络？什么数据量？）。没有口径的数字在 QA 那里会变成争论。

### 3.2 错误处理

| 模糊需求 | EARS 改写 |
|---|---|
| 出错要有友好提示 | `IF 导出因数据源不可用而失败 THEN 系统 SHALL 显示「数据源暂时不可用，请稍后重试」并保留用户已填的筛选条件` |
| 要有重试机制 | `IF 汇率服务调用失败 THEN 系统 SHALL 以 1s/2s/4s 间隔重试至多 3 次`<br>`IF 3 次重试全部失败 THEN 系统 SHALL 使用最近一次缓存汇率并在报表页脚标注取数时间` |
| 不能丢数据 | `IF 导出任务在写文件过程中中断 THEN 系统 SHALL 删除半成品文件并将任务状态置为 failed`<br>`WHEN 任务状态变为 failed THEN 系统 SHALL 保留原始请求参数以支持一键重试` |
| 异常要记日志 | `IF 导出任务失败 THEN 系统 SHALL 记录一条含任务 ID、失败阶段与原始错误的 ERROR 日志` |

「友好」本身不可验证，但「显示哪句话」「保留哪些状态」可以。把形容词换成可观测结果。

### 3.3 权限

| 模糊需求 | EARS 改写 |
|---|---|
| 只有管理员能导出全量数据 | `IF 请求导出的用户不具备 report:export_all 权限 THEN 系统 SHALL 返回 403 并且不返回任何数据行` |
| 数据要按部门隔离 | `WHEN 用户导出报表 THEN 系统 SHALL 只包含该用户所属部门及其下级部门的订单` |
| 越权要拦住 | `IF 用户通过直接构造 URL 访问他人的导出任务结果 THEN 系统 SHALL 返回 404 而不是 403`（不泄露任务是否存在） |
| 登录过期要处理 | `WHILE 用户会话已过期 系统 SHALL 拒绝所有导出接口调用并返回 401` |

权限类标准要同时写**允许什么**和**拒绝时发生什么**——只写允许，QA 就只会测快乐路径。

### 3.4 数据校验

| 模糊需求 | EARS 改写 |
|---|---|
| 金额字段要校验 | `IF 退款金额为负数或超过原订单金额 THEN 系统 SHALL 拒绝该条记录并在校验报告中列出订单号` |
| 必填项不能空 | `IF 导出请求缺少 start_date 或 end_date THEN 系统 SHALL 返回 400 并指出缺失的具体字段名` |
| 时间格式要统一 | `系统 SHALL 接受 ISO 8601 格式的日期参数`<br>`IF 日期参数不符合 ISO 8601 THEN 系统 SHALL 返回 400 并给出格式示例` |
| 空值要处理好 | `IF 某订单无退款记录 THEN 系统 SHALL 在退款金额列输出 0 而不是空值或 null` |

"要处理好"是最典型的假标准。**处理成什么**才是标准：0？空字符串？跳过这行？三种做法下游会各选一种。

### 3.5 兼容性

| 模糊需求 | EARS 改写 |
|---|---|
| 不能影响现有调用方 | `WHEN 已有客户端调用 v1 导出接口且未传 include_refund 参数 THEN 系统 SHALL 返回与本次变更前完全一致的列集合` |
| 老数据也要能用 | `IF 订单创建于本次上线之前且无退款关联记录 THEN 系统 SHALL 输出 0 而不是报错` |
| 要支持主流浏览器 | `WHERE 浏览器为 Chrome / Safari / Edge 的最近两个大版本 系统 SHALL 支持直接下载导出文件` |
| 数据库升级要平滑 | `WHILE 迁移脚本正在执行 系统 SHALL 继续以只读模式提供报表查询` |

兼容性标准写清楚**谁是消费方**。写"不能影响现有调用方"，QA 无从判断该拿哪个客户端去测。

### 3.6 UI 行为

| 模糊需求 | EARS 改写 |
|---|---|
| 导出中要有反馈 | `WHILE 导出任务处于 running 状态 系统 SHALL 在按钮位置显示进度百分比并禁用重复提交` |
| 完成后要通知用户 | `WHEN 导出任务完成 THEN 系统 SHALL 在页面右上角显示可点击的下载链接并保持至少 30 秒` |
| 表格要好看好用 | 拆成可验证的几条：<br>`WHEN 报表列数超过屏幕宽度 THEN 系统 SHALL 横向滚动而不换行折叠`<br>`系统 SHALL 冻结报表首列与表头` |
| 要支持无障碍 | `系统 SHALL 为导出按钮提供 aria-label`<br>`WHEN 用户使用键盘 Tab 导航 THEN 系统 SHALL 按视觉顺序聚焦筛选项、导出按钮、结果列表` |

UI 类标准里出现「好看」「直观」「友好」时，正确做法不是硬找一个数字，而是问：**用户做什么动作、看到什么结果，才算这条成立？** 答不出来的，标 `verification: manual` 并指定 `verified_by`，比编一个假的自动化标准诚实。

## 4. 六类常见错误

### 4.1 把任务写成标准

标准描述**系统的行为**，任务描述**人要做的工作**。混淆的后果是 QA 无法测——你没法测"重构完成了"。

```
❌ 优化报表导出逻辑
❌ 重构 ReportExporter 类，抽出 RefundCalculator
❌ 给导出接口加缓存
✅ WHEN 用户在 5 分钟内重复提交相同参数的导出请求 THEN 系统 SHALL 直接返回上次的结果文件
```

识别方法：这句话的主语是不是「我们」「开发」？动词是不是「重构/优化/添加/实现」？那就是任务。任务属于 build 的 ledger，不属于 contract。

### 4.2 不可验证的形容词

```
❌ 系统应该有良好的性能
❌ 错误提示要友好
❌ 导出要高效可靠
❌ 界面要直观易用
```

每一个都要换成"什么条件下、什么可观测结果"。换不出来的，说明这条要求还没被想清楚——它应该回到 exploration.md 的未决问题，或者在 contract 里成为一条 `open_decisions`，而不是被塞进 criteria 假装已经定了。

### 4.3 一条标准塞多个行为

一条 criterion 只能有一个 `SHALL`。多个行为塞一条，会导致 QA 无法给出部分结论——测出来一半过一半不过时，这条算过还是不过？

```
❌ 1.1  WHEN 用户导出报表 THEN 系统 SHALL 包含退款金额、支持按部门筛选、并在 10 秒内完成

✅ 1.1  WHEN 用户导出月度报表 THEN 系统 SHALL 在每行包含该订单的退款总额
✅ 1.2  WHEN 用户指定部门筛选条件 THEN 系统 SHALL 只导出该部门及下级部门的订单
✅ 1.3  WHEN 用户提交行数不超过 5 万行的导出请求 THEN 系统 SHALL 在 10 秒内产出可下载文件
```

看到「并且」「同时」「以及」「，还要」就停下来拆。**数量不是问题，含糊才是**——criteria 有 30 条不奇怪，一条里有三个 SHALL 才奇怪。

### 4.4 隐含前置条件没写出来

写标准的人心里有一堆默认前提，读的人没有。

```
❌ WHEN 用户导出报表 THEN 系统 SHALL 包含退款金额
   （哪种报表？月度还是明细？所有用户都能导吗？导出的是全部订单还是筛选后的？）

✅ WHEN 具备 report:export 权限的用户导出月度对账报表 THEN 系统 SHALL 在每行包含该订单的退款总额
```

自查方式：把这条标准念给一个不了解这个项目的人听，问他"你会怎么测"。他要反问的每一个问题，都是一个没写出来的前置条件。

### 4.5 把实现方式写进标准

标准写**做到什么**，不写**怎么做到**。写死实现方式会让 Build 失去合理的选择空间，也会让标准在重构后失效——明明行为没变，测试却挂了。

```
❌ WHEN 用户导出报表 THEN 系统 SHALL 通过 Redis 缓存查询结果
✅ WHEN 用户在 5 分钟内重复提交相同参数的导出请求 THEN 系统 SHALL 在 1 秒内返回结果

❌ 系统 SHALL 使用 pandas 生成 Excel 文件
✅ 系统 SHALL 输出可被 Excel 2016 及以上版本直接打开的 .xlsx 文件
```

例外：技术选型确实是被批准的约束时（合规要求、既有架构决定），它属于 `policies` 字段，不属于 criteria。

### 4.6 只写快乐路径

一份只有 WHEN 没有 IF 的 criteria 清单，是这一环最常见的系统性缺陷。写完之后逐条过一遍：

- 这个输入越界了会怎样？
- 这个依赖挂了会怎样？
- 这个操作被并发触发会怎样？
- 权限不足的人来做会怎样？
- 数据不存在 / 为空 / 是历史遗留格式会怎样？

每个答案都是一条 IF-THEN。答不出来的，写进 `open_decisions`。

## 5. 层级编号

编号是**全套件的连接坐标**：build 的任务写 `_Criteria: 1.1_`，qa 的 Test Intent 绑定 `criterion: "1.1"`，release 的 Evidence Case 按它组织，`coverage_stats.py` 靠它统计覆盖缺口。

### 组织方式：按 requirement 分组

第一级 = requirement 的序号，第二级 = 该 requirement 下的第几条标准。

```yaml
requirements:
  - id: R1
    text: 月度报表包含每笔退款的金额与发生时间
    criteria: ["1.1", "1.2", "1.3"]
  - id: R2
    text: 导出受部门权限约束
    criteria: ["2.1", "2.2"]

criteria:
  - id: "1.1"
    ears: "WHEN 用户导出月度对账报表 THEN 系统 SHALL 在每行包含该订单的退款总额"
  - id: "1.2"
    ears: "IF 某订单无退款记录 THEN 系统 SHALL 输出 0 而不是空值"
  - id: "1.3"
    ears: "WHEN 用户导出月度对账报表 THEN 系统 SHALL 在每行包含最近一次退款的发生时间（UTC）"
  - id: "2.1"
    ears: "WHEN 用户导出报表 THEN 系统 SHALL 只包含该用户所属部门及其下级部门的订单"
  - id: "2.2"
    ears: "IF 请求导出的用户不具备 report:export 权限 THEN 系统 SHALL 返回 403 且不返回任何数据行"
```

### 规则

- **两级为止**。`1.2.3` 说明 requirement 拆得不够细——把它拆成两条 requirement，不要加第三级。
- **id 写成字符串**（YAML 里加引号）。不加引号 `1.10` 会被解析成浮点数 1.1，和 `1.1` 撞车。
- **编号唯一，且一旦被下游引用就不再改**。
- **删除时不补位**。删掉 `1.2` 之后，`1.3` 保持 `1.3`，不要往前挪——下游引用的是编号本身。
- **新增往后追加**。R1 下新增一条就是 `1.4`，即使它在逻辑上属于中间。
- 补充说明写在 `notes` 字段，不要写进 `ears`——`ears` 一行一句，多余的话会污染 QA 的读取。

✅
```yaml
  - id: "1.4"
    ears: "IF 退款金额为负数 THEN 系统 SHALL 拒绝该条记录并在校验报告中列出订单号"
    verification: automated
    notes: 负数退款在历史数据中出现过 3 次，来源见 exploration.md F7
```

❌
```yaml
  - id: 1.10                    # 未加引号，会被解析成 1.1
    ears: "IF 退款金额为负数 THEN 系统 SHALL 拒绝。注：历史数据里有 3 条这样的记录，
           需要 build 时注意兼容，另外这条可能还要考虑并发场景"   # 说明混进 ears，且藏了第二条标准
```

## 6. 写完自查

对每一条 criterion 问这几句：

- [ ] 它含 `SHALL`，且是五模式之一？
- [ ] 它只有一个 `SHALL`（没有「并且」「同时」）？
- [ ] 主语是系统的行为，不是人的工作？
- [ ] 里面没有「良好」「友好」「高效」「直观」这类形容词？
- [ ] 一个不了解本项目的人读完，能说出怎么测吗？
- [ ] 它写的是「做到什么」而不是「用什么技术做」？
- [ ] 它的编号是字符串、两级、唯一？

对整份 criteria 清单问：

- [ ] 每条 requirement 至少挂一条 criterion？
- [ ] IF-THEN 类（异常路径）占比是否合理——一条都没有基本可以确定是漏了
- [ ] 每条的来源都能指回 exploration.md 的某条事实、澄清结论或假设？
