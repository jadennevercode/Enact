## 为什么这一步最容易被跳过

因为它是唯一一件**做完之后线上不会有任何变化**的事。

报警停了，用户不投诉了，补丁合并了——此刻所有人的注意力都在离开这个事故。上游归位的收益要等到下一次、下下次工作才兑现，而它的成本是现在就要付的：写一份 AMD、加一条 criterion、提一个 LP，每一样都要有人看、有人批。

于是它被跳过。跳过的方式通常不是"决定不做"，而是"没想起来"——incident.md 第 6 节留空，事故标为已关闭，三个月后同一类问题换个入口再发生一次。

判别的入口问题只有一句：

> **如果这个根因明天以另一种形式出现（另一个接口、另一个字段、另一个客户），现有的 Contract / 测试标准 / 流程能拦住它吗？**

拦不住，就有上游对象要改。

---

## 判别总表

| 根因类型 | 通常该更新什么 | 判别信号 |
|---|---|---|
| 需求理解偏差 | Execution Contract（走 AMD） | 代码实现的是 Contract 写的东西，但业务方说"我要的不是这个" |
| 边界条件未考虑 | 新增 criterion + 对应 Test Intent | Contract 是对的，只是从来没提过这种输入/状态/规模 |
| 接口契约不一致 | 接口规则文档 + 双方 contract | 我方与上下游对同一字段的理解不同，且没有一份双方都引用的文档 |
| 测试覆盖盲区 | 测试标准 / Execution Class 调度规则 | Contract 有这条 criterion，测试也"通过"了，但它测不到真实场景 |
| 流程本身有漏洞 | Skill / 模板 / 清单（走 LP） | 换一个人、换一个功能，按现有流程走一遍还会犯同样的错 |
| 环境与配置 | 部署文档 + **Policy / 保护范围**（`config.yaml` 的 `protected_paths` / `data_policy`） | 代码在所有环境都一样，只有生产坏了 |

一次事故可以命中多类。**不要为了让表格干净而只挑一类填**——需求偏差往往同时暴露测试盲区，接口不一致往往同时暴露流程漏洞。

## 六类根因详解

### 1. 需求理解偏差 → Execution Contract

**典型信号**
- 业务方看到修复方案时说"这个我们本来就以为是这样的"
- 代码严格实现了某条 criterion，而那条 criterion 本身描述错了业务规则
- 事故的"正确行为"在 contract.yaml 里找不到任何一条对应条款
- exploration.md 里这条是一条 Assumption，从没被人确认过

**怎么确认**
打开原 WI 的 `contract.yaml`，找与故障行为对应的 criterion 编号。三种结果：
- 找到了，且写的与业务期望不符 → 确认是需求偏差
- 找到了，写的是对的，代码没照做 → 这是实现缺陷，不属于本类
- 找不到任何对应条款 → 也是本类（Contract 漏了一整块意图）

**产出什么**
在原 WI 下提 `amendments/AMD-###.md`：写清冲突的两处说法各在哪里、为什么不能在实现里解决。由 sdlc-contract 裁决并生成 contract 新版本，原版本标 `superseded` 但不删。

顺带回看 exploration.md：这条是不是一条没人确认就进了 Contract 的假设？如果是，探索环节的"假设记账"规则可能也需要一条 LP。

---

### 2. 边界条件未考虑 → criterion + Test Intent

**典型信号**
- Contract 描述的主流程完全正确，故障发生在一个从没被讨论过的输入或状态上
- 出问题的是：空值、超长、并发、时区、跨天、数据量级、重试、部分失败、权限降级
- 复盘时大家的反应是"哦，这种情况确实没想到"，而不是"这写错了"

**怎么确认**
把故障时的真实输入/状态写成一句话，然后去 contract.yaml 逐条比对：有没有任何一条 criterion 覆盖了它？没有，就是本类。

区别于第 1 类的关键：需求偏差是**写错了**，边界条件是**没写到**。处置不同——前者改现有条款，后者新增条款。

**产出什么**
1. AMD 新增一条 EARS criterion，编号接在原 requirement 下（如原有 `2.1`、`2.2`，新增 `2.3`）
2. 交 sdlc-qa 补对应的 Test Intent，绑定这个新编号
3. 判断这是不是**一类**边界而不是一个：如果"超长输入"没考虑，那"空输入""特殊字符"多半也没考虑。一次补一类，比事故三次各补一条划算

---

### 3. 接口契约不一致 → 接口规则文档 + contract

**典型信号**
- 报错来自反序列化、类型转换、字段缺失、枚举值未知
- 上游说"我们一直是这么返回的"，我方说"文档里不是这么写的"
- 双方各有一份文档，两份说法不同，且没人负责对齐
- 或者更常见：根本没有一份双方都引用的文档，靠口头和抓包

**怎么确认**
找出**双方都引用的那一份**接口定义在哪里。找不到，本类成立——不一致只是时间问题，这次只是刚好轮到这个字段。

**产出什么**
- 项目内的接口规则文档 / schema 文件的修订（这是一次正常的文档变更，走新 WI）
- 我方 contract 里补一条关于该接口契约的 criterion，让它被测试覆盖
- 如果我方 contract 里对上游行为的假设从没被验证过 → 提 AMD 把它变成显式条款
- 跨团队的对齐动作属于"需人批准"分类，不要自己替对方决定

**不要**把处置停在"我方加一个 null 判断"。加了判断，下一个字段照样炸。

---

### 4. 测试覆盖盲区 → 测试标准 / Execution Class 调度规则

**典型信号**
- 该 criterion 在 `qa-report.md` 里显示"通过"，但故障恰好发生在它应该覆盖的范围内
- 测试用的是 mock，而故障来自被 mock 掉的那一侧
- 测试跑在 Fast deterministic 类，而故障只在 cross-service 环境出现
- 某个 Gate 类测试当时被"临时跳过"，`qa-report.md` 里有记录（或者更糟，没有记录）
- 测试 locator 绑的是 CSS 类名，页面结构变了测试仍然通过

**怎么确认**
打开 `test-plan.yaml`，找绑定该 criterion 的 TestCase，看它的 Execution Class 与执行环境。问一句：**这个测试在故障发生的那种条件下会跑吗？** 不会跑，就是调度规则的问题，不是用例的问题。

**产出什么**

| 具体盲区 | 改哪里 |
|---|---|
| 用例本身写得测不到 | 补 Test Intent（交 sdlc-qa，属下游） |
| 整类场景没有对应的验证策略 | 测试标准修订（走 LP） |
| Execution Class 分配错了（该跑集成的跑成了单测） | Execution Class 调度规则（走 LP） |
| Gate 类测试被静默跳过 | 流程漏洞，走第 5 类 |

只补一个用例是下游动作。**判断标准是"这个盲区是这一条独有的，还是一整类场景都没被安排验证"**——后者才需要改标准。

---

### 5. 流程本身有漏洞 → Skill / 模板 / 清单（走 LP）

**典型信号**
- 复盘时发现"按现有流程走完全程，也不会发现这个问题"
- 同类事故不是第一次（翻 `.sdlc/incidents/`，有没有相似的）
- 某个必填项在模板里没有位置，于是没人填
- 某个检查存在，但没有任何一步要求执行它
- 事故期间的豁免记录没补齐，而且流程里没有任何机制会提醒补

**怎么确认**
做一次反事实推演：**假设换一个人、换一个功能，严格按现有 Skill 和模板走一遍，这个缺陷会在哪一步被拦下？** 答不上来任何一步，本类成立。

**产出什么**
`.sdlc/lessons/LP-###-slug/lesson.md`，移交 **sdlc-learn** 走六阶段闭环。带上：现象、根因、你认为该改哪个文件的哪一节、以及本次的证据引用。

**你不直接修改任何模板或 Skill 文件。** 一次成功的处置不等于普遍规律；未经验证就固化的"经验"会污染之后所有工作，而且极难回溯（红线 4.2）。sdlc-learn 会先做 Validate（用历史案例和反例验证适用范围），再拿具名批准，然后才动文件。

说不清适用边界的 Lesson 不要推进——"这次这样做对了"不足以支撑"以后都该这样"。

---

### 6. 环境与配置 → 部署文档 + Policy / 保护范围

**典型信号**
- 同一份代码在测试环境正常，只有生产坏了
- 根因是环境变量、密钥、连接串、资源配额、限流阈值、feature flag 状态
- 某项配置的当前值没人说得清是谁改的、什么时候改的、为什么是这个值
- 配置改动没有出现在任何 WI 的 change-scope 里

**怎么确认**
问两个问题：这项配置的**期望值**记录在哪个文件里？它的改动**经过**了哪次评审？两个都答不上来，本类成立。

**产出什么**
- 部署文档 / 环境配置清单的修订：把这项配置的期望值、生效范围、谁能改写下来
- **`.sdlc/config.yaml` 的保护范围补充**——落在 incident.md 第 6 节的 `Policy / 保护范围` 行：
  - 改错的代价是生产事故 → 进 `protected_paths`，以后改它要走 scope expansion 的人工 Gate
  - 根因涉及密钥、凭据、个人数据被读进上下文或写进证据 → 进 `data_policy.never_read` 或 `evidence_redaction`
  - 某类命令本就不该由 Agent 直接跑 → 进 `tool_actions.always_forbidden`
- 如果配置漂移是长期存在的（多个环境值不同且无人知情）→ 同时属于第 5 类，走 LP

**不要**把处置停在"把生产的值改回去"。值改回去了，下次还是没人知道它该是多少。

---

## Policy / 保护范围这一行放什么

上游对象有五类，Policy 是最晚被想起来的一类——因为它不像 Contract 或测试标准那样有明确的产物文件，它的载体是 `.sdlc/config.yaml` 里几行 glob。

**归到这一行的，是"以后什么东西不许被随手动、不许被随手读"这类结论**：

| 事故里出现了什么 | 落到哪一项 |
|---|---|
| 一次误改配置/基础设施/CI 就打穿了生产 | `protected_paths` 补一条，以后改它要走 scope expansion 的人工 Gate |
| 密钥、凭据、连接串被读进上下文，或写进了日志、notes、证据 | `data_policy.never_read` / `evidence_redaction` 补模式 |
| 某个有副作用的命令本就不该由 Agent 直接执行 | `tool_actions.always_forbidden` 补一条 |
| 某类数据的保留期或外发范围事后才发现没约定 | `data_policy.trace_retention` / `external_send` 补充 |

**它与"Skill / 模板 / 清单"那一行的分界是适用范围，不是内容**：

- 结论只对**本项目**成立（"我们这套 k8s 配置该保护起来"）→ Policy 行，走新 WI 直接改 `.sdlc/config.yaml`，改动本身也要有人批。
- 结论对**所有项目、所有工作**都成立（"这类文件本来就该默认保护"、"这个检查本来就该出现在清单里"）→ 走 LP 交 sdlc-learn，`target_kind: policy`，由它做 Validate 和具名批准之后才改共享定义。

分不清时选 Policy 行 + 本项目生效。把一条只在这个项目成立的规则推成全套件标准，代价比反过来大得多——它会在别的项目里以"这条规则莫名其妙"的形式被绕过，然后连带削弱其余规则的可信度。

**这一行填"无"也要有依据**：本次根因与配置、保护范围、密钥、命令权限都无关。写得出这句话就够了，写不出就说明还没想过。

## 成对例子

**例 A：导出接口对某客户返回 500**

❌ 只打补丁的处置
> 根因：`refund_amount` 字段在部分历史订单中为 null，导出时 KeyError。
> 修复：`src/reports/exporter.py` 加 `.get('refund_amount', 0)`。
> 上游归位：（空）
> 事故关闭。

这份记录里，"为什么当初没人想到历史数据可能缺这个字段"完全没有被回答。下一次导出加新字段，同样的事会再发生一次。

✅ 完成上游归位的处置
> 根因：Contract 的 criterion 2.1 假定所有订单都有 `refund_amount`，该假定来自 exploration.md 的一条 Assumption，从未被数据核实。属"边界条件未考虑"。
> 上游归位：
> - Execution Contract → AMD-003：新增 criterion 2.3「WHEN 订单缺少 refund_amount THEN 系统 SHALL 以 0 参与导出并在导出说明中标注」
> - 测试标准 → 交 sdlc-qa 补 TI 绑定 2.3，并追加"历史数据完整性"这一类场景（不止此一字段）
> - Skill/模板 → LP-002：exploration 模板的 Assumptions 节没有要求"数据类假设必须用真实数据核实一次"
> - Policy / 保护范围 → 无——本次不涉及配置、保护范围、密钥或命令权限
> 修复：WI-014（lane: quick）
> 补记录：无豁免动作。

---

**例 B：发布后服务在流量高峰时 OOM**

❌ 只打补丁的处置
> 根因：内存不足。
> 修复：把 pod 内存 limit 从 512Mi 调到 2Gi，服务恢复。
> 上游归位：（空）

"内存不足"是现象不是根因；调大 limit 是缓解不是修复。这次买到的是时间，不是解决方案。

✅ 完成上游归位的处置
> 触发条件：流量高峰。根本原因：新增的报表聚合把整表载入内存，数据量随时间线性增长——即使不涨流量，两个月后同样会 OOM。
> 上游归位：
> - Execution Contract → AMD-004：Contract 的 requirement 3 完全没有规模约束条款，新增 criterion 3.4「WHEN 单次聚合涉及超过 10 万行 THEN 系统 SHALL 分批处理且常驻内存不超过 <阈值>」
> - 测试标准 → LP-003：现行测试标准中没有任何一类要求做数据量级验证，所有性能类 criterion 实际都跑在千行级 fixture 上
> - Policy / 保护范围 → 部署文档补记 memory limit 的设定依据；`infra/**` 下该 manifest 加入 `config.yaml` 的 `protected_paths`，以后调它要走 scope expansion
> 缓解：调 limit（WI-018，lane: quick，已确认执行），deadline 前必须由 WI-019 的分批实现替换
> 补记录：调 limit 时改了 protected 中的 k8s 配置，`gates/scope-expansion-001.yml` 记 `gate: WAIVED`，waiver.deadline 2026-08-23，已于 8-22 补签。

## 什么情况下确实只需要下游补丁

不是所有事故都有上游对象要改。以下情况下"无上游对象"是正确结论：

| 情形 | 为什么没有上游对象 |
|---|---|
| 纯粹的编码笔误，且 Contract、criterion、测试都是对的，测试也确实能测到它——只是这次没跑到 | 缺陷发生在实现层，治理链每一环都尽到了责任 |
| 第三方服务单方面故障，我方降级行为符合 Contract 已有条款并生效了 | 系统按设计工作了。上游归位的对象在别人家 |
| 一次性的人为操作失误，且该操作已经在受控流程内（有审批、有记录、有回滚） | 流程拦不住的是人的手滑，不是流程的漏洞 |
| 已知并已记录的技术债按预期方式暴露，`evidence-case.md` 第 6 节里有它、有 owner | 风险当时被显式接受了，这是决策的结果不是缺口 |

**但"没有"必须是一个判断，不能是一次省略。** 写"无上游对象"之前，逐条回答这四问，并把答案写进 incident.md 第 6 节：

1. **Contract 里能找到覆盖这次正确行为的条款吗？** —— 找不到 → 有上游对象（第 1 或 2 类）
2. **现有测试在故障发生的那种条件下会被执行吗？** —— 不会 → 有上游对象（第 4 类）
3. **换个人按现有流程走一遍，会在哪一步被拦下？** —— 答不上来 → 有上游对象（第 5 类）
4. **这类问题在 `.sdlc/incidents/` 里出现过吗？** —— 出现过 → 一定有上游对象，第一次的归位没做到位

四问都有明确的肯定答案，才可以写：

> 无上游对象。Contract criterion 1.2 已覆盖该行为；TC-007 在集成环境覆盖该路径且本次确实执行并通过；缺陷为 <具体> 的编码笔误，代码评审环节应当拦下且流程中确实有这一步；`.sdlc/incidents/` 中无同类记录。

## 填好的上游归位表长什么样

incident.md 第 6 节的五行，不是每行都必须有内容，但**每行都必须有结论**：

```markdown
## 6. 上游归位

| 该更新什么 | 具体哪一处 | 处置 |
|---|---|---|
| Execution Contract | WI-007 contract v1 criterion 2.1 假定字段必存在 | AMD-003（已提，待 sdlc-contract 裁决） |
| 接口规则 / 标准 | 无——本次不涉及跨系统接口 | 无 |
| 测试标准 | 无"历史数据完整性"这一类验证策略 | LP-002（走 sdlc-learn） |
| Skill / 模板 / 清单 | exploration 模板未要求数据类假设做真实核实 | 并入 LP-002 |
| Policy / 保护范围 | 无——本次根因不涉及配置、密钥或命令权限 | 无 |
```

对比一下不合格的填法：

```markdown
| Execution Contract | | |
| 接口规则 / 标准 | | |
| 测试标准 | 需要加测试 | |
| Skill / 模板 / 清单 | | |
| Policy / 保护范围 | | |
```

空格子和"需要加测试"这种没有具体对象、没有编号、没有承接方的内容，等价于没填——三个月后没有人能据此做任何事。
