# 红线

三条铁律加三条支撑规则。读到这里，通常是因为当前情形让某条红线显得不合时宜——那正是它存在的理由。

```
NO GATE PASSAGE WITHOUT A HUMAN APPROVAL RECORD
NO TEST EXPECTATIONS DERIVED FROM IMPLEMENTATION
NO WRITES OUTSIDE THE APPROVED CHANGE SCOPE
```

**违反字面就是违反精神。**

红线不在流程内协商。发现红线挡路时，正确的动作是停下来改产物或找人批准，而不是重新解释红线的适用范围。如果确实有一次无法消除的违背，走 §4 的书面记账流程——可以豁免，但要付书面代价。

---

## 1. Gate 必须有人类批准记录

**规则**：任何 Gate 的 `approved_by` 字段只能在一次真实的人工确认交互之后写入，填真实的人名或标识。AI 可以收集证据、解释证据、给出建议结论，但不能自己签字。

**为什么**：Gate 存在的意义是把风险接受这件事落到一个具体的人身上。一旦 AI 能自签，整条证据链就只是自证——出事之后没有人对这个决定负责，也没人能说清当时基于什么接受了风险。这不是形式主义：主规格把 Contract 批准、保护范围扩大、Release 这三处定为必须人工，正是因为它们各自对应一次不可逆的风险转移。本套件在此之上又加了两处——`lesson-approval`（改的是之后所有工作的标准）与 `build-review`（进 QA 之前看一眼方向），**共五个**，清单见 `gates.md`。

**具体表现**：
- `approved_by: AI` / `approved_by: Claude` / `approved_by: system` / 留空 / 填 `""` —— 全部无效。
- 用户说"你看着办"不等于批准某个具体 Gate。它是授权你推进工作，不是授权你替他签字。需要 Gate 时仍要明确问，把选项和影响摆出来。
- 用户在很久之前的一次批准不能延续到修改后的版本。产物一改，重新问。

| 借口 | 现实 |
|---|---|
| "用户说了不用问我，所以我直接过 Gate" | 他授权的是"不要为每个小决定打断我"，不是"替我承担生产风险"。把 Gate 攒起来一次性问，比自签好。 |
| "这个 Gate 显然会通过，问了也是浪费时间" | 显然会通过的 Gate 花 10 秒就能拿到批准。真正的成本在于：你判断的"显然"如果错了，没有任何人拦得住。 |
| "先填上 approved_by，等会儿补确认" | 补不上的。事后没人记得当时是不是真看过。记录的价值全在时序。 |
| "用户不在，工作不能停" | 工作可以停在 Held 状态。把待批清单写清楚，是比越权推进更有用的产出。 |
| "我在 reason 里写清楚了是 AI 判断的" | 那是在诚实地记录一次无效的 Gate。诚实不能让它变有效。 |

**自检信号——出现以下念头就停下**：
- "这次的批准可以推断出来"
- "用户的意思应该是同意"
- "先往下走，Gate 记录最后补"
- 写 Gate YAML 时，`approved_by` 一栏你不知道该填谁

## 2. 测试期望不得从实现推导

**规则**：Test Intent（预期行为）必须只依据已批准的 Execution Contract 生成，并在读实现之前冻结。之后才允许读实现来绑定 endpoint、fixture、locator、环境。

**为什么**：从实现反推测试，测的是"代码做了什么"，不是"代码该做什么"。这类测试永远通过，也永远发现不了需求被误解的情况——而需求误解正是最贵的缺陷类别。主规格把它列为必须修订的现有故事之一（US-31 同时从需求、设计和代码生成测试，违背独立 QA）。

**具体做法**：sdlc-qa 用一个只拿到 contract、拿不到实现代码的 subagent 产出 Test Intent 集，主会话再做绑定。这是结构性隔离，不是靠自觉。

| 借口 | 现实 |
|---|---|
| "看一眼实现能让测试更准确" | 更准确地符合实现，而不是更准确地符合需求。这正是要避免的。 |
| "Contract 写得太模糊，没法直接出测试" | 那是 Contract 的缺陷。提 Amendment 回到 contract 环节，这个发现比测试本身更有价值。 |
| "实现里的边界值就是正确的边界值" | 也许是，也许是个 off-by-one。你无法从实现本身判断——只有 Contract 能。 |
| "我只是看看函数签名" | 签名会告诉你参数顺序、可选性、返回结构，然后你的预期就长成了它的形状。 |
| "测试跑挂了，看看实现怎么写的再调一下预期" | 停。测试挂了说明实现与 Contract 不一致，该改的是实现，或者该提 Amendment。调预期是在销毁证据。 |

**自检信号**：
- 你在写 Test Intent 时打开了实现文件
- 某条预期值你说不出它来自 Contract 的哪一条编号
- 测试失败后你的第一反应是修改期望值

## 3. 不得在批准范围外写入

**规则**：可读范围与可写范围分开建模。读可以宽（要理解全局），写必须窄（`change-scope.yaml` 的 write 白名单）。碰到白名单外的文件、或需要调用未授权的工具类别，停止 → 说明理由 → 拿到确认 → 生成 change-scope 新版本 → 继续。

**为什么**：AI 能一次改动几十个文件，而人的复核带宽没有同步增长。范围边界是让复核成为可能的前提。更重要的是，越界往往发生在"顺手修一个看起来明显的问题"时——那个问题可能是别人有意为之，也可能属于另一个正在进行的变更。

**具体表现**：
- 改共享接口、数据模型、基础设施配置、安全配置——这些默认是 protected，即使没人明说。
- "重构一下顺便"、"这个 lint 错误顺手修了"、"删掉这段没用的代码"——都是越界，即使改动本身是对的。
- 新建文件也要落在白名单声明的落点内。

| 借口 | 现实 |
|---|---|
| "这个改动很小很安全" | 范围的意义不是防止你改错，而是让复核者知道该看哪里。小改动藏在大 diff 里最危险。 |
| "不改这个文件功能就不完整" | 那说明 change-scope 定小了。这是一次正常的范围扩大，走升级流程只需要一轮交互。 |
| "protected 目录里明显有 bug" | 记下来，作为独立发现交出去。在别人的保护区里修 bug，你既不知道它是不是有意的，也没人在复核你。 |
| "已经改完了，回退太麻烦" | 那就在 ledger 里如实记录这次越界，并立即补一次范围确认。掩盖比越界本身严重得多。 |
| "白名单里没写但同一个目录下" | 白名单是路径级的，不是目录精神级的。 |

**自检信号**：
- 你正要编辑的文件，不在 change-scope.yaml 的 write 列表里
- 你想"先改了再说，反正会被 review"
- 你要跑的命令类别没在 tool actions 里声明（尤其是任何有网络副作用、会 push/publish/部署的命令）

## 4. 三条支撑规则

这三条不如上面三条刚性，但违反它们同样会让治理链断掉。

**4.1 发现上游缺口不得在下游补意图。** Build 或 QA 中发现 Contract 不完整、矛盾、或与现实不符时，不允许自己决定"应该是什么意思"然后写进代码。提 Contract Amendment（`amendments/AMD-###.md`）回到 contract 环节。理由：Contract 是 QA 与 Release 的唯一锚点，一旦实现里悄悄夹带了没写进 Contract 的意图，QA 测不到它，Release 也不知道自己批准了什么。

**4.2 经验不得自动变成标准。** 任何模板、检查清单、Skill 文件的修改，只能由 sdlc-learn 在拿到 `lesson-approval.yml`（含具名批准）之后执行。理由：一次成功不等于普遍规律；未经验证就固化的"经验"会污染之后所有工作，而且极难回溯。

> sdlc-learn 是本套件唯一能改动能力资产的入口，所以它把这条写成本环节的铁律：
> `NO ASSET CHANGES WITHOUT AN APPROVED LESSON`。在别的环节它是支撑规则，在 learn 里它是主场。

**4.3 无可信依据时不得给出事实性结论。** 找不到权威来源就说找不到，并提出需要补充什么。版本冲突时显示冲突和各自来源，不静默选最新。所有事实性陈述可回溯到具体文件与版本。理由：一条编造的"事实"进入 Contract，会一路传导到实现、测试和发布证据，而且看起来和真事实一模一样。

---

## 5. 无法消除的违背：书面记账

极少数情况下确实存在无法通过改产物消除的违背（例如生产事故中必须先止血、批准人不可达且损失在扩大）。这时可以豁免，但必须留下书面代价：

在对应的 Gate YAML 里增加 `waiver` 段：

```yaml
gate: WAIVED
approved_by: <事后补签的具名责任人>
status_reason: <一句话说明当时发生了什么>
waiver:
  redline: <违背了哪条红线>
  why_unavoidable: <为什么改产物或等批准不可行>
  what_was_done_instead: <实际采取的动作>
  compensating_record: <事后补齐了什么：补签、补测、补 Amendment>
  deadline: <补齐动作的截止时间>
```

`gate: WAIVED` 与 `gate: PASS` 在统计和审计里是两回事。豁免可以用，但每一次都会留在 history 里被看见——这正是它该有的成本。

未经这个流程的违背，就只是违背。
