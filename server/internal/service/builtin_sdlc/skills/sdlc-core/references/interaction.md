# 澄清提问协议

**什么时候读**：任何环节要向人提问、收集判断、处置未决问题之前。

本文件管**收集信息**的提问。收集**授权**（Gate 批准、范围扩大、发布决定）是另一件事，
话术和呈报格式在 `gates.md`，不要混用——问"你想怎么办"和问"你批不批"，
需要的信息量和责任落点完全不同。

## 1. 为什么改掉"一次一问"

本套件早期版本写死了「一次只问一题」。它要防的失败是真实的，实测记录如下：

> 一次抛五个开放式问题，用户会挑最容易的那个回答，最难的那个——通常也是最重要的
> 那个——被沉默地跳过。

**这个观察没错。错的是把"串行"当成了唯一解药。**

串行的代价在实测里同样明显：问一句、等一句、再问下一句。用户看不到这场对话有多长、
还要被打断几次、这些问题之间有没有关系。他失去的是**判断的上下文**——第 3 个问题的答案
往往取决于他对第 5 个问题的倾向，而串行让他在看到第 5 个问题之前就得回答第 3 个。
拿到的答案因此更差，不只是体验更碎。

真正要防的不是"一次给多个问题"，是**问题被沉默地跳过**。这件事有结构化的解法，
不需要牺牲连续性：

| 失败模式 | 串行的做法 | 本协议的做法 |
|---|---|---|
| 挑软的答 | 一次只给一个，没得挑 | 每题带选项，答一题的成本被压到选一个字母 |
| 难的被跳过 | 靠"下一个问题"逼出来 | **回执**逐题点名，没答的下一轮明确标「上一轮未答」重问 |
| 看不到全貌 | 未解决 | **议程先行**：先亮出全部问题再开始问 |
| 一句"都行"打包了事 | 未解决（串行同样会得到"都行"） | 「都行」不是选项之一，回执里它算未答 |

## 2. 三段式：议程 → 成批 → 回执

### 第一段：议程先行

事实盘点做完、缺口排完序之后，**先把完整的问题清单亮出来**，再开始问第一题。
议程给的是形状，不是内容：

```
需要你定的一共 5 件事，按影响面排序。我会分两轮问，每轮给选项。

1. 历史退款单怎么处理        影响：迁移脚本 + 对账口径
2. 金额小数位数              影响：数据结构，改错要迁移
3. 新字段进不进对外 API      影响：接口契约，影响消费方
4. 并发退款的处理顺序        影响：一致性策略
5. 列表默认分页大小          影响：一个常量（这条我倾向直接取默认值，你不反对就跳过）

前三条我先问，答完再问后两条。
```

议程里就可以**主动降级**：能猜的直接说"我打算猜、猜什么、你不反对就跳过"。
把 5 个问题变成 3 个问题的最好时机是在问之前，不是在用户已经被打断之后。

**议程要先落盘再呈报**，见 §6。

### 第二段：成批提问

一轮 **≤4 题**，同一主题的放在一轮。每题按 §3 的形状写。

为什么是 4：这是"一屏能读完、还能记住第 1 题在问什么"的边界。超过 4 题，
用户开始需要往回翻——往回翻的那一刻，跳过就又开始了。
（多数结构化提问接口的单轮上限也在这个量级，但那是巧合，不是理由。）

用户在**一条消息里答完整批**是正常的，也是这个设计想要的：`1A 2B 3标记未决`。

### 第三段：回执

每轮答完，**逐题点名**这一轮的处置结果，然后立刻写回产物：

```
收到，已写入 exploration.md：
1 → A（历史单 fee=0，principal=amount）
2 → 两位小数
3 → 你没答，下一轮重问

下一轮：3（上一轮未答）、4、5。
```

回执是这套协议的承重结构。没有它，成批提问就退化成"抛一堆问题然后假装都答了"——
那才是当初写下「一次一问」时真正在防的东西。

**含糊回答在回执里按未答处理。** "都行"、"你看着办"、"应该没问题"不是决定。
回执里写「3 → 未答」，下一轮重问，或者由你给出默认值并明确说"我按 A 走了，记进假设"。
不要把含糊回答写成一条看起来有人拍过板的结论。

## 3. 一个问题应该长什么样

四件事，缺一件这个问题就该重写：

1. **问题本身**，一句话，具体到能回答
2. **为什么问**：这个答案会改变什么。让用户看出你已经查过了
3. **来源**：你查到了什么（带文件路径行号），或者明确写"查不到"
4. **2–5 个选项**，标推荐项，每项写清影响与风险

✅ 好的澄清问题：

> **退款拆分后，已存在的 1.2 万条历史退款单怎么处理？**
> 问这个是因为：`src/models/refund.py:31` 现有 `amount` 是非空字段，加拆分列必然要决定
> 历史数据填什么，这个决定会传导到迁移脚本和对账口径。
> - **A（推荐）**：历史单 `fee=0`、`principal=amount`。对账口径不变，迁移最简单。风险：如果历史上真收过手续费，账就是错的。
> - **B**：历史单三个字段都置 NULL，查询侧区分新旧。对账要改。
> - **C**：回填真实手续费。需要 DBA 确认能否从支付流水关联，工期不可控。
> - **标记未决**：留给 DBA 判断，进 open decisions。

❌ 坏的澄清问题：

> 关于这次的退款功能，我想确认几点：1）业务背景是什么？2）有哪些用户角色？
> 3）性能要求如何？4）需要考虑安全吗？5）什么时候上线？

坏在四处：全是开放式、没有一个说明了为什么要问、没有选项、而且第 1 和第 2 问在
objective 和代码里本来就查得到。**这是把问卷念了一遍。**注意它坏的地方不是"一次五问"——
把这五个问题拆成五轮串行地问，五个毛病一个都没少。

用户的合法回答有三种：**选一个 / 改一个 / 标记未决**。未决是合法状态——
带着已知的未决往下走，好过假装它不存在。

## 4. 什么必须单独问

成批是默认，以下三类**单独问，一次一个**：

| 类别 | 例子 | 为什么 |
|---|---|---|
| **不可逆** | 删数据、改线上配置、对外发公告 | 批量勾选会让人用处理清单的心态处理一个不能撤销的决定 |
| **授权类** | 任何 Gate、范围扩大 | 责任要落到具体的人，走 `gates.md` 的话术，不走本协议 |
| **前一题的答案会改变后一题是否存在** | "要不要做灰度" → 决定了后面三个灰度参数问不问 | 打包问会逼用户回答一个可能根本不存在的问题 |

第三类要在议程里就体现出来：写「先定 1，1 的答案决定 2–4 还问不问」。

## 5. 配额

- 一轮 **≤4 题**（上限，不是下限。只有 1 个问题就问 1 个，不要凑）
- 未决标记全程 **≤3 个**（硬上限。超过说明在发散，先收敛已有的）
- 轮次没有硬上限，但**每多一轮，议程都要重报一次剩余项**——用户不该需要往回翻才知道还剩几件事

数量约束一律是上限。强制凑满会逼出编造的问题，而编造的问题会得到编造的答案。

## 6. 落盘先于呈报

**议程和每一轮的答案，先写进产物文件，再出现在对话里。** 顺序不能倒。

理由是实测出来的：对话里的总结不是产物。上下文一压缩、会话一换，凝练过的结论
就只剩你记得，而"你记得"在下一个环节读文件的时候一点用都没有。

具体到落点：

| 内容 | 落到哪 | 什么时候 |
|---|---|---|
| 完整问题议程 | `exploration.md` §5 未决问题（或本环节对应的未决节） | **提问之前** |
| 每轮答案 | 对应正文节，并**消灭与之矛盾的旧内容** | 回执的同时 |
| 被采纳的默认值 | `exploration.md` §3 Assumptions，含"如果错了会怎样" | 回执的同时 |
| 每个被回答的问题 | `evidence.jsonl` 追加 `question_answered` | 回执的同时 |

不要留着两个版本等最后统一整理——中途上下文一压缩，你会不知道哪个是新的。

## 7. 有结构化提问工具时怎么用

当前 Runtime 提供**结构化提问接口**（能一次给出多个带选项的问题、并把每题作为独立控件呈现的那种）
时**优先用它**：它把"每题都要被处置"变成界面约束，比靠自觉可靠。用法对齐本协议——
一次 ≤4 题、每题带选项、推荐项排第一。

具体叫什么名字由 Runtime 决定，本套件不绑定任何一家的工具名——同一套协议要能在
Claude Code、Codex 和 Enact 管理的 Runtime 上都跑得通。

没有这类工具时（纯文本 Runtime），用 §2 的三段式手写，回执那一段**尤其不能省**——
纯文本环境里它是唯一能让"跳过"变得可见的机制。

两种情况下议程和落盘纪律都一样，不因工具而变。
