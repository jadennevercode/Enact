# 晋升指南

- [1. 什么样的经验值得晋升](#1-什么样的经验值得晋升)
- [2. 目标类型怎么选](#2-目标类型怎么选)（七类 + `new_asset`）
- [3. Validate 怎么做](#3-validate-怎么做)（含 Validation 六项与回归集）
- [4. 怎么安全地修改目标资产](#4-怎么安全地修改目标资产)（含采用范围、新建、Amend、Deprecate）

这份文件解决四个判断题：这条经验配不配进受治理资产、该进哪一层、怎么证明它成立、怎么改才不会误伤。

判断的成本不对称，值得先说清楚：**漏掉一条好经验，损失是下次再犯一次同样的错；固化一条坏经验，损失是之后每一次工作都被它影响，而且没人知道它是从哪来的。**所以这里的默认答案偏保守——拿不准就留在候选状态等下一次复现，不要现在推进。

## 1. 什么样的经验值得晋升

### 三个必要条件

**跨场景复现。** 在至少两个不同的 Work Item、场景或时间点上出现过同一个问题或同一个有效做法。一次事件是样本，不是规律。

**边界清楚。** 你能说出它在什么条件下成立，也能说出什么情况下不适用。说不出反例的经验没有边界，没有边界的规则会在你没预料到的场景里误伤。

**有证据支持。** 每条主张都能指回一个具体的文件和位置——`WI-003/qa-report.md#失败归因`、`INC-002/incident.md#根因`、evidence.jsonl 里的某条 `boundary_stop`。凭印象说的"我记得上次也这样"不算证据，去把上次翻出来。

### 判断清单

推进之前逐条过一遍。任何一条答不上来，就留在 `observe` 或退回 `classify`：

- [ ] 这件事发生过几次？分别是哪几次？（能报出编号）
- [ ] 换一个项目、换一个技术栈，它还成立吗？
- [ ] 如果不固化，下次会不会有人自然而然地做对？（会 → 不值得固化）
- [ ] 它是一条规律，还是一次运气？（上次成功是因为方法对，还是因为场景刚好合适）
- [ ] 它和现有的哪条规则冲突或重叠？
- [ ] 如果这条规则三个月前就存在，历史上哪些正确的做法会被它拦下来？

### 四类不值得晋升的候选

| 反例 | 表现 | 正确处置 |
|---|---|---|
| **只发生过一次** | "这次踩了个坑，记下来" | 留在 `observe`，等第二次。第二次不来，说明它本来就不重要 |
| **只在这个项目成立** | 依赖本项目的技术栈、目录结构、团队约定、历史包袱 | 目标改成 `project-doc`，不要碰 template 和 skill |
| **其实是个人偏好** | "这样写更清楚""我习惯先 X 再 Y"，说不出不这样做的具体损失 | 拒绝。偏好写进标准，会变成别人的成本 |
| **是执行问题不是规则问题** | 规则已经写在那里，只是这次没照做 | 拒绝。再写一遍不会让人更照做；该看的是规则为什么没被读到 |

还有一类要特别小心：**用一条新规则去补一条旧规则没被遵守的洞**。这会让文档越堆越厚，而每一层都在稀释前一层的注意力。

### ✅ / ❌ 对照

✅ **值得晋升**
> WI-003 和 WI-007 的 contract 都漏了外部支付网关不可用时的降级行为，两次都在 QA 阶段才发现，各返工一轮。→ 在 contract 模板的 requirements 节增加一条提示：涉及外部依赖时，说明依赖不可用时的预期行为。

理由：复现两次、能指到具体文件、边界清楚（只针对外部依赖）、代价可量化（两轮返工）。

❌ **不值得晋升**
> 这次先写测试再写代码感觉效率更高，应该写进 build 的 SKILL.md。

理由：一次；"感觉"不是证据；说不出什么情况下不适用；而且这是通用工程主张，不是这个套件在这次工作里发现的东西。

✅ **值得晋升（但目标是 project-doc）**
> 本项目的 legacy 报表模块用了一套自己的日期工具，直接用标准库会静默产生时区偏差。已经有两个人踩过。

理由：复现两次、有具体损失——但它完全依赖这个代码库的历史包袱，写进 Skill 会污染所有别的项目。

❌ **不值得晋升**
> Gate 审批太慢了，应该允许小改动跳过 contract 批准。

理由：这不是经验，是在提议削弱红线。红线不在流程内协商（见 `../../sdlc-core/references/redlines.md`）。真正的问题如果是"仪式太重"，正确的落点是 lane 机制，不是取消审批。

## 2. 目标类型怎么选

### 影响半径对照表

七类，对应主规格 §16 Classify 的判断维度。四类版本曾经把 `policy` / `eval` / `tool` 挤到没有落座点——
`upstream-mapping.md` 产出的「`config.yaml` 的 protected 路径要补一条」这类结论就属于其中之一，它既不是文档也不是模板。

| 目标类型 | 落点 | 影响谁 | 生效时机 | 错了以后 |
|---|---|---|---|---|
| `project-doc` | 目标项目的 `docs/`、`CLAUDE.md`、`.sdlc/` 内的项目文档 | 只有本项目 | 下次有人读到 | 本项目内修正，影响可控 |
| `template` | `sdlc-core/templates/*` | 之后所有同类产物 | 下次实例化模板 | 每份新产物都带上错误字段；已生成的不受影响 |
| `checklist` | `sdlc-core/references/` 或各 Skill references 里的自检清单条目 | 用这份清单的所有工作 | 下次跑到这个检查点 | 多一条噪音，或漏放一类问题 |
| `policy` | `.sdlc/config.yaml` 的 `protected_paths` / `data_policy` / `test_policy` / `tool_actions`、`roles` 与各 Gate 的 `require`，或 `sdlc-core/references/redlines.md` | 之后所有工作的**边界** | 立即，下一次范围检查就生效 | 两个方向都很贵：放宽了会静默放行本该被拦的动作，收紧了会把正常工作全部堵死 |
| `eval` | `evals/scenarios.md` 的用例与通过判据 | 之后所有 Skill 变更的**验证基准** | 下次跑 eval | 基准错了，之后每一次"验证通过"都不可信 |
| `tool` | `sdlc-core/scripts/*`、`tools/*` | 之后所有调用该脚本的环节 | 立即 | 确定性检查出错比人出错更难发现——没人会怀疑脚本 |
| `skill` | 任一 `sdlc-*/SKILL.md` 或 `references/` | **之后所有工作，所有项目** | 立即，且整个会话常驻 | 静默影响每一次执行，最难回溯 |

三类容易混淆的边界：

- **`policy` vs `checklist`**：清单是"别忘了检查 X"，漏了只是漏了；策略是"X 不被允许"，违反会被拦下。能不能被机械拦住，是分界线。
- **`eval` vs `tool`**：eval 定义"什么算通过"，tool 执行"是不是通过了"。判据变了改 eval，执行方式变了改 tool。
- **`tool` vs `skill`**：判断是确定性的（编号、格式、统计、diff）就该进脚本，不要写成让模型每次记住的规则（写作规范 §8）。反过来，需要语义判断的不要硬塞进脚本。

### 分界线

**第一问：换个项目还成立吗？**

不成立 → `project-doc`。到此为止，不要再往上走。

这一问拦掉的候选最多，也最有价值。"我们这里 CI 环境有个坑"、"这个遗留模块要特殊处理"、"团队约定用 X 不用 Y"——全部是项目事实，不是工作方法。写进 Skill 会让之后所有项目背上一条不属于它们的规则。

**第二问：是"别忘了检查"，还是"工作方式要变"？**

只是提醒别漏掉某件事 → `checklist`。清单条目便宜、局部、容易删。

**第三问：是产物缺东西，还是过程缺东西？**

产物里少了一个字段、一段说明、一个必填项 → `template`。模板改动可见度高：下次有人填的时候就会看到，不对劲会被立刻发现。

**第三问半：改的是"怎么做得更好"，还是"什么被允许"？**

是后者 → `policy`。策略的判断标准很硬：**这条经验能不能被写成一个会拦下动作的边界？**能，就是 policy，落到 `config.yaml` 或 `redlines.md`，不要写成一段谁都可以绕过的建议。

再分一道：落在 `config.yaml` 的是**项目级**策略（只管本项目，本项目自己能改回去）；落在 `redlines.md` 的是**套件级**红线（管所有项目，且红线本身不在流程内协商）。拿不准就落 `config.yaml`。

**第三问四分之三：判据错了还是执行错了？**

"这类失败 eval 根本没测到"、"eval 判过了但实际是坏的" → `eval`，改 `evals/scenarios.md` 的用例或通过判据。

"每次都要靠人记住去数、去比、去校验" → `tool`，把它变成脚本。脚本要自己处理错误分支，报错信息要具体到能自修（写作规范 §8）。

**第四问：只有工作方式本身错了，才选 `skill`。**

选 `skill` 之前还要再过一道：**没有 Skill 的情况下，baseline 会犯这个错吗？**

- baseline 不会犯 → Skill 里没有东西要修。这个失败要么另有来源，要么根本不是失败。
- baseline 会犯，但现有 Skill 已经写了对应的规则 → 是规则没被读到、或写得不够醒目，改的是位置和措辞，不是加新规则。
- baseline 会犯，Skill 也确实没覆盖 → 这才是要修的洞。

### 拿不准的时候往低选

模板改错了，下次有人填的时候会看出来。SKILL.md 改错了，它会安静地影响每一次执行，直到某天有人发现输出变差了——而那时候已经没人记得是哪次改动造成的。

同一条经验也可以分两步走：先落到 `project-doc` 观察一段时间，确认在别的项目也成立之后，再开一条新 LP 提升到 `template` 或 `skill`。第二条 LP 引用第一条的观察记录作为证据——这正是 Observe again 该产生的东西。

### 什么时候是 `new_asset: true`

主规格 §08 写的是「晋升为**新资产**或现有资产的新版本」——两条路都合法。`new_asset: true` 走的是前一条：新增一份 reference、一个模板、一条清单、一个脚本、一组 eval 场景。

判断顺序**先找现有落点，找不到才新建**：

1. 现有资产里有没有一节讲的是同一件事？有就改那一节（`new_asset: false`），别开新文件。
2. 塞进去之后那份文件会不会超出它该承担的范围？（例如把一份 500 行的操作手册塞进一个 40 行的清单）会，才考虑新建。
3. 新建之后，**谁会读到它**？答不上来就不要建。

`new_asset: true` 时 §2 必须多写两件事，它们是预检的检查对象：

| 要写的 | 为什么 |
|---|---|
| **创建理由** | 说明"现有资产里为什么放不下"。写不出来通常意味着它其实该并进某一节 |
| **归属目录** | `sdlc-core/references/`（跨环节共享）、`sdlc-<环节>/references/`（单环节专用）、`sdlc-core/templates/`、`sdlc-core/scripts/` 或 `tools/`、`evals/`。选错目录的后果是它被引用不到，或被所有环节无差别加载 |

**新资产的验收标准比修改现有资产多一条：它必须在上级导航里有入口**（见 §4.6）。一份没有任何 SKILL.md 指向它的 reference，不是资产，是死文件——而且它会在下一次审计里被当成"疑似遗留"删掉。

跨环节共享还是单环节专用，用一个问题决定：**第二个环节会不会读它？**只有一个环节读，就放那个环节自己的 `references/`；放进 core 会让所有人都要判断一次"这个跟我有没有关系"。

## 3. Validate 怎么做

三件事：找历史案例、构造反例、划适用范围。

### 3.1 找历史案例

目的是回答"这件事发生过几次"。按成本从低到高：

| 方法 | 怎么做 | 找什么 |
|---|---|---|
| 翻已有 LP | 读 `.sdlc/lessons/` | 同一条经验是不是已经登记过、或被拒绝过 |
| 搜 Gate 记录 | grep `.sdlc/**/gates/*.yml` 的 `status_reason` 与 `top_issues` | 同一类原因导致的 FAIL / CONCERNS |
| 搜失败归因 | grep 各 WI 的 `qa-report.md` | 归因到同一来源的缺陷 |
| 搜越界记录 | grep evidence.jsonl 的 `boundary_stop` | 反复在同一处被拦下，通常说明范围模板漏了声明 |
| 读事故 | `.sdlc/incidents/*/incident.md` 的根因节 | 上游归位结论指向同一个资产 |
| git log | 搜相关文件的历史 commit message | 反复的同类修补 |

**找到零个** → 留在 `observe`，写清楚"等第二次出现"。不要用"我相信它会再发生"代替证据。

**找到一个** → 检查两次是不是同一个根因，还是表面相似。表面相似的两次不构成规律。

**找到两个以上** → 可以推进。把编号写进 lesson.md §3 的历史案例表。

### 3.2 构造反例

反例不是"这条经验的例外"，是**边界的另一侧**。找不到反例的规则，通常是措辞太宽，而不是它真的普适。

四种问法，任选有效的：

1. **把条件反过来**：这条经验成立是因为 A 成立。如果 A 不成立呢？
2. **换规模**：这条经验在一个 3 人项目上成立。50 人呢？1 人呢？
3. **换 lane**：`full` lane 上成立。`quick` lane 上，它会不会把一次热修变成半天的流程？
4. **换阶段**：它在 build 阶段成立。同样的动作放在 explore 阶段还对吗？

反例找到之后，它就是适用范围的边界，写进 §3。

✅ `反例：内部服务间调用不适用——内部依赖的可用性由同一个团队保证，要求写降级预案会让 quick lane 平白变重。`
❌ `反例：特殊情况下可能不适用。`

第二种写法等于没写。它把判断推给了下一个读到的人，而那个人没有你现在的上下文。

### 3.3 回放：如果当时就有这条规则

挑 3 个历史案例——**其中至少一个是当时做得对的**——问：如果那时候这条规则已经存在，会发生什么？

| 回放结果 | 含义 | 处置 |
|---|---|---|
| 会拦下当时的错误 | 有效 | 记进 §3 的历史案例表 |
| 无影响 | 场景不覆盖 | 正常，说明适用范围确实有边界 |
| **会拦下当时正确的做法** | **误伤** | 回去改措辞或缩小范围，不要带着误伤推进 |
| 会让流程明显变重但不解决问题 | 净成本 | 拒绝 |

误伤是最重要的信号。一条拦住了 1 次错误、同时给 20 次正确操作添堵的规则，是负收益——而且它带来的摩擦会让人开始整体忽略这一类规则。

### 3.4 适用范围问题清单

写 §3 之前逐条回答，写不出来的那条就是还没想清楚的地方：

- [ ] 什么条件下这条经验成立？（写条件，不写"需要的时候"）
- [ ] 什么条件下不成立？（至少一条具体反例）
- [ ] `quick` lane 上也要求吗？还是只在 `full`？
- [ ] 它作用在哪个阶段？跨阶段吗？
- [ ] 谁来执行它——人、Skill、还是脚本？
- [ ] 怎么知道它被违反了？（看不出违反的规则等于没有）
- [ ] 它和现有哪条规则重叠？重叠的部分留谁？

最后一条容易被跳过。两条说同一件事的规则会互相稀释——读的人会以为它们有细微差别，然后花时间去找那个不存在的差别。

### 3.5 Validation 六项与回归集

主规格 §08 要求 Validation 至少覆盖六项。模板 `lesson.md` §3 有对应的表，逐项给结论，**不适用的写"不适用 + 理由"，不要留空**——留空和"查了没问题"在事后读起来一模一样。

| 检查 | 具体做什么 | 常见做错的地方 |
|---|---|---|
| 结构校验 | 校**改动后的资产**：改 Skill / reference / 模板跑 `python3 tools/check_suite.py`；改 YAML 跑 `python3 -c "import yaml,sys;yaml.safe_load(open(sys.argv[1]))" <文件>`；改脚本跑一次它自己的样例 | 校成了这份 LP 自己的格式。那是 Approve 预检的事，不是 Validation |
| 依赖解析 | `grep -rn "<被改文件名>" .claude/skills/` 列出引用点，逐个确认措辞还对得上 | 只看被改的那份文件。删掉一节而别处还写着"详见 X 节"，是最典型的破链 |
| 权限检查 | 两问：**谁有资格批准**（`gates.lesson-approval.require` 要的角色 + `roles` 里谁担它），**改动后谁被允许使用**（`adoption_scope`） | 只答了第一问。git 权限管的是谁能改文件，管不了这条资产对哪些工作生效——两个正交问题 |
| 样例 / 反例 | 一个正例（本来会失败、改后应该通过）+ 一个反例（本来正常、改后不能被误伤） | 只看正例。只验证"修好了"，没验证"没修坏别的" |
| 场景运行 | 2–3 个历史 WI 回放，问"如果当时就有这条规则会怎样" | 挑的三个都是当时做错的。至少要有一个是当时做对的，那个才验得出误伤 |
| 回归结果 | 见下 | 只跑改动后的一次。那不是回归，是自证 |

**回归集**：在 Validate 阶段**先固定下来**的一组用例，改动前跑一遍记录结果，改动后用**同一组**再跑一遍，两次结果并列写进 §3。

固定的意思是：用例清单在看到改动效果**之前**就写死。改完之后再挑用例，等于在挑那些一定会通过的。

| 目标类型 | 回归集取自 | 规模 | 比什么 |
|---|---|---|---|
| `skill` / `checklist` | `evals/scenarios.md` 的相关场景 + 2 个难负例（与本 Skill 共享关键词但应该走别的环节的请求） | 3–5 | 改前 vs 改后的 transcript 与通过判据。读 transcript，不要只看产物 |
| `template` | 2–3 份历史 WI 的**真实**产物内容 | 2–3 | 用改后的模板重填，新字段填不填得出来。填不出来就是字段设计有问题 |
| `policy` | 历史上被这条策略挡住 / 放过的具体事件（grep evidence.jsonl 的 `boundary_stop`） | 全部相关事件 | 同样的事件在新策略下结论是否翻转。翻转的每一条都要能解释 |
| `eval` | 该 eval 判过的历史用例 | 全部 | 判定结果有没有**意外**翻转。改判据的目的之外的翻转都是意外 |
| `tool` | 该脚本已有的输入样例 | 全部 | 退出码与报错文本逐条比对。退出码约定：0 通过 / 1 检查未通过 / 2 脚本自身出错 |
| `project-doc` | 不适用 | — | 写"不适用：只读文档，无可执行用例" |

回归集是**这条 LP 的资产**，写进 §3 就固定下来。同一个位置的下一条 LP 应当沿用它并按需扩充——这样才能看出"这块地方的判据在逐轮变强"，而不是每次重新发明一套。

## 4. 怎么安全地修改目标资产

### 4.1 五种门槛

**改模板（`sdlc-core/templates/*`）——门槛正常。**

模板改动局部、可见、可逆。下次有人实例化模板时就会看到新字段，不合适会被立刻反馈。

注意：新增必填字段会让所有之后的产物都要填它。字段的价值必须大过每次填它的成本。填不出内容的必填字段会逼出敷衍内容，那比没有这个字段更糟。写字段注释时说明"为什么必须有"——那是后面 Gate 校验的依据。

**改 `policy` / `eval` / `tool`——门槛较高，且错法特殊。**

这三类改的不是"怎么做得更好"，是"什么被允许、什么算通过、什么被自动检查"。它们的失败模式是**静默**的：

| 改的是 | 改松了会怎样 | 改紧了会怎样 |
|---|---|---|
| `policy`（`config.yaml`、`redlines.md`） | 本该被拦的动作从此不再被拦，而且不会有任何报错 | 正常工作被全面堵死，人开始绕过整套机制 |
| `eval`（`evals/scenarios.md`） | 之后每一次"验证通过"都不可信 | 正确的改动被判失败，没人再信 eval |
| `tool`（`scripts/`、`tools/`） | 脚本说通过就没人复查——确定性检查出错比人出错更难发现 | 报错信息含糊会让人直接跳过这一步 |

所以这三类的回归集要求最硬：**把历史上被它挡住和被它放过的事件全部重跑一遍**，结论翻转的每一条都要能解释（见 §3.5）。改 `config.yaml` 之前还要确认它属于项目级还是套件级——落错层的策略要么管不到该管的项目，要么管到了不该管的项目。

**改 references——门槛较高。**

references 被多个 Skill 按需引用。改之前先确认谁在引用它：

```bash
grep -rn "references/<文件名>" .claude/skills/
```

改的是被引用的段落时，检查引用处的措辞是否还对得上。删段落尤其危险——某个 SKILL.md 可能写着"详见 X 节"，而 X 节已经不在了。

**改 SKILL.md 正文——门槛最高。**

SKILL.md 在整个会话常驻，每一行都在花所有人的上下文预算。新增内容前先问：

- 这条能不能放进 references，在 SKILL.md 只留一行导航？
- 现有的哪一段可以因此删掉？（净增行数是要付代价的）
- 它是"知法犯法"型失败吗？如果失败是输出形状不对（格式、结构、篇幅），给正面配方和示例，不要给禁令——禁令对这类问题无效，实测下禁令组产出的不良内容反而更多。

改 `description` 是一类特殊情况：它决定 Skill 会不会被触发，改错了整个 Skill 就静默失效。只写触发条件，绝不写工作流摘要（`../../sdlc-core/references/authoring-conventions.md` §1）。改完之后跑一遍触发测试，包括与相邻环节共享关键词的难负例。

### 4.2 一次一改

**一条 lesson 对应一个改动点，一次 commit。**

三个理由：

1. **批准的边界**——批准人批的是这一处。捎带的第二处没被任何人批准过。
2. **可归因**——Observe again 要判断效果。一次改三处，你分不清是哪一处起了作用，或哪一处造成了误伤。
3. **可回滚**——`git revert` 一个只做一件事的 commit 是干净的；revert 一个混合 commit 会把还有用的部分一起撤掉。

真的有多个改动点时，拆成多条 LP 各自走完六阶段。如果这让你觉得太麻烦，那通常说明这些改动点其实是同一条经验的不同表述——那就合并成一条，重新想清楚它到底在说什么。

### 4.3 改动后怎么验证没有误伤

按目标类型，成本递增：

| 目标 | 验证方式 |
|---|---|
| `project-doc` | 读一遍，确认没和现有内容冲突 |
| `checklist` | 拿 2-3 个历史 WI 走一遍新清单，看会不会卡住本来正常的工作 |
| `template` | 用改后的模板填一份**历史 WI 的真实内容**，看新字段填不填得出来。填不出来就是字段设计有问题 |
| `policy` | YAML 能解析；拿历史上被挡住和被放过的事件各跑一遍，确认结论翻转的都是想要翻转的那些 |
| `eval` | 用该 eval 判过的历史用例重跑，意外翻转要能逐条解释 |
| `tool` | 跑一遍已有输入样例，退出码与报错文本逐条比对；错误分支要自己处理，不要把异常抛给调用方 |
| `references` | grep 引用点，确认措辞对得上、被引用的小节还在 |
| `skill` | 跑对照 eval：改前 vs 改后，同一组用例（含正例和难负例）。读 transcript 而不是只看产物 |

改 SKILL.md 至少要有一个正例（本来会失败、现在应该通过）和一个负例（本来正常、改后不能被误伤）。两个方向都不看，就不知道自己是修好了还是修坏了。

### 4.4 落盘与记录

```
chore(learn): LP-007 契约模板增加外部依赖降级预案字段
```

commit message 带 LP 编号，让之后任何人从 `git blame` 就能查到这条规则的来源、证据和批准人。**一条查不到来源的规则，早晚会被当成历史遗留删掉，或者被当成不可动的教条供起来——两种都不对。**

填 lesson.md §5：改了哪些文件、commit hash、生效时间。§6 留观察锚点：下次什么时候、看什么现象能判断它有没有起作用。

### 4.5 填 §5 的采用范围

`adoption_scope` 不是装饰。默认值 `all` 的含义是"从此刻起，所有项目、所有会话无差别生效"——对 `skill` 类改动来说，这是套件里爆炸半径最大的一个动作。

| adoption_scope | 写法 | 还要做的事 |
|---|---|---|
| `all` | 全套件生效 | 呈报时明确说出"之后所有工作"，让批准人知道自己在批什么 |
| 本项目 | 只对当前项目生效 | 改动落在项目级（`.sdlc/`、项目 `docs/`），不要改套件文件 |
| 指定环节 | 例如"只在 `full` lane 的 contract 阶段" | **在被改资产的正文里就近注明适用条件**，否则读到的人无从判断它管不管自己 |

最后一行是最容易漏的。一条范围受限的规则如果只在 LP 里写了范围、在资产正文里写成无条件命令，那它实际生效范围就是 `all`——没人会为了读一条规则先去翻它的 LP。

### 4.6 新建资产（`new_asset: true`）

建文件只是第一步，**没有入口的新资产等于没发布**。三件事一起做完才算：

1. **建文件**，放进 §2 声明的归属目录，格式随目标类型对齐（reference 顶部放目录、模板顶部放编辑权限注释、脚本遵守退出码约定）。
2. **在上级导航里加入口**——这一步决定它会不会被读到：

| 新建的是 | 入口加在哪 |
|---|---|
| 某环节专用 reference | 该 `SKILL.md` 的「开工前」：常读的写 `**REQUIRED**`，偶尔读的写进"需要展开时才读"那一行 |
| 跨环节共享 reference | `sdlc-core` 的导航 + 每个真正会用到它的环节各加一行。**不要只加 core**，没有环节指向它就没人会打开 |
| 模板 | 引用它的环节写明"什么时候实例化、复制到哪里" |
| 脚本 | 调用它的环节给出完整命令行（`"$CORE/scripts/xxx.py"` 形式），并说明退出码含义 |
| eval 场景 | `evals/scenarios.md` 的场景列表 |

3. **跑结构校验**：`python3 tools/check_suite.py`。它会检查引用的文件是否真的存在——加了入口但路径写错，这一步就会报出来。

引用只允许一层深（`SKILL.md → references/x.md`）。新建的 reference 不要再去引用另一份 reference，那会让读者在两层跳转之后忘记自己在找什么。

### 4.7 Amend——出修订版，不推翻结论

判据只有一条：**结论变了就是新 LP，只是说得更准确就是 Amend。**

| 情况 | 走哪条 |
|---|---|
| 收窄或放宽适用范围 | Amend |
| 补一条反例、补一个例外条件 | Amend |
| 改措辞让规则更容易被读到、位置上移或下移 | Amend |
| 修字段名笔误、修脚本里的边界条件 | Amend |
| 换了 `target_kind` 或 `target_path` | 新 LP |
| 结论反过来了（"应该 X" → "不该 X"） | 新 LP |
| 影响半径变大（`project-doc` → `template` / `skill`） | 新 LP |

Amend 的走法：

1. 在**原 LP** 的 §5 追加一行修订记录：改了什么、新 commit hash、日期
2. §1–§3 沿用原文，只补充这次修订依据的**新证据**（哪次工作说明原措辞不够准）
3. **照样要一次 Gate**——省的是重开六阶段，不是省批准。话术里写明"Amend LP-###"，`target_version` 填目标资产**当前**的 hash
4. commit message 仍带原 LP 编号：`chore(learn): LP-007 amend 收窄适用范围到外部同步调用`

不做这个区分的代价很具体：每次微调都要走一遍完整六阶段，成本和新增一条经验相同，于是没有人愿意维护已发布的经验——它们就停在第一版，然后慢慢和现实脱节。

### 4.8 Deprecate——结论不再成立

回滚和废弃是同一件事的两种触发（效果有害 / 前提消失），动作一样，三件缺一不可：

1. **撤掉改动**：`git revert <commit>`；删掉会破坏上下文的段落，改为**原地标注失效**（保留文字 + 注明"已废弃，见 LP-###"）
2. **在原 LP §6 记录**：什么时候发现的、什么现象、为什么撤
3. **`status` 改为 `deprecated`**

**Deprecate 同样要一次 Gate。** 废弃一条已经在生效的规则，和加一条一样会改变之后所有工作的行为——尤其是 `policy` 类，撤掉一条边界意味着从此刻起某类动作不再被拦。

**不要删 LP 文件。** 被推翻的经验和被采纳的经验一样是资产，它记录了"这条路走不通"，能省下下一个人重走一遍的时间。`rejected`（从未发布过）和 `deprecated`（发布过后来被撤）是两种状态，不要混用。

废弃本身是一次 Observe：如果同一类改动被撤了两次，那说明该被质疑的是这一类改动的判断方式，而不只是这一次的措辞。
