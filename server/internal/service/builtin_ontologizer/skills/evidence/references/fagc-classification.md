# 四分：Fact / Assumption / Guidance / Constraint

分类不是给陈述贴标签，是决定它以后能不能被当作依据用。分错的代价在生成阶段
才显现，而且那时候已经看不出来了——candidate 里的对象只写着 "support: evidence"。

## 定义与硬性要求

| 类 | 是什么 | 硬性要求（`no_inference_as_fact` 逐条核） |
|---|---|---|
| `fact` | 材料里明确写着的事 | `source_ids` 非空 + 至少一个带 `location` 与 `exact_snippet` 的锚点 |
| `assumption` | 材料没说、我们自己填的空 | `rationale`：凭什么这么填，以及不这么填会怎样 |
| `guidance` | 建模口径、命名约定、内部惯例 | `authority_or_owner`：这条口径谁说了算 |
| `constraint` | 业务上必须成立的硬约束 | `authority_or_owner`：这条约束由谁负责 |

四个值之外的分类会被判失败，没有 `unknown`、没有 `other`。分不出来说明还没想清楚，
想清楚之前不要登记。

## 决策程序

对每一条陈述，按顺序问：

**1 · 我能指出它写在哪一句话里吗？**

- 能 → 继续问 2。
- 不能 → 它是 `assumption`。写 `rationale`。**到此为止，不要再往回找理由把它变成 fact。**

**2 · 它说的是「事情就是这样」还是「事情应该这样」？**

- 是这样（描述现状、描述数据、描述已发生的流程）→ `fact`。
- 应该这样（规定、禁止、要求）→ 继续问 3。

**3 · 这条「应该」是业务对世界的要求，还是我们对建模的约定？**

- 业务对世界的要求（违反了业务上就是错的）→ `constraint`。
- 我们对建模/命名/口径的约定（违反了只是我们内部不一致）→ `guidance`。

第 3 步最容易含糊。判据：**这条规定被违反时，是业务出事，还是我们的模型出事。**

## 用日记账冲销的材料走一遍

**「冲销分录的借贷方向与原分录相反，金额相同」**
→ 手册 §6.2/4 原文写着，描述系统实际行为 → `fact`，锚点 `§6.2/4`。

**「一条分录只能被冲销一次」**
→ 手册 §6.2/2 原文写着。但它说的是"不许"，不是"是"。违反了业务上就是错账 →
`constraint`，`authority_or_owner: 总账操作手册 §6.2/2`。

注意它同时有锚点。有锚点不等于是 `fact`——`fact` 与 `constraint` 的区别在
描述还是规定，不在有没有出处。约束有出处是好事，没出处才要额外小心。

**「50,000 阈值按本位币不含税计」**
→ 政策 §3.3 白纸黑字写着"未对『金额』是否含税、是原币还是本位币作出说明"。
材料明确表示自己没说 → 这条只能是 `assumption`。

`rationale` 要写全：政策明说未定义；样本里 `JE-2026-0110` 恰好是 50,000 且
`tax_included=Y`（正好卡在阈值上，含税与否直接改变审批人）；`JE-2026-0105` 是 USD
（币种口径也没定）；共享中心现行按本位币不含税执行但无文件支持。

这是最典型的陷阱：共享中心天天这么做，所有人都当它是事实。但"大家都这么做"
不是出处。降级成 assumption 并挂一条有主的未决事项（`ud.002`），
才能让它在半年后还看得出来是个未决的口径。

**「『红冲』是习惯说法，系统里没有这个动作，建模时统一到『冲销』」**
→ 术语表里"系统里没有这个动作"是 `fact`（有锚点、描述现状）。
但"建模时统一到冲销"是我们的约定，违反了只是模型内部不一致 → `guidance`，
`authority_or_owner` 写术语表。

一句话里有两类内容时，**拆成两条**。不拆的话，`guidance` 那半句就借了
`fact` 那半句的锚点，看起来像有出处。

**「制单、审批、复核三项职责不得由同一人承担」**
→ 政策 §3.4 原文，业务硬要求，违反了是内控问题 → `constraint`，
`authority_or_owner: 集团财务政策部`。

**「审批被否决之后退回制单人」**
→ 流程图上这条线是断的（`ev.gap.001`），材料里没有。访谈里 PO1 说了。
访谈答案不是文档，但它是一个可归因的人的陈述：登记为 `fact`，
`source_ids` 指访谈轮次，`location` 写 `访谈 q.202`，`exact_snippet` 记他的原话。

访谈可以产生 `fact`，前提是锚点指向那次访谈的具体一问一答，不是"据领域专家说"。

## 常见误判

| 看起来像 | 其实是 | 为什么 |
|---|---|---|
| "系统一般三天内处理完" | `assumption` | "一般"是没有出处的概括，材料里没有这个数 |
| "分录必须有原因代码" | `constraint` | 是规定不是描述，即使手册用陈述句写它 |
| "我们把 JE 统一叫日记账分录" | `guidance` | 是我们的命名约定，不是业务要求 |
| "样本里有 6 条记录" | `fact` | 描述数据现状，锚点指向 CSV |
| "软关账期间可以冲销" | `fact` 且 `disputed` | 有出处，但另一份材料说反话，见 `conflict-handling.md` |

## 状态字段

`status` 与 `classification` 是两件事：

- `classification` 是它属于哪一类，**不随裁决改变**。
- `status`（`proposed` / `confirmed` / `disputed` / `resolved` / `deprecated`）
  是它现在处于什么处境。

一条 `assumption` 被裁决之后不会"变成 fact"。它的 `status` 变成 `resolved`，
`resolution_rationale` 写明裁决内容和裁决人。原样留着，因为半年后有人要问的是
"当初这个口径是谁定的、凭什么"，而不是"现在的口径是什么"——后者在 candidate 里就有。
