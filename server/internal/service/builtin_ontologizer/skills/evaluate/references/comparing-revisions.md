# 跨 revision 比较

`compare` 步骤。把两次 evaluation run 逐题对齐，找出**能力回归**——
上一版能答的这一版答不了了。

流程 §11.1 把"识别 revision 之间的能力回归"写进了这个阶段的目标。
它是修订循环唯一的外部反馈：`unaffected_unchanged` 保证没人乱改，
跨 revision 比较保证改对了的地方没有顺手弄坏别的。

## 对齐的依据是 cq_id，不是题面

题面可以改（改得更清楚是好事），`cq_id` 不能改。改了 `cq_id` 就等于换了一道题，
历史比较从那一刻断掉。要换题就新开一个 id，旧的留在登记里标明为什么不再用。

## 四类变化

| 变化 | 从 → 到 | 意味着 |
|---|---|---|
| **退步** | passed → failed / unsupported | 上一轮修订弄坏了什么，或者删掉了还有人依赖的东西 |
| 进步 | failed / unsupported → passed | 修订生效了 |
| 新增 | 上一次没有这道题 | 没有可比基线，单独列 |
| 消失 | 这一次没跑 | **要解释为什么**，不能默默不提 |

## 退步要排在最前面

呈现顺序固定：**退步 → 新增 → 消失 → 进步 → 未变**。

退步排第一不是为了戏剧性，是因为它是唯一需要立刻决定的一类：
其余四类都可以留到 `interpret` 慢慢看。

例：

> **ev-0003（r0003）对比 ev-0002（r0002）**
>
> **退步 1 题：** cq.003"冲销分录对应的原始分录是哪一条" passed → failed。
> r0003 里 `rel.reverses` 的目标端基数从 1 改成了 many，
> 答案形状从"一条分录编号"变成了一组。这条改动来自 chg.001。
>
> 进步 1 题：cq.002 unsupported → passed（`evt.reversal_approved` 补上了审批人参与者）。
> 消失 0 题，新增 0 题，未变 4 题。
>
> 退步这条要不要回滚？还是改题目的 expected_answer_shape？

最后那一问是 `interpret` 的入口：**退步不一定是错的**。
基数确实该改成 1:many 的话，该改的是题目，不是模型。这个判断属于人。

## 消失的题要解释

一道题这次没跑，可能是三种原因，三种后果完全不同：

- 它从登记里被删了 → 谁删的、为什么；
- 它被 `bind` 步骤过滤掉了（`origin: ai_proposed` 未批准）→ 去批或去掉；
- 这次运行只跑了子集 → 说明是子集运行，不要拿它和全量运行比。

**默默不提是最坏的一种。** 一道悄悄消失的题，在下一次比较里会变成
"没有退步"，因为它两次都不在。

## 结果绑定 revision

`cq_result_bound` 查每次运行的 `revision` 字段指向一个真实存在的 revision。
比较的时候两边都要报出来：说"退步了 1 题"而不说是哪两个 revision 比出来的，
这个数字没有出处（`shared/conventions.md` 第 7 条第 5 款）。

还有一个容易忽略的坑：**被比较的 revision 可能已经 superseded**。
拿一个已经被后继版本取代的 revision 的评估结果当现状报，
是在报一个过期的结论。`state.py status` 会把这件事列进"问题"。

## 比较不改任何东西

`compare` 只读两次运行的结果文件，产出一段呈现。它不写 `cq-register.yaml`，
不改任何一次历史运行，也不新建运行。要重新跑就跑一次新的 `ev-NNNN`——
运行记录和 revision 一样，写完就不改。
