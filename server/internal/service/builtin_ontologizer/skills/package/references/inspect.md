# 陪人看哪三样

渲染是确定性的，所以「渲染对不对」不需要人看——`skill_package_current` 管这个。
需要人看的是三处只有人能判断的东西。

## 1 · description：别人的 Agent 会不会在该用的时候用它

它是这个包唯一的触发机制。渲染器从领域名、实体别名和胜任问题拼出来一版，
但**只有人知道用户实际会怎么说**。

念给人听，然后问一个具体的问题：

> 你们的人问这类问题时，一般会用哪些词？现在这版描述里写的是
> 「日记账分录、JE、分录、凭证」——还差什么说法吗？

漏了的说法，去 `ontology/glossary.md` 看看有没有；没有就说明那是一条
`evidence` 阶段漏掉的别名，回去补，不要在包里补。

**不要在这里改 description 的文字**。要改就改渲染器
（`tools/package/render.py` 的 `description()`），那对以后所有项目生效。

## 2 · boundaries：未决的那几条，人认不认

逐条念，不要只报数字。每条问一句「这条你接受它就这么发出去吗」。

三种典型反应，对应三种动作：

| 人说 | 意思 | 动作 |
|---|---|---|
| 「这条其实早就定了」 | FAGC 登记没跟上 | 回 `evidence` 改状态，重新生成，重新打包 |
| 「这条确实没定」 | 正常 | 留着，确认 owner 是谁 |
| 「这条不该让外面看到」 | 边界与保密的冲突 | 停下来，这是治理问题，交给本体负责人 |

第三种要认真对待：**未决项本身可能是敏感信息**（"我们的政策和操作手册打架"）。
包是要发出去的，这一条得有人拍板，而不是渲染器默认带出去。

## 3 · glossary：说法对得上吗

术语表是消费方查的第一份文件。翻一遍，特别看两类：

- **只有机器名没有中文说法的对象**——用户不会用 `JournalEntry` 提问；
- **同一个说法指向两个对象**——这是歧义，消费方解析时会挑一个，挑错了后面全错。

两类都要回 `evidence` 或 `interview` 补，不在包里改。

## 看完之后

告诉人三件事：包在哪、来自哪一版、有几处未决且分别是什么。
然后给安装命令（见 `references/installing.md`），不要替他执行。
