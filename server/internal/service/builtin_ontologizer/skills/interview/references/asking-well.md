# 怎么问

访谈的失败模式不是问得少，是问得多、问得散、问了已经知道的。
一个把人当资料库反复查询的访谈，问到第三轮就没人认真答了——
而真正需要他判断的那两三个问题，正好在后面。

## 分轮，一轮最多五题

一轮的意义是：**后一轮的问题取决于前一轮的答案。** 一次甩二十道题出去，
拿回来的是二十条互不相干的回答，其中一半可以由另一半推出来。

轮次的组织方式：一轮聚焦两到三项 readiness，问题之间有逻辑关联。

```
第 1 轮  goal · boundary · users_and_decisions        —— 先定方向
第 2 轮  core_objects · key_processes · exceptions     —— 再定形状
第 3 轮  terminology · granularity                     —— 最后收边界情况
```

每轮开头交代**为什么问这一轮**（`asked_because`）。
「章程有边界但没写清楚谁在什么时候做什么决定」比「请回答以下问题」有效得多——
人知道你在补哪个洞，就会顺手把相关的事一起说了。

## 能出选择题就不出开放题

开放题拿回来的是散文，要人自己组织结构；选择题拿回来的是决定。

**选项必须带后果。** 没有后果的选择题是伪选择题——人只能凭语感挑一个。

```yaml
question: 冲销申请单要不要建成对象？
kind: choice
options:
  - value: 建成实体
    consequence: 三条记录（申请、审批、冲销分录）能挂到同一个单号上，可追溯到人
  - value: 只当成分录的属性
    consequence: 模型更小，但审批记录无处可挂，cq.005「追溯责任」答不了
```

后果要落到**具体哪个问题会答不出来**，不要写"影响模型完整性"。
前者他能判断，后者他只能相信你。

## 三种问法

| kind | 用在 | 形状 |
|---|---|---|
| `choice` | 有明确候选的设计决定 | 候选 + 每项后果 |
| `confirm_inference` | 系统能猜出一版的事 | 把猜的内容**原样**摆出来问对不对 |
| `confirm_recorded` | 登记里已经有答案的事 | 指出记在哪，问还作不作数 |
| `open` | 只有人知道、猜不出来的事 | 一句话，不带引导 |

`confirm_inference` 是效率最高的一种。系统读完材料能列出核心对象的候选名单，
把名单摆出来问"对吗"，比问"这个域里有哪些核心对象"好得多——

前者人只要挑错，后者人要从零组织。而且前者会暴露系统的误判：
猜出来的「审批人」被人一眼看出是角色不是对象，这个纠正在开放题里根本不会发生。

摆的时候要**原样**摆，包括你自己觉得可疑的那几项。挑着摆等于替他筛过一遍。

## 不要重问已经记录过的

开工第一件事是把 `define/project-charter.yaml`、`define/fagc-register.yaml`、
`define/evidence-snapshots/**` 读一遍，逐项判断八项 readiness 里哪几项
**登记里已经能答**。

能答的用 `confirm_recorded` 指过去：

```yaml
question: 粒度还按章程写的「单条分录，line 不展开」吗？
kind: confirm_recorded
recorded_answer_ref: define/project-charter.yaml#scope.data_granularity
answer: 是，本轮不改。
outcome: skipped
rationale: 章程已定，无新信息，不重复登记
```

这既是礼貌，也是准确性：人被重复问同一件事时，第二次的回答未必和第一次一样，
而两个版本都会被记下来。

## 分组，不要逐条审讯

有二十个候选对象要确认时，不要问二十次。按类型或按层分组，
给整组一个建议，让人只改例外：

> 从材料里读出六个核心对象：分录、冲销分录、冲销申请单、会计期间、原因代码、员工。
> 另有三个我判断是角色而不是对象：制单人、审批人、复核。
> 这样分对吗？哪几个要挪位置？

一次回答解决九项。逐条问会得到九个"对"，其中至少一个是敷衍的。

## 人答"不知道"是一个答案

「总部的财务控制和工厂的财务经理，冲销审批权限等同吗」——
人说"不确定，要查授权表，先按等同处理"。

这一项的 `status` 是 `answered`，`answer` 记他的原话，
同时在 FAGC 里开一条 assumption（`asm.002`）。

**不要因为答案不确定就把这一项标 `skipped`。** 他回答了，
回答的内容是"这件事没定"——这是一条真实的、有价值的领域知识，
而 `skipped` 会把它抹成"没问"。

## 访谈补上证据缺口时

人的回答填上了材料里的洞（比如流程图上断掉的那条线），
要在 FAGC 里新增一条 `fact`：`source_ids` 指访谈轮次、
`location` 写 `访谈 q.202`、`exact_snippet` 记他的原话。

访谈可以产生 `fact`，前提是锚点指向那次具体的一问一答，
不是"据领域专家说"。落笔在 `evidence` 那边的文件，本 Skill 只提出该补哪一条。
