# Marketplace recommending source map

- Scoring is a pure function in `server/internal/recommend/recommend.go`. `Rank(profile, candidates, limit)` returns each candidate with a `Score`, its `Reasons`, and `Matched` — true only when at least one reason came from the workspace's own profile. No model is involved anywhere in this path, by design: a ranking that depended on a provider would put its latency in front of the Marketplace page and would be unexplainable when wrong.
- Weights are constants in the same file. A tag match (10) outranks category (6), name (5), description (3) and body text (1), because a tag is a publisher's deliberate claim and a mention in a paragraph is not. Only the best-scoring field for a term counts, so a listing repeating its own title in its description does not score twice.
- `typical_work` reaches listing text through `TypicalWorkVocabulary` in `server/internal/workspaceprofile/profile.go`: the gloss is split into words and matched, capped at `maxWorkScore` so gloss vocabulary cannot outweigh a real stack match.
- Latin terms match on word boundaries (`containsTerm`), so `go` does not match `google` and `ts` does not match `tests`. Terms with no Latin characters — Chinese, Japanese, Korean — match as plain substrings, because those scripts do not delimit words and a boundary check would never fire.
- Popularity is compressed logarithmically and capped at `maxPopularScore`. It is the one signal that would otherwise make the ranking self-reinforcing, recommending whatever is already installed everywhere regardless of fit.
- `stackAliases` is small and hand-maintained (`go`/`golang`, `postgres`/`postgresql`, and so on). A general stemmer would match `gopher` for `go`; a missing alias costs one reason, a wrong one costs an indefensible recommendation.
- `server/internal/handler/marketplace_recommend.go` is the endpoint. `GET /api/marketplace/recommendations` reads the workspace's profile and `ListVisibleMarketplaceListings`, narrows to what is eligible, ranks, and renders each result with the same listing shape browse returns so a client reuses its card and its install dialog.
- Eligibility drops four kinds of listing, each for its own reason: not `published` (nothing to offer), already installed (the update prompt is browse's job), dismissed at the current version, and — through the status filter — deprecated, since recommending one to a workspace that does not already depend on it is pointing at a dead end.
- `ExtraText` on a candidate is left empty by the handler. For a skill listing the publish path already copies SKILL.md's description into the listing description, which is the richest matching text available; for an agent template the remaining text is its instructions, and reading one manifest per listing would turn a two-query endpoint into a hundred-query one to weight a field at one point.
- Dismissals live in `marketplace_recommendation_decision` (migrations `449` and `450`), unique on `(workspace_id, listing_id)`. The row stores the `version_id` the member judged, and the recommender suppresses a listing only while that version is still the latest — so publishing a new version puts it back. `POST`/`DELETE /api/marketplace/recommendations/{id}/dismiss` write and clear it; both gate on the same visibility rule browse uses, so a workspace cannot probe for another's private listings by dismissing ids.
- `prerequisites` is on the manifest envelope (`marketplaceManifest` in `server/internal/handler/marketplace_manifest.go`), not inside a kind-specific member, so an installer reads one field regardless of kind. `normalizeMarketplacePrerequisites` bounds it. Nothing validates the content — the condition is on the installing host — so it is prose shown before an install. The client carries it on `MarketplaceManifestSchema` (`packages/core/api/schemas.ts`) and renders it twice: as a "Before you install" section on `marketplace-listing-page.tsx`, and restated above the confirm button in `install-dialog.tsx` — a condition read after the install has already cost the reader the install.
- CLI: `enact marketplace recommend` in `server/cmd/enact/cmd_marketplace.go`. Its table prints a WHY column built from the reasons, because a ranking without its evidence is not something a reader can disagree with. `--limit` is bounded server-side by `maxRecommendationLimit`.
- The setup checklist's capability step reads `ListMarketplaceInstallsForWorkspace` or `CountMarketplaceRecommendationDecisions` — either is a member having decided, and the step asks for a decision rather than for an install. See `server/internal/handler/workspace_setup.go`.
