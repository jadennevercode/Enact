# Resources source map

- `server/cmd/enact/cmd_resource.go` registers `resource list/add/update/remove`.
- `resource add` supports shortcuts for `github_repo` (`--url`, non-JSON `--ref` for the checkout ref, `--default-branch-hint`) and `local_directory` (`--local-path`, `--daemon-id`, `--ref-label`, `--execution-mode`), or a generic JSON `--ref '<json>'`. The shortcut merging lives in `buildResourceRefFromFlags` / `buildResourceRefFromRefFlag` in the same file.
- `resource update` merges shortcut edits with the existing `resource_ref` so a partial edit does not clobber required fields; a non-JSON `--ref` updates `github_repo.resource_ref.ref`. It re-reads the row through `fetchWorkspaceResources` first because the server replaces `resource_ref` wholesale.
- `resource update` / `remove` accept a short id prefix, resolved by `resolveWorkspaceResourceID` in `server/cmd/enact/cmd_id_resolver.go`.
- `local_directory.execution_mode` is validated in `server/internal/handler/workspace_resource.go` (`validateLocalDirectoryRef`); the daemon reads it in `server/internal/daemon/local_directory.go` (`localDirectoryAssignment.UsesWorktree`) and builds the per-task worktree in `server/internal/daemon/execenv/local_worktree.go`.
- Saving `execution_mode=worktree` is gated on the daemon having advertised the `local-worktree-v1` capability (`protocol.DaemonCapabilityLocalWorktreeV1`), checked by `requireWorktreeCapableDaemon` in `server/internal/handler/workspace_resource.go` against the daemon's most recently seen runtime row; not capable → HTTP 422 `daemon_version_unsupported`. The authoritative gate is at claim time (`worktreeClaimBlockReason` in `server/internal/handler/daemon.go`), which reads the capability off the claim request itself and cancels the task with a reason. `MinLocalWorktreeCLIVersion` (`server/pkg/agent/version.go`) is only the number shown to the user; nothing gates on it.
- One `local_directory` per (workspace, daemon) is enforced by `findLocalDirectoryConflict` in `server/internal/handler/workspace_resource.go` (HTTP 409). The daemon re-checks in `findLocalDirectoryAssignment` (`server/internal/daemon/local_directory.go`) and fails the task rather than guessing when two match.
- `server/cmd/server/router.go` exposes `GET/POST /api/resources` and `PUT/DELETE /api/resources/{resourceId}`.
- `server/pkg/db/queries/workspace_resource.sql` is the CRUD query surface for `workspace_resource` rows (migration `432_workspace_resource`).
- Resources reach a running task through the claim response: `applyWorkspaceResourcesToClaim` (`server/internal/handler/workspace_resource.go`) fills `AgentTaskResponse.WorkspaceResources` (`server/internal/handler/agent.go`). That field deliberately keeps the wire name `project_resources` so already-installed daemons keep receiving it.
- The daemon mirrors it as `Task.WorkspaceResources` (`server/internal/daemon/types.go`), converts it with `convertWorkspaceResourcesForEnv` (`server/internal/daemon/daemon.go`) into `TaskContextForEnv.WorkspaceResources` (`server/internal/daemon/execenv/execenv.go`), renders the brief's `## Workspace Resources` section from it (`writeWorkspaceResources` / `formatWorkspaceResource`, `server/internal/daemon/execenv/runtime_config_sections.go` and `runtime_config.go`), and writes `.enact/project/resources.json` from it (`writeWorkspaceResourcesFile`, `server/internal/daemon/execenv/context.go`). The on-disk path keeps its `project` segment on purpose — installed agents and skills already read it there.
- `github_repo.resource_ref.ref` is lifted into `RepoData.Ref` by `applyWorkspaceResourcesToClaim`; `server/internal/daemon/daemon.go` stores it per task (`taskRepoDefaultRef`), and `server/internal/daemon/health.go` uses it as the default `/repo/checkout` ref when the checkout request does not pass one.

## Knowledge bases (`knowledge_repo`)

- `knowledge_repo` is validated by `validateKnowledgeRepoRef` in `server/internal/handler/workspace_resource.go`: `url` through the shared `isValidGitRepoURL`, `path` through `normalizeKnowledgePath` (relative only, no `.`/`..`/absolute/drive-letter, stored without surrounding slashes), `delivery` limited to `pull_request` / `commit`. `knowledgeDelivery` applies the `pull_request` default on read, so the default is never written to the row.
- Bindings live in `agent_resource` (migration `444_agent_resource`, index `445_agent_resource_resource_index`), queried through `server/pkg/db/queries/agent_resource.sql`. No foreign keys, per the repo rule: `DeleteWorkspaceResource` clears bindings in the same transaction as the resource, and `DeleteWorkspace` (`server/pkg/db/queries/workspace.sql`) sweeps them through `ws_agents`.
- `server/internal/handler/agent_knowledge.go` serves `GET/POST /api/agents/{id}/knowledge` and `DELETE /api/agents/{id}/knowledge/{resourceId}`, registered in `server/cmd/server/router.go`. `loadKnowledgeResourceForAgent` refuses a resource from another workspace (404) and a non-`knowledge_repo` resource (400).
- Claim-side routing is the design's core: `applyWorkspaceResourcesToClaim` SKIPS `knowledge_repo` rows so they never reach the workspace-wide list, and `applyAgentKnowledgeToClaim` (same file) adds only the claiming agent's bindings, called once in `buildClaimedTaskResponse` (`server/internal/handler/daemon.go`) rather than beside each of the four per-kind resource calls. It fills `AgentTaskResponse.KnowledgeSources` and also appends each base to `resp.Repos` with `Kind: RepoKindKnowledge` — the repo list is what `repoAllowlist` (`server/internal/daemon/daemon.go`) turns into the `enact repo checkout` allowlist, which is how an agent writes a document back.
- `RepoData.Kind` (`server/internal/handler/agent.go`, mirrored in `server/internal/daemon/types.go`) is empty for code repos on purpose, so older daemons and older servers keep their meaning. `convertReposForEnv` drops knowledge entries so they do not also appear under the brief's `## Repositories`.
- The daemon checks each base out and indexes it in `server/internal/daemon/knowledge.go` (`prepareKnowledgeSources`). The checkout lives under `<workspaces-root>/.knowledge/<workspace-id>/`, NOT in the task workdir: an `in_place` `local_directory` task runs inside the user's own directory and must not gain Enact-owned files. It is shared and refreshed per task, keyed per resource by `knowledgeCheckoutKey`. Any failure is contained as `KnowledgeContextForEnv.Unavailable` and reported in the brief rather than failing the task.
- Indexing is `ScanKnowledgeDocs` in `server/internal/daemon/execenv/knowledge.go`: markdown only, `.`-prefixed directories (including `.git`) skipped, title/description from front-matter with a `# heading` then filename fallback, sorted by path so an unchanged base renders a byte-identical brief. `ApplyKnowledgeIndexLimit` swaps the document list for a directory summary past `maxIndexedKnowledgeDocs` (60), which is what bounds the section's context cost.
- The brief section is `writeKnowledge` (`server/internal/daemon/execenv/runtime_config_sections.go`). It renders the INDEX only — title, description, relative path — plus the location, the document count, and the write-back instruction derived from `delivery`. Document bodies are never injected; the agent opens what it needs with its own file tools.
- `server/cmd/enact/cmd_resource.go` gained `--path` / `--delivery` and treats a non-JSON `--ref` as a checkout ref for `knowledge_repo` as well as `github_repo` (`refFlagIsCheckoutRef`). `server/cmd/enact/cmd_agent_knowledge.go` adds `enact agent knowledge list/add/remove`.

## Ontology-backed operational connections and applications

- `server/internal/handler/semantic.go` registers the `/api/semantic` control plane; `semantic_ontology.go`, `semantic_run.go` and `semantic_action.go` implement publication, query evidence, approvals and receipts.
- `server/internal/semantic/adapter.go` executes configured REST/PostgreSQL/MCP operations with the source caller's scoped credentials.
- `server/internal/handler/semantic_application.go` stores immutable source/build versions and human publication history; `semantic_application_invoke.go` restricts each app to its pinned release, capability manifest and current user's runs.
- `packages/views/resources/components/resources-page.tsx` links Connections; `packages/views/semantic` contains the shared web/desktop workbench and application host. `packages/core/semantic` owns wire validation and query state.
