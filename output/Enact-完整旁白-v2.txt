企业交付的竞争力，来自对业务的理解，以及将专业经验转化为可靠结果的能力。但这些经验往往分散在个人判断、项目文档和工作习惯中，每个新项目都需要重新组织。

Enact 通过两个核心能力，将专业经验转化为人与 AI 可以共同使用、持续复用的交付能力。

首先，将专业知识转化为 Skill，并以 Agent Family 的方式组织交付。

一个 Skill，可以包含完成某类工作所需的方法步骤、参考知识、产物模板和检查脚本。它让专家经验成为智能体执行时能够遵循的具体要求。

进入智能体团队，可以看到面向不同场景的 Agent Family。每个成员拥有明确职责，配置相应的 Skill，由协调者组织分工，将复杂项目拆解为相互衔接的工作。

团队可以围绕任务补充背景、确认关键判断和审阅产物。经过验证的方法能够在后续项目中继续使用，再结合客户和项目特点调整，让专家将更多时间投入关键决策。

其次，搭载主流 Runtime，专注构建企业语境。

Codex、Claude Code 等主流运行时，已经具备理解代码、调用工具和执行任务的能力。Enact 直接利用这些能力，让企业把投入集中在自己的专业知识、业务规则、系统背景和交付标准上。

在运行时页面，可以统一管理本地、远程和云端执行环境。桌面端自动发现本机已安装的 AI 工具，也可以添加服务器和远程开发机，为不同智能体配置合适的运行位置。

专业角色与执行环境分别配置，让同一套交付方法能够结合不同运行时使用。随着底层工具持续进步，企业积累的知识、Skill 和 Agent Family 也能继续发挥价值。

下面，通过三个场景，看这种交付方式如何改变专业工作。

首先是 AI SDLC。

AI 加快了代码生成，但软件研发的难点贯穿整个生命周期：需求存在遗漏，项目和跨系统背景不完整，兼容性与执行权限缺少验证，发布和运行也缺乏充分证据。更快的编码，可能被后续评审与返工抵消。

AI SDLC 用一套 Agent Family 贯穿需求、设计、开发、测试、发布和运行。

需求阶段，AI 通过交互式澄清，识别遗漏、假设和边界条件。

技术设计阶段，形成 Contract，明确业务目标、系统约束、兼容要求、执行权限和验收标准，作为后续 AI 工作必须遵循的顶层指引。

测试阶段，验证角色在独立上下文中依据 Contract 开展测试。一方面检查功能、集成和兼容性；另一方面检查 AI 是否遵守约定与权限，执行证据是否真实、完整、可追溯。

发布阶段，汇集测试结果、变更范围、风险、审批与回退准备，形成完整的 Evidence Package，由负责人决定是否发布。

进入运行阶段，AI 将告警、日志和实际表现关联到原始需求与发布记录，协助诊断和提出处置建议，再将根因反馈到 Contract、测试与 Skill，经过审阅持续改进。

软件交付因此从代码生成，扩展为以共同约定和证据贯穿全生命周期的协作。

第二个场景，是 MMM。

MMM 交付横跨业务、数据和算法。项目知识集中在少数专家身上，扩张往往依赖增加人员。大量时间消耗在资料整理、数据检查、反复分析和报告制作上，真正用于算法与高阶洞察的时间反而有限。

MMM Agent Family 将这些能力贯穿起来：从业务访谈、模型设计，到数据收集、质量评估、可视化分析，再到算法建模和最终汇报。

在项目任务中，不同角色承接各阶段工作，产物与判断持续共享，让专家集中处理关键假设、模型选择和业务解读。

以此次 MMM 案例的数据质量评估与可视化分析为例，百万级数据原本需要两到三周的处理分析工作，现在可以压缩到数小时内。

这种变化，让交付能力逐步建立在可复用的方法和工具上，把更多专业时间释放给洞察与决策。

第三个场景，是 Ontologizer。

企业建设本体，常常面临三个困难：起步时不知道从哪里开始；建模复杂，难以判断是否正确；验收依赖看图，却无法确认 Agent 是否真正理解并有效使用。

Ontologizer Agent Family 像 FDE 一样，从业务任务出发，与用户交互式、引导式地建模，先明确要解决的问题、范围和验收标准。

随后开展证据驱动的本体共创：整理业务资料和系统证据，生成语义候选，标注来源、冲突与假设，再由用户逐步确认。

在 Ontology Studio 中，这些内容被组织为业务对象、关系、行动和规则，并经过构建、测试、审阅与版本治理。

最终，将本体放进真实业务任务，检查 Agent 获取的上下文、调用轨迹和任务结果，评审它能否正确支持查询、判断与行动。

本体的验收，由模型是否看起来合理，推进到它是否真正帮助业务任务完成。

从软件研发，到营销分析，再到业务本体建设，Enact 将专业经验转化为可复用的能力，让交付过程产生证据，让实践反馈持续改善下一次工作。
