# 工作区横切与隔离

> **文档说明**：本文给出一条判定规则，决定一项功能应该跨工作区共享还是留在工作区内，并记录已经按这条规则落地的部分。业务视角见[业务架构](business-architecture.zh.md)，组件视角见[应用架构](application-architecture.zh.md)。

---

## 1. 问题

Enact 只有两层作用域：**用户**和**工作区**。没有组织层，也不打算为了这件事引入一层。

在这两层之间，有一类东西被放错了位置：它描述的是一台电脑或一个人的资产，却被存成了每个工作区一份。一个人把同一台电脑接入三个工作区，服务端就有三套记录，各自保存这台电脑的名字、CLI 版本和在线状态。改名要改三次，而且没有任何机制保证三份改完之后是一致的。

这不是权限问题，是**归属建模错误**。

---

## 2. 判定规则

一项功能归哪一层，问四个问题：

| 问题 | 横切 | 隔离 |
| --- | --- | --- |
| 真实资源归谁所有？ | 机器、CLI 登录凭据、个人身份 | 任务、状态、评论这些团队事实 |
| 删除工作区时它应该消失吗？ | 不应该——删工作区不该删掉你的电脑 | 应该 |
| 它是**资产**还是**授权**？ | 资产 | 授权 |
| 成本按什么维度问？ | "这台机器跑了多少" | "这个项目花了多少" |

第三个问题是核心，可以浓缩成一句话：

> **资产横切，授权隔离。**

一台机器可以跨工作区，但"这个工作区的成员能不能用它"必须每个工作区单独决定。一份运行时配置可以跨工作区，但"这个工作区要不要启用它"是这个工作区自己的事。

这条规则也会否掉一些看起来该横切的东西。设计过程中我们一度打算把 `daemon_token` 提升为机器级——它明明是"这台机器的凭据"。但它是授权，不是机器事实：成员离职流程按 `(workspace_id, daemon_id)` 删除令牌，一旦提升为机器级，把某人移出一个工作区就会切断他的守护进程对其他所有工作区的访问。**规则抓住了我们自己的设计错误**，所以令牌保持工作区级。

---

## 3. 分类结论

### 3.1 横切（用户级 / 机器级）

| 对象 | 归属 | 说明 |
| --- | --- | --- |
| **机器** | 用户 | 电脑本身：名称、设备信息、CLI 版本、在线状态、心跳。`daemon_id` 本来就是机器级稳定 UUID，存在 `~/.enact/daemon.id`，所有 CLI profile 共用 |
| **运行时配置（runtime profile）** | 创建者 | 描述的是**这个人电脑上**的一个命令，由他自己的守护进程在自己的 `PATH` 里解析。跟着人走：配置过一次，之后进入任何工作区、担任任何角色都在。可另行发布给整个工作区 |
| 模型目录、本地 skill 清单缓存 | 机器 | 同一台机器缓存一次即可 |
| Composio 连接、个人访问令牌、语言/时区偏好 | 用户 | 已经是用户级，保持 |

### 3.2 隔离（工作区级）

| 对象 | 说明 |
| --- | --- |
| 任务、状态、标签、属性、视图、活动日志、收件箱、订阅 | 团队事实 |
| 成员、角色、邀请、席位订阅与计费 | 工作区治理 |
| **智能体定义与 Access** | 智能体是"工作区内的身份"，可见范围就是权限模型本身 |
| Squad、自动化、配额 | 工作区级编排 |
| **运行时可见性（private/public）** | 机器横切了，但"在工作区 A 公开"绝不等于"在工作区 B 公开" |
| **守护进程令牌** | 授权，不是机器事实。见上文 |
| 渠道安装、VCS 连接、插件安装、工作区 MCP | 携带团队授权与 webhook 密钥，横切风险大 |
| Skill、Ontology | 工作区沉淀；跨工作区复用走 Marketplace 导入，不是把表改成全局 |

### 3.3 暂不处理

- **IM 个人身份绑定**（`lark_user_binding`、`channel_user_binding` 等）：同一个人在每个工作区都要重新绑定，属于同类问题，但独立于本次改动，单独处理。
- **机器级并发上限**：目前并发在智能体上，守护进程侧是一个启动参数。多工作区叠加可能超过机器承受能力，是已有隐患，机器实体为修复它提供了落点。

## 4. 已落地

### 4.1 机器实体

`machine` 表按 `daemon_id` 唯一，`agent_runtime` 增加 `machine_id`，成为"这台机器在某个工作区的投影"。

一次真实回填的结果：6 条运行时记录、2 个工作区、3 个 provider，收敛为 1 台机器，并保留了用户此前设置的自定义名称。

被替换掉的旧机制：`UpdateAgentRuntimeCustomNameByDaemon` 和 `ListDaemonCustomNames` 曾用来把一次改名扇出到同一 `daemon_id` 的所有行，前端 `sharedCustomName` 则反过来猜测"所有行同名才算机器名"。这些都是在逼近机器这个概念。

新接口刻意不放在 `/api/workspaces` 下——把机器路由到工作区，正是当初造成重复的原因：

```
GET    /api/machines
GET    /api/machines/{machineId}
PATCH  /api/machines/{machineId}
```

**披露规则**：机器可以告诉它的所有者自己服务了**多少个**工作区，但只能列出读者本人是成员的那些。否则运行时页会变成枚举同事所属工作区的手段。

### 4.2 运行时配置跟随用户

先说清楚一个容易混淆的点：**运行时本来就是每个人用自己的电脑**。工作区级的配置从来没有共享过机器，它共享的是一份*定义*，每个成员的守护进程在自己电脑上各自解析这个命令。可见性默认 `private`，别人绑不上你的机器。

真正缺的是：**配置本身不跟着人走**。以前它是工作区级的，进一个新工作区要重填一遍。

`runtime_profile` 增加 `owner_id`，新增 `runtime_profile_workspace` 发布关系表。`runtime_profile.workspace_id` 保留但含义收窄为**来源工作区**，不再是访问检查。

一份配置在某个工作区可用有两条路径，第二条才是"跟着人走"：

1. **发布**到这个工作区——这个工作区的**每个成员**的守护进程都会尝试注册，是团队标准化场景；
2. **属于这台守护进程的操作者**——不论他在哪个工作区、担任什么角色。

守护进程侧的操作者身份正是靠机器表解析出来的：守护进程令牌只证明工作区访问权，不含身份，但 `daemon_id` 能查到 `machine.owner_id`。解析不出来时收窄为"只看已发布的"，绝不放宽。

```
GET    /api/runtime-profiles                                  我拥有的全部配置
POST   /api/workspaces/{id}/runtime-profiles/publish          发布进这个工作区
PATCH  /api/workspaces/{id}/runtime-profiles/{pid}/enabled    这个工作区的开关
DELETE /api/workspaces/{id}/runtime-profiles/{pid}            从这个工作区撤下
```

**修改权限随传播范围变化**：只被一个工作区使用时，该工作区的 admin 可以修改，与共享功能上线前完全一致；一旦发布到第二个工作区，只有所有者可以修改。这样做的目的是让共享功能不成为一次伪装成功能的权限回退。

**两个启用开关**：所有者的全局开关退役整个定义，工作区的开关只让本团队退出。守护进程两者都开才注册。

**删除即撤回**：从一个工作区删除只撤回这个工作区。**管理员不能删除他人的配置定义**——配置跟着所有者进入他所有的工作区，删掉它会伸手到这个管理员毫不相干的工作区，毁掉同事自己的工具配置。撤回已经满足了管理员一切正当诉求：本工作区不再看到它，守护进程也不再注册。只有所有者本人、且没有任何工作区还在发布它时，定义才被删除。

### 4.3 工作区删除

因为配置和机器现在可以比工作区活得久，删除工作区改为**撤回而非删除**，只回收确实没人再引用的记录，并且只考虑与被删工作区相关的记录。一个与被删工作区无关的配置或机器永远不会被碰到——否则删除一个工作区就可能删掉另一个工作区刚创建的东西。

---

## 5. 前端影响

前端本来就有机器概念，只是 id 是客户端合成的（`local:<daemon_id>`），并靠解析显示名里的主机名来兜底。现在 `machine_id` 成为权威分组键，旧推断保留为兜底：云运行时没有宿主机，旧服务端注册的记录在守护进程重新注册前也没有 `machine_id`。

这修掉了旧推断的两个方向的错误：同一台机器被拆成两台（`daemon_id` 变更），以及两个人同名的笔记本被合并成一台（设备名撞名）。
