# AI SDLC：从局部任务加速，走向受治理的人机协同交付

> 来源：用户提供的《AI-SDLC Introduction@20260902(1).pdf》，共17页。  
> 本文按完整故事组织材料，围绕整体痛点、全生命周期各环节的痛点与变化，以及工作协作和交付范式展开。工作模式与范式变化的概括属于对材料的分析性归纳；引用对应原PDF页码。

## 一、故事的起点：代码更快完成，业务变更却未必更快成立

企业希望让接待人员和顾问共享客户上下文。AI更新了接待工作台，代码生成完成，单元测试通过，持续集成检查也全部正常。但顾问与后续跟进工作台仍然使用旧的会话结构和授权字段，结果上下文不匹配，后续业务被阻断。

这是材料用来说明核心问题的例子：**每个组件看起来都已完成，完整的业务旅程仍然可能失败。**[^p3]

AI加快了局部任务的执行，却没有自动解决任务之间的连接问题。一次企业级软件变更，还需要跨越三个缺口：

**首先是理解缺口。** 当前任务看起来清楚，但项目背景、关联系统规则和业务依赖可能没有进入AI的上下文。

**其次是执行缺口。** AI能够完成修改，但修改是否兼容其他系统、Agent是否有权执行这些操作，仍然需要验证。

**最后是接受缺口。** 代码和测试已经产生，但企业仍然需要足够的发布与运营证据，才能判断这次变更是否可以投入使用。材料将可接受变更的要求归纳为预期行为、系统兼容性、受控执行和发布准备度。[^p2]

因此，企业面对的整体痛点可以概括为：

> **AI提高了产出速度，企业还需要把需求理解、系统协同、执行边界、质量验证和上线责任连接起来，才能把局部效率转化为完整的交付价值。**

这就是AI SDLC的切入点。它沿用企业现有的需求、设计、开发、质量保证、发布和运营生命周期，在每个环节强化交付成果、权限边界和证据，并通过生产反馈形成闭环。[^p4]

## 二、沿着一次业务变更，AI SDLC如何改变全生命周期

### 1. 需求澄清：先解决没有被问清楚的问题，再生成需求文档

一个业务请求进入交付流程时，最初表达的通常是希望实现的效果。材料中的共享客户上下文，就隐藏着一系列需要确认的决定：如何识别访客、不同角色共享什么信息、记录不确定时如何处理、哪些材料可以推荐、后续工作如何交接，以及试点如何监控。[^p5]

**这一环节的痛点，是需求已经能够被写出来，关键业务决策却可能尚未形成。**

这些问题没有确定时，后续开发就容易建立在未确认的假设上。即使生成的文档条理清楚，也不能证明其中隐含的业务含义已经得到认可。

AI SDLC在这里引入的变化，是让AI先帮助暴露缺失的问题，再由产品、架构、业务、安全、隐私和运营等责任方确认业务含义、记录决策，最后形成需求文档。材料明确强调，责任人作出业务决定应当发生在PRD生成之前。[^p5]

因此，需求工作的重点扩展为：**把意图变成明确的决策，并为决策找到承担责任的人。**

这一环节交给下游的，包含需求文档，也包含已确认的规则和责任归属。接下来的问题是：这些决定如何在开发、测试和发布中保持一致？

### 2. 设计与架构：把业务决定转成各环节共同使用的执行依据

即使业务已经作出决定，后续团队仍可能产生不同理解。开发关注如何实现，测试关注如何判断，发布关注什么条件下能够上线。如果这些环节各自解释需求，就可能重新出现偏差。

**这一环节的痛点，是业务意图已经明确，但还没有形成开发与验证共同遵循的规则。**

AI SDLC提出跨系统可执行规范，将行为、调用方契约、示例、反向场景、可观测性，以及发布与回滚要求组织在一起。同一份规范进一步支撑编码任务、测试判定依据、评审规则和发布门禁。这里的调用方契约，是关联系统对接口和行为的依赖约定。[^p6]

它带来的关键变化是：

**同一个业务决定，在实现、测试、评审和发布中，都有共同的参照。**

由此，设计成果的作用从说明方案，进一步延伸为支撑后续执行与验收的共同依据。材料将其定位为共享执行逻辑，但没有展示从规范自动生成各类执行资产的具体技术实现。

有了共同规范，下一步还需要确保Agent了解当前系统，并且只在允许的范围内行动。

### 3. 开发实施：先准备上下文，再授权Agent执行

开发阶段存在两个相互关联的问题：**Agent是否了解足够的系统背景，以及它能够采取哪些行动。**

只了解当前需求和局部代码，可能遗漏调用方、事件机制或工程标准；拥有工具访问能力，也不意味着可以任意修改相关系统。材料通过上下文包和受限工作空间，分别处理这两类问题。[^p7][^p8]

首先，为当前变更准备受治理的上下文。Agent可以使用已批准的行为、相关代码、调用方契约、事件契约、工程标准，以及测试和可观测性模式；无关仓库和数据被排除。这些上下文需要能够检索、具有版本，并且可以追溯。[^p7]

随后，在明确的工作空间内开放执行权限。材料中的编码示例限定了可以使用的工具、文件和测试执行器，调用方仓库保持只读，生产环境与凭据禁止访问。同时记录提示词和上下文、执行动作、代码差异、测试及异常。[^p8]

**这一环节的变化，是把一次代码生成任务组织成有输入依据、有授权边界、有过程记录的工程执行。**

Agent获得一定自主性，企业仍然能够回答：它依据了什么、被允许做什么、实际做了什么，以及留下了哪些问题。

开发交出的成果因此同时包含**实现结果和可审查的执行证据**。接下来，需要有人独立判断，这些结果是否真正满足要求。

### 4. 代码评审与质量保证：从组件检查，延伸到跨系统行为和完整业务旅程

开头的失败案例已经说明，单元测试和持续集成正常，只能证明部分条件成立。关联系统能否继续调用、完整业务流程能否走通，还需要进一步验证。

**这一环节的痛点，是局部检查通过，容易被误认为整个变更已经正确。**

AI SDLC保留单元测试、静态检查和组件安全等工程验证，同时设置独立QA，覆盖调用方契约测试、业务旅程测试、安全检查和可观测性检查。这些结果共同进入质量门禁，可以通过、阻断或转入人工复核。[^p9]

这里最重要的责任变化是：**Coding Agent负责实施，独立QA负责发布质量证据。** 材料明确区分这两项职责。[^p9]

这样，验证的对象就从代码本身，延伸到了代码与其他系统、业务流程和运行要求之间的关系。

这一环节交给发布方的，应当是一组能够支撑质量判断的独立证据，而不仅是开发任务已经结束的状态。

### 5. 发布：把分散的结果连接起来，让风险接受有明确依据和责任

即使已有代码评审和测试报告，发布者仍需要理解：为什么进行这次修改？哪些要求已经验证？是否还有未关闭风险？上线后如何监控，出现问题如何回滚？

**这一环节的痛点，是单独的结果记录未必足以支撑一次完整的生产风险判断。**

AI SDLC将证据沿着同一次变更连接起来：

**业务决策 → 可执行规范 → 受控实现 → 独立质量保证 → 生产准备。**

生产准备包含监控、回滚和未关闭风险。AI负责汇集和追踪证据，具有发布权限的人据此决定发布、暂缓或拒绝，并承担接受生产风险的责任。[^p10]

这里，人的工作重心体现为：**依据可追溯证据判断剩余风险是否可以接受。**

证据链还提供了反馈路径。出现失败时，需要返回原始决策或相关交付成果，识别问题究竟来自业务规则、规范、实现还是其他环节。材料明确设置了这一反向反馈。[^p10]

这意味着，交付过程虽然有前后衔接，也允许根据证据回到问题的源头修正。

### 6. 运营：通过实际业务结果，验证交付是否真正成立

发布批准、部署完成之后，业务是否成功仍然需要观察。接口是否持续兼容、通知是否送达、客户旅程是否走通，都发生在实际运行环境中。

**这一环节的痛点，是部署成功与业务成功之间仍有距离。**

AI SDLC将运营监控延伸到完整业务旅程，观察契约错误、通知送达、客户旅程成功等信号，同时准备回滚或安全降级。遥测、事件和经确认的学习结果，再反馈到DevOps。材料明确提出，完成标准从部署延伸到被观察到的客户结果。[^p11]

至此，一次变更形成完整闭环：

**从业务意图出发，通过实施与验证进入生产，再由真实运行结果检验最初的意图是否实现。**

这里的持续学习指运营反馈进入后续交付改进；材料没有描述AI自动修改生产系统或自动训练模型的机制。

## 三、工作协作的变化：人、Agent和质量保证如何围绕同一次变更工作

把上述环节连起来，可以归纳出三项工作模式变化。这些是对材料中机制与责任安排的提炼。

### 1. 人的工作重心，增加了定义、编排、验证与风险判断

在人机协作链路中，人需要确认业务含义，明确执行所需的规范、上下文和边界，并在质量与发布环节保留清楚的责任。Agent在授权范围内实施，AI也参与缺失问题识别和证据整理。[^p5][^p8][^p10]

因此，可以将人的工作重心归纳为：

**定义好要实现什么，组织好执行条件，判断结果是否成立，并对关键决定负责。**

这能够支撑从执行工作向更多编排与判断工作转移的方向。材料也列出了AI编排者、AI工程师和独立AI质量保证等角色，并将其连接到职业路径、能力要求和质量绩效体系。[^p16]

不过，材料没有给出现有岗位到新职责的完整映射，也没有说明人员配比或多Agent调度方式。因此，能够确认的是工作重心和角色体系的变化方向。

### 2. 团队协作，从交接单独成果，走向共享规范与证据的持续关联

沿着这条链路，需求、开发、测试和发布之间传递的信息发生了变化。

需求环节交出的决定，需要进入规范；规范需要支撑编码、测试和发布要求；实际修改和验证结果，又需要与最初的决定关联。共享规范和可追溯证据因此成为各角色共同使用的协作依据。[^p6][^p10]

可以将这种变化理解为：

**团队围绕同一次变更共同维护它的业务含义、执行依据和验证状态。**

它希望减少的，是不同角色在交接过程中重新解释需求、丢失背景或难以追溯判断依据的问题。前一环节的产出，需要能够被后一环节直接理解、使用和验证。

### 3. 自主执行、独立验证与最终责任，被放在不同位置

这套协作方式有一条清楚的责任链：

| 工作职责 | 材料中的安排 |
| --- | --- |
| 确认业务含义 | 由承担责任的业务及专业角色作出决定。 |
| 实施变更 | Coding Agent在明确范围和权限内执行。 |
| 证明交付质量 | 独立QA负责发布质量证据。 |
| 接受生产风险 | 具有发布权限的人决定是否放行。 |

上述分工分别体现在需求决策、受限执行、独立QA和人工发布门禁中。[^p5][^p8][^p9][^p10]

**Agent可以自主完成获准任务，但实施、证明质量和接受风险仍然需要明确区分。**

这些分工也需要平台与组织机制支撑。材料提出交付赋能层，将规范、上下文编排、Agent执行、质量保证、证据台账、策略控制和运营反馈连接到现有工具链，同时配套角色与决策权设计、工程集成和能力移交。[^p13][^p14]

由此，AI使用逐步进入团队共同遵循的交付方式，而不只停留在个人如何使用工具的层面。

## 四、交付范式的变化：企业如何重新理解什么叫交付成功

如果把工作协作进一步提升到交付逻辑层面，这份材料可以归纳出以下变化。这里的对比针对材料所描述的局部AI辅助交付与目标模式，并不意味着成熟DevOps此前不存在这些工程原则。

### 1. 从局部产出，走向可接受的端到端变更

代码、文档和测试结果都属于交付过程中的成果。它们需要共同证明业务意图得到实现、系统仍然兼容、执行过程受控，并且具备上线和运营条件。

因此，交付管理的核心对象变成了**一次具有完整依据、可以被接受的业务变更**。这与材料从AI生成变更走向被接受并运营的变更的主线一致。[^p2]

### 2. 从后期发现问题，走向沿途暴露不确定性、形成证据

需求阶段暴露缺失决策，设计阶段明确跨系统规范，开发阶段控制上下文与权限，质量阶段独立验证，发布阶段汇总剩余风险。

这套机制希望让问题更早显现，减少后期集成返工和重新验证。材料给出了这一收益逻辑，但使用的是概念性风险曲线，没有提供量化实测成效。[^p12]

**质量由各阶段逐步形成，发布时再对完整证据作出综合判断。**

### 3. 从部署完成，走向被观察到的业务结果

完成定义延伸到实际客户旅程，意味着技术上线只是过程中的一个节点。企业还需要通过运行事实确认预期效果，并将问题反馈到后续交付。[^p11]

相应地，价值衡量也围绕达到可接受变更的交付时间展开，同时观察周期与等待时间、集成缺陷与返工、证据完整性与异常未关闭时长，以及客户旅程成功和恢复时间。[^p17]

**效率、质量、控制和运营结果，需要放在一起评价。**

### 4. 从单点AI工具应用，走向企业拥有的可复用交付能力

当规范、上下文、权限、验证和证据机制能够嵌入现有平台与流程，并由具备相应能力的团队持续运行时，企业获得的是一套可以继续使用和改进的交付能力。

材料明确将运营模式、工程集成和质量保证组合起来，通过共同设计、共同交付、能力移交和持续改进，形成企业自己拥有的可复用能力。[^p14]

这也解释了为什么整套方案最终同时涉及**流程、平台、角色、决策权和人才体系**：它们需要共同支撑AI参与软件交付的方式。

## 五、将整个故事收束起来

这套AI SDLC从一个现实矛盾出发：**AI已经能够加快局部工作，但企业仍然需要为端到端结果负责。**

于是，业务意图先经过责任人的澄清与确认，再进入开发和QA共同使用的规范；Agent获得相关上下文，在授权范围内实施并留下证据；独立QA验证跨系统质量，人依据完整证据决定是否发布；上线之后，实际客户结果继续检验交付，并推动下一轮改进。[^p5][^p6][^p7][^p8][^p9][^p10][^p11]

**生命周期保持连续，工作协作开始围绕人机分工重新组织，交付成功则由共享规范、独立验证、可追溯证据和实际业务结果共同定义。** 这就是材料所支撑的工作模式与交付范式变化的主线。
