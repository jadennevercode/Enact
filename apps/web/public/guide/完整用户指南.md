# Enact × AISDLC 用户上手指南

## 从理解方法，到完成第一个受治理的交付任务

本指南面向在 Enact 中使用 AISDLC 的业务负责人、产品、架构、开发、QA 和运维人员。

读完并完成本指南，你将能够：

- 理解 AISDLC 如何把 AI 的局部效率转化为完整交付。
- 在 Enact 中准备工作区、运行时、代码与智能体团队。
- 提交一个目标清楚、责任明确的任务，并参与关键评审。
- 根据实现、验证和发布证据判断任务是否真正完成。

全文分为两部分：**第一部分介绍方法论，第二部分带你完成产品上手与首个任务。**

> 适用说明：本文依据所提供的方法论附件及 2026 年 9 月 15 日核对的 Enact 本地代码、产品文档和内置 AISDLC 套件编写。界面入口按当前代码组织；组织部署的登录方式、可用集成与版本可能不同。文中的示例需求、人员与路径均为示例，使用前需替换为本项目的信息。

# 第一部分｜理解 AISDLC：把 AI 产出变成可接受的业务变更

## 从 AI 辅助写代码，走向人机协同交付

AI Coding / Vibe Coding 让人通过提示、生成和快速迭代，更快地实现想法。

AISDLC 将这种能力放进完整的交付生命周期：从业务意图出发，明确共同规范、执行边界和责任，通过独立验证与可追溯证据，判断一次变更能否被接受，并在运行中验证业务效果。

| 对比维度 | 聚焦 AI Coding / Vibe Coding | 采用 AISDLC 的交付模式 |
|---|---|---|
| 管理对象 | 围绕一次提示、一段代码或一个功能推进 | 围绕一次端到端业务变更组织交付 |
| 执行依据 | 主要依靠提示词、对话上下文和人的持续补充 | 将已确认的业务决定固化为共享规范，并提供相关、有版本的上下文 |
| 协作方式 | 人与 AI 反复生成、检查和修改，再由人串起各环节 | 需求、设计、开发、QA、发布与运营持续关联，明确阶段交接和责任 |
| 质量判断 | 重点检查生成结果，结合自测与人工 Review 判断是否符合预期 | 从共同规范出发开展独立验证，覆盖组件、系统契约和完整业务旅程 |
| 人的工作 | 频繁补充背景、检查输出、协调修改和返工 | 在持续审查的基础上，更有组织地定义目标、准备条件、验证证据和判断风险 |
| 完成标准 | 容易把“功能能跑、修改完成”作为局部完成点 | 区分执行结束、质量通过、发布批准与实际部署，继续验证业务结果 |

**AI Coding 加快产出的形成；AISDLC 组织产出如何成为可接受的交付。**

当生成能力变强，交付管理能力也需要同步提升。关注点从“AI 多快写完”，扩展到“团队如何更可靠地完成一次业务变更”。

这组对比描述的是关注重心的变化。AI Coding 也可以具备严谨的工程实践；AISDLC 将这些实践组织成贯穿生命周期、责任明确且可追溯的交付方式。

## 1. 为什么代码写得更快，交付却未必更快

设想一次客户服务系统的改造：接待人员与顾问需要共享客户上下文。

AI 很快完成了接待工作台的代码修改，单元测试通过，持续集成检查正常。但顾问工作台和后续跟进系统仍使用旧的会话结构与授权字段，客户信息无法正确交接，完整业务流程依然失败。

这个例子揭示了一个问题：**每个组件都可以看起来已经完成，完整的业务变更仍然可能不成立。**

AI 加速了编写代码、生成文档和执行检查，却没有自动消除三类缺口：

| 缺口 | 典型问题 | 交付需要补齐什么 |
|---|---|---|
| 理解缺口 | AI 知道当前要求，却不知道相关业务规则、历史决定和系统依赖 | 已确认的业务决定与有来源的项目上下文 |
| 执行缺口 | 修改在局部可用，却破坏调用方，或超出原定授权范围 | 跨系统规范、明确边界与受控执行 |
| 接受缺口 | 代码和测试已经产生，但没人能判断剩余风险是否可以接受 | 独立质量证据、发布准备与具名责任人 |

AISDLC，即 AI 参与的软件开发生命周期，围绕一次业务变更，把需求、设计、实施、验证、发布和运营连接起来。

它关注的核心问题是：

> **这次变更是否实现了预期行为、保持了系统兼容、在授权范围内执行，并具备可以接受的上线与运营条件？**

## 2. 沿着一次变更，AISDLC 如何工作

### 2.1 需求澄清：先形成业务决定

"让接待人员和顾问共享客户上下文"还不足以直接进入开发。

团队需要先回答：如何识别同一位客户？不同角色可以看哪些信息？身份不确定时如何处理？授权变化后共享信息如何更新？出现异常时由谁接手？

AI 帮助识别遗漏、整理事实与假设、提出需要确认的问题。业务与专业责任人确认规则，并留下决定依据。

**这一阶段的产出：明确的目标、范围、责任人，以及已经确认或仍待确认的业务决定。**

### 2.2 设计与架构：建立实现与验证共同遵循的规范

业务决定明确后，还需要转成开发、QA 和发布共同使用的依据。

规范应说明：系统在什么条件下做什么；关联接口与调用方有哪些约定；正常、异常和反向场景如何判断；需要什么监控；如何发布与回滚。

在 Enact 的 AISDLC 套件中，这些内容主要组织在 **Execution Contract（执行契约）** 中。它是一份交付规范，连接目标、设计、验收标准和边界。

**这一阶段的产出：获批的执行契约，让实现与验证使用同一套业务含义。**

### 2.3 开发实施：准备上下文，在获批边界内执行

智能体需要知道相关代码、工程约定、系统依赖和已批准的规范，也需要清楚哪些文件可读、哪些文件可改、哪些操作不能执行。

AISDLC 将这两件事分别管理：

- **上下文**说明本次任务依据什么，包括来源与版本。
- **执行边界**说明本次任务被允许做什么，包括文件范围、工具动作与环境限制。

实施过程中保留代码差异、自测结果、执行记录和异常。如果发现必须扩大范围，先提出理由，由责任人决定。

**这一阶段的产出：实现结果，以及足以被审查的执行证据。**

### 2.4 评审与 QA：独立判断要求是否成立

开发自测能发现一部分问题。完整交付还需要验证调用方是否兼容、异常路径是否正确，以及业务旅程是否走通。

AISDLC 将实施与独立 QA 分开：Builder 负责实现；QA 先依据获批契约确定测试预期，再验证实现，避免把"代码现在的行为"当成"业务应该有的行为"。

进入独立 QA 前，内置套件还设置实现评审：由人判断做法方向是否合理、是否值得进入下一轮验证。

**这一阶段的产出：可追溯到验收标准的独立质量证据，以及缺陷与未关闭风险。**

### 2.5 发布：根据完整证据接受风险

发布决定需要把分散的信息连成一条线：

**业务决定 → 获批契约 → 实现与执行边界 → 独立 QA → 发布准备。**

AISDLC 用 **Evidence Case（交付证据档案）** 汇总这条证据链，包括已经证明的要求、尚未关闭的风险、监控和回滚准备。

智能体负责整理证据、指出缺口、提出建议；具名责任人决定发布、暂缓或拒绝。

**这一阶段的产出：有明确对象、理由与责任人的发布决定。**

### 2.6 运营与学习：用实际结果验证交付

部署完成后，还要观察客户旅程是否成功、接口是否持续兼容、异常是否被及时发现与处理。

如果出现问题，团队应追溯到业务规则、契约、实现或验证环节，找到需要修正的位置。有效经验经验证与批准后，再固化为项目规范、清单或能力资产。

**这一阶段的产出：真实运行反馈、问题归因，以及可复用的改进。**

## 3. 人与智能体分别承担什么责任

使用 AISDLC 后，人需要更多地参与目标定义、执行条件准备、证据判断和风险决策。

| 责任 | 人的工作 | 智能体的工作 |
|---|---|---|
| 定义目标 | 确认业务含义、范围和优先级 | 发现遗漏，整理事实与待决问题 |
| 确定方案 | 确认技术方案、验收标准和执行边界 | 编写契约，分析影响与风险 |
| 实施变更 | 审查方向，决定是否扩大范围 | 在获批范围内实现并保留证据 |
| 证明质量 | 判断验证是否充分 | 独立设计验证预期、执行测试与归因 |
| 接受风险 | 决定发布、暂缓或拒绝 | 汇集交付证据，说明剩余风险 |
| 持续改进 | 决定哪些经验值得固化 | 整理运营反馈，提出改进建议 |

可以记住三条原则：

1. **没有具名人工批准记录，不通过需要人工授权的关口。**
2. **测试预期来自获批契约，不能反过来从实现推导。**
3. **不能超出获批的变更范围进行修改。**

这些原则需要项目规则、校验脚本、运行环境权限和团队实际评审共同支撑。仅在提示词里写下限制，不能证明系统已具备操作系统或生产环境层面的强制隔离。

## 4. 什么才算交付成功

AISDLC 带来的变化，可以从四个角度理解：

| 观察角度 | 需要关注的变化 |
|---|---|
| 工作对象 | 从单份代码、文档或测试结果，扩展到一项可接受的端到端业务变更 |
| 协作方式 | 各角色共享规范，并持续关联决定、实现与证据 |
| 质量形成 | 在各阶段暴露不确定性、形成证据，在发布前综合判断 |
| 完成定义 | 从执行与部署完成，延伸到实际业务结果得到验证 |

衡量效果时，既看交付周期，也看返工、集成缺陷、证据缺口、人工决策等待和上线后的业务结果。

这些工程原则与成熟的 DevOps 实践相承接。AISDLC 进一步明确了 AI 参与执行时的上下文、权限、验证与责任安排。

## 5. 这套方法如何落到 Enact

Enact 提供组织工作和执行协作的载体；AISDLC 套件提供阶段分工、交付规范、校验与评审规则。

| 你要解决的问题 | Enact / AISDLC 中对应的对象 |
|---|---|
| 谁一起工作、围绕什么项目协作 | 工作区：集中管理成员、任务、资源与共享上下文 |
| 工作在哪里执行 | 运行时：连接的电脑及其可调用的 AI 工具 |
| 智能体依据什么工作 | 代码资源、项目画像、工作区上下文，以及本次任务的契约 |
| 谁负责哪一段工作 | Agent Family：有队长和阶段分工的智能体团队 |
| 具体怎么做、怎样检查 | skill：可复用的方法、模板和脚本 |
| 当前请求如何被协作与追踪 | Enact 任务：需求、评论、负责人、执行记录与产物入口 |
| 这次变更的交付依据如何保留 | Work Item：仓库 `.sdlc/` 中的契约、证据与决策记录 |

一个 Enact 任务可以产生多次智能体执行。执行完成只说明这一轮运行结束；业务交付还需要检查对应的验收和证据。

# 第二部分｜首次使用 Enact：完成第一个 AISDLC 任务

## 6. 先判断你从哪里开始

### 第一次为团队搭建环境

按下面的顺序完成准备：

**注册 / 登录 → 创建工作区 → 连接运行时 → 接入代码与项目背景 → 安装 AISDLC Agent Family → 初始化交付规则 → 开始首个任务。**

### 加入已经使用 AISDLC 的团队

接受邀请并进入已有工作区，先确认自己能使用团队的智能体和运行时，再直接开始任务。仓库、Family 和项目规则已有时，无需每位成员重复配置。

### 开始前准备好这些信息

| 准备项 | 需要什么 |
|---|---|
| 账号 | 组织提供的 Enact 入口，以及符合该部署要求的账号 |
| 执行环境 | 一台可运行任务的电脑；已安装并登录至少一款受支持的 AI 编程工具 |
| 代码 | 本次试点仓库、目标分支，以及运行环境可用的访问权限 |
| 项目背景 | 项目用途、技术栈、工程规范、构建和测试方式 |
| 人员 | 任务负责人，以及业务、架构、开发、QA、运维职责的实际承担者 |
| 第一个目标 | 一个范围有限、可以明确验证结果的小变更 |

AI 工具的账号、模型服务与额度需自行准备。Enact 的账号和 AI 工具的账号是两回事。

## 7. 第一步：注册或登录账号

**目标：让 Enact 知道你是谁。**

1. 打开组织提供的 Enact Web 入口或 Enact Desktop。
2. 已有账号，直接登录；首次使用，选择"注册新账号"。
3. 按页面填写用户名、邮箱和密码，完成注册。
4. 如果组织提供其他登录入口，按该入口完成登录。

当前核对的注册实现要求使用 `@deloittecn.com.cn` 邮箱，密码至少 8 个字符。Google 登录是否出现取决于部署配置。不能把"任意邮箱均可注册"作为本版本的使用说明。

**完成标志：**登录成功，看到工作区选择、创建工作区或已有工作区页面。

## 8. 第二步：创建或加入工作区

**目标：确定这项工作属于哪个项目与协作范围。**

工作区集中管理项目成员、任务、代码、智能体与共享背景。建议围绕同一项目和同一组协作规则建立工作区；业务与权限边界明显不同的项目分别管理。

### 创建新工作区

1. 选择创建工作区。
2. 填写便于团队辨认的名称，例如"客户服务平台"。
3. 确认工作区 URL 标识和任务编号前缀。
4. 完成创建，邀请将参与交付与评审的同事。

创建者成为工作区 `owner`。工作区 URL 标识应认真确认，当前产品创建后不能修改。

### 加入已有工作区

使用团队邀请加入，并在工作区切换器中进入正确的工作区。如果当前部署关闭自行创建工作区，由管理员提供邀请。

**完成标志：**能进入目标工作区，查看任务与成员，并确认自己拥有后续所需的使用或配置权限。

> 工作区里的 `owner` / `admin` / `member` 是产品权限。AISDLC 中的业务、架构、QA 等是交付职责。两者需要分别配置；成为工作区 `owner` 不等于已经批准某次发布。

## 9. 第三步：连接运行时

**目标：为智能体准备真正能执行工作的环境。**

运行时包括执行所在的电脑，以及这台电脑上的 AI 编程工具。守护进程负责把它们连接到 Enact，并接收执行任务。

### 使用 Desktop

1. 在目标电脑安装并登录所选 AI 编程工具。
2. 先直接运行该工具，确认能正常完成请求。
3. 打开并登录 Enact Desktop，进入目标工作区。
4. 打开"运行时"，确认本机及所选工具被识别并上线。

Desktop 会自动启动本地守护进程。新安装工具后，按界面刷新或重启 Desktop 重新检测。

### 使用 Web，或连接另一台电脑

1. 打开"运行时"，选择"添加电脑"。
2. 在准备执行工作的电脑上，运行弹窗给出的安装和连接命令。
3. 按提示完成 CLI 登录授权，并等待守护进程上线。

请使用当前部署弹窗里的命令，确保电脑连接到正确的 Enact 实例。

### 这一关检查什么

- 电脑在线。
- 所选 AI 工具被识别，并已完成自身的登录或模型配置。
- 工作区可以使用这条运行时。
- 电脑具备项目所需的 Git、构建与测试环境。
- 运行 AISDLC 校验脚本的 Python 环境具备 PyYAML 依赖。

**完成标志：**运行时可被选择，并能完成一次简短请求。在线状态只说明连接正常，实际请求还能验证工具认证与调用是否可用。

本地执行时，代码目录与 AI 工具的本机登录凭据留在执行电脑；任务、评论、执行记录与结果会回传 Enact。运行工具调用模型服务时仍遵循组织的数据使用规则。智能体自定义环境变量和 MCP 配置也不能一概理解为"只保存在本机"。

## 10. 第四步：接入代码，补齐项目背景

**目标：同时告诉智能体"代码在哪里"和"这个项目是什么"。**

### 10.1 接入仓库

打开工作区的"资源"页面，找到"代码仓库"区域。当前界面已把资源集中到独立页面；旧版本文档中的"设置 → 资源 / 代码仓库"可能跳转到这里。

普通 Git 项目优先使用仓库 URL：

1. 添加仓库地址，或通过已连接的代码托管服务选择仓库。
2. 确认本次试点使用的分支或版本引用。
3. 确认执行电脑能够访问仓库，尤其是私有仓库的认证与网络。
4. 有多个仓库时，写清本次修改的主仓库和作为依赖参考的仓库。

能把地址保存进 Enact，只证明资源已登记；还需确认运行时能实际读取代码。

Desktop 也支持关联本地目录。若使用"原地"模式，智能体会直接操作该目录及其当前工作状态；需要并行隔离时，使用满足条件的 Git worktree 模式。已有项目的执行模式由项目维护者确认。

### 10.2 填写项目画像

在"设置 → 工作区"填写项目用途、技术栈与常见工作类型，也可以请 Enact 引导补齐。

示例：

> 这是面向接待人员与顾问的客户服务平台，支持客户识别、服务记录与后续跟进。主要使用 TypeScript、Go 和 PostgreSQL。当前试点以小范围缺陷修复为主，需要保持已有接口兼容。

项目画像帮助智能体理解背景，也用于能力中心的推荐排序。

### 10.3 补充工作要求

由有权限的成员在工作区上下文中写入适用于整个项目的要求，例如：

- 构建、测试与代码风格以仓库说明为准。
- 接口与数据结构变更需要先明确调用方影响。
- 本次试点的目标环境与允许执行的动作。
- 结果需要给出代码差异、验证结果和遗留问题。

项目画像描述背景；工作区上下文表达工作要求；`.sdlc/config.yaml` 和执行契约进一步记录 AISDLC 的项目规则与单次变更边界。它们的作用不同。

**完成标志：**智能体能根据实际读取结果说明仓库结构、相关模块和测试入口；缺失的业务规则被列为待确认问题。

## 11. 第五步：从能力中心安装 AISDLC Agent Family

**目标：把协作方法配置为可以运行的智能体团队。**

1. 打开"能力中心"。
2. 找到 **AI-SDLC Delivery** 条目，查看说明、成员及前置条件。
3. 如果工作区已有所需版本，检查现有配置即可。
4. 需要安装时，选择已连接的运行时，并填写条目要求的配置。
5. 安装完成后，进入"智能体团队"，检查 Family 与成员。

当前内置 Family 包含以下九个智能体角色：

| 智能体 | 主要工作 |
|---|---|
| SDLC Orchestrator | 队长；协调路由、排程与一致性核对 |
| SDLC Intake | 登记工作、读取状态与阻塞信息 |
| SDLC Explorer | 澄清事实、假设和未决问题 |
| SDLC Contract | 形成执行契约，并提交人工确认 |
| SDLC Builder | 在获批范围内实施变更 |
| SDLC QA | 独立确定验证预期、测试与归因 |
| SDLC Release | 做发布预检，整理交付证据档案 |
| SDLC Operator | 诊断运营问题，将根因关联回上游 |
| SDLC Learner | 验证经验，提出可复用的改进 |

Family 配套使用十个 `sdlc-*` skill，其中 `sdlc-core` 提供共享模板与脚本，不对应一个单独的执行角色。

### 安装后必须检查

- **运行时绑定：**安装时全部成员绑定到所选运行时，之后可以逐个调整。
- **使用权限：**安装的智能体默认私有，按团队需要配置可见性与调用权限，尤其要确认用户可以运行队长。
- **依赖：**各成员的阶段 skill 与共享 `sdlc-core` 已配置；所需本机工具可用。
- **交接条件：**下一阶段必须能读到上一阶段的产物和准确版本。

**完成标志：**可以在任务负责人选择器中选择该 Family，队长及必要成员能够执行任务。

安装得到的是工作区副本。后续目录更新不会自动覆盖本项目已安装和修改的配置。

## 12. 第六步：初始化项目交付规则

**目标：把通用方法绑定到本项目的实际人员、工程命令和边界。**

安装 Family 后，还要为目标仓库准备 `.sdlc/`。首次运行时由 Intake 检查并初始化，项目维护者负责确认配置。已存在配置时先读取，不重复覆盖。

建议先建立一个准备任务，分配给 `AI-SDLC Delivery`：

```text
请为本工作区的 <目标仓库> 做 AISDLC 首次准备。

先检查运行时、仓库访问、sdlc-core 及阶段 skill、Python 与 PyYAML。
确认实际工作目录、代码版本，以及后续各阶段如何读取同一条交付记录。

由 Intake 检查并在必要时初始化 .sdlc/。
读取项目现有规范，列出需要我确认的人员角色、工程命令和执行边界。
这次准备的可写范围仅限所需的 .sdlc/ 初始化文件，不修改业务代码。

请返回：已就绪项、待补项、需要哪位成员补齐、初始化产物的位置与版本。
```

### 12.1 指定真实人员

在 `.sdlc/config.yaml` 的角色配置中填入实际承担职责的人：

| 角色 | 确认的内容 |
|---|---|
| 业务负责人 | 目标、业务规则、验收标准与用户风险 |
| 架构 | 技术方案、接口影响与变更边界 |
| 开发 | 实现方向与工程做法 |
| QA | 验证是否充分 |
| 运维 | 发布、监控与回滚准备 |

一个人可以承担多个角色，应如实记录。邀请进工作区或加入 Family，不会自动完成这些职责配置。

### 12.2 确认工程与执行规则

项目维护者需要确认：

- 真实的 lint、test、build 命令。
- 受保护路径和不得读取的数据。
- 允许执行的工具动作与目标环境。
- 何种任务可以使用 `quick` 通道。
- 人工评审要求和批准人。

首次试点沿用默认人工关口。`quick` 可以缩短材料篇幅，但不代表略过契约或发布决定。

内置模板默认禁止智能体执行 `push`、`deploy`、`publish`、`db-migrate`。发布批准后，由有权限的人通过既有工程流程完成相应操作；不要把 Release 智能体理解为部署服务。

### 12.3 确认交付记录可以延续

`.sdlc/` 存放在仓库中，各阶段必须依据同一项变更的有效记录开展工作。

初始化配置经项目维护者确认后，应纳入团队版本管理，并确保后续执行使用包含它的版本。使用多个运行时、独立 checkout 或不同 worktree 时，维护者还需确认阶段产物的交接方式。

**把九个智能体绑定到同一台电脑，并不自动意味着它们会使用同一个目录或分支。** 如果下一阶段读不到契约或证据，先修复交接条件。

**完成标志：**项目规则有实际人员认领，命令可用，初始化记录已保存，各阶段能够读取交付所需的文件与版本，阻塞准备的问题已解决。

## 13. 第七步：开始第一个任务

### 13.1 选择一个足够小、可以验证的目标

首次任务应帮助团队体验完整协作过程。优先选择目标清楚、影响范围有限、已有验证入口的小变更。

例如：修复 CSV 导出时负数金额丢失负号。若项目没有这项功能，换成真实存在的类似缺陷。

"优化整个系统"难以形成可验证的第一步。更好的表述是："导出后的负数金额与列表显示一致，财务无需手工修正。"

### 13.2 创建并分配任务

在 Enact 新建任务，填写标题和说明，并把负责人设为 **AI-SDLC Delivery**。确认状态为 `todo`，提交后查看执行记录。

处于 `backlog` 的任务不会因分配自动执行。任务进入可执行状态后，Enact 先唤醒队长，由队长把新需求交给 Intake，再按所需阶段推进。

可以复制下面的模板：

```text
标题：修复 CSV 导出时负数金额丢失负号

业务目标：
让导出文件中的金额与页面金额一致，减少人工核对与修正。

当前问题：
页面显示 -100.00，导出后变成 100.00。
请先确认实际复现步骤与影响范围，不把本描述直接当成已验证事实。

目标仓库与起始版本：
<仓库名称 / URL>，<分支或版本>

本次任务负责人：
<真实姓名>
各阶段评审与批准按已确认的 .sdlc/config.yaml 执行。

初步范围：
仅修复当前 CSV 导出金额符号问题；保持既有列结构。
不新增导出功能，不调整权限体系，不实施生产数据变更。

候选验收场景：
1. 负数保留负号。
2. 零值和正数保持现有约定。
3. 导出结果与列表一致。
4. 相关自动化测试与现有回归通过。
这些是待澄清的候选标准，由 Contract 阶段固化。

请先登记工作并核对上下文，集中提出需要人确认的问题。
遇到人工关口时，说明批准对象、当前版本、证据、风险与下一步。
```

### 13.3 接下来你会参与什么

| 阶段 | 智能体推进的工作 | 你需要做什么 |
|---|---|---|
| 登记 | 建立 Work Item，记录目标、owner 与通道 | 确认登记的是正确问题 |
| 澄清 | 核对事实，分析影响，集中提出未决问题 | 回答业务问题，明确取舍 |
| 契约 | 固化行为、设计、验收和边界 | 对当前版本作出明确批准或修改要求 |
| 实施 | 修改代码，记录差异与自测证据 | 必要时判断范围扩展；完成实现方向评审 |
| QA | 独立验证，记录结果与归因 | 判断验证是否充分，处理需人判断的缺口 |
| 发布准备 | 汇总证据与风险 | 决定 Release / Hold / Reject |
| 后续反馈 | 整理运营观察或经验候选 | 检查实际效果，决定是否固化经验 |

遇到问题可以回到上游：实现缺陷回 Builder；契约含义不清回 Contract；业务目标有问题回到澄清。

### 13.4 什么时候需要你明确批准

套件有五类人工关口。一次普通任务通常经过契约批准、实现评审、发布决定；扩大范围与固化经验时，才触发另外两类。

| 关口 | 你实际在决定什么 |
|---|---|
| 契约批准 | 目标、方案、验收标准与边界是否正确 |
| 范围扩展 | 是否允许新增修改范围 |
| 实现评审 | 做法方向是否合理，是否进入独立 QA |
| 发布决定 | 当前证据支持的剩余风险是否可接受 |
| 经验批准 | 是否将已验证经验固化到后续工作中 |

批准时应指明对象、版本和承担的角色。例如：

> 我以业务负责人身份确认 WI-001 的 contract v1 中业务目标与验收标准。架构和运维部分由已配置的对应责任人分别确认。

如果同一人承担全部所需角色，可以一次明确列出。含糊肯定、沉默或把任务状态改为 `done` 都不能替代相应批准记录。

重要内容修改后，需要对新版本重新确认。普通阶段评审也有价值，但不应把每次查看产物都新增成一道阻塞审批。

### 13.5 去哪里看进度与证据

从任务详情查看：

- **评论与时间线：**进展、澄清、交接与待决问题。
- **执行记录：**每轮运行的状态、过程、错误与结果。
- **产物与引用：**契约、实现证据、QA 报告和证据档案。
- **仓库记录：**对应 Work Item 的 `.sdlc/` 文件及实际代码版本。

仓库文件只有在智能体提供引用或提交为产物后，才有相应的便捷访问入口；不要假设所有 `.sdlc/` 文件都会自动展示在独立产品页面。

你可以继续在任务中提问：

> 现在在哪个阶段？卡在哪里？缺什么证据？下一步需要谁做什么？

需要主动触发特定智能体时，用编辑器的 `@` 菜单选择对象，并查看触发预览。单纯输入一段同名文字不等于有效提及。

## 14. 第一个任务怎样才算完成

请分开看三件事：

| 完成层次 | 判断依据 |
|---|---|
| 一轮执行结束 | 当前运行已结束，有结果或明确的失败原因 |
| 试点交付通过 | 获批契约、实现、独立 QA、交付证据和人工决定完整，实际成果已验收 |
| 生产效果成立 | 发布后真实业务行为达到目标，监控与恢复准备有效 |

AISDLC 内部 Work Item 的 `Completed` 状态也不能单独证明部署已经发生或线上指标已经达标。实际发布与业务效果需要对应事实。

### 首个任务的完成清单

- [ ] 目标与责任人明确，关键业务决定有记录。
- [ ] 契约已由所需角色批准，批准对象与版本明确。
- [ ] 实现处于获批范围内，差异、自测和实现评审可回查。
- [ ] QA 独立验证，验收标准与结果能够对应。
- [ ] 交付证据档案说明遗留问题、风险和处理人。
- [ ] 具名责任人作出发布、暂缓或拒绝的决定。
- [ ] 成果所在分支、提交或文件位置明确，已按本次试点范围验收。
- [ ] 如果包含实际发布，已通过既有流程执行，并记录发布结果和业务观察。
- [ ] 值得继续验证的经验已记录，并说明后续负责人。

如果试点只做到测试环境验证与发布准备，应明确这样收尾，后续生产发布和运营验证作为待办继续追踪。

任务因缺少决定或证据而暂停时，只要明确"缺什么、谁来补、补齐后回到哪一步"，就可以有据地继续推进。

## 15. 常见卡点

| 现象 | 优先检查 |
|---|---|
| 无法注册 | 当前部署的邮箱域限制、必填信息与密码要求 |
| 登录后没有工作区 | 是否已接受邀请；部署是否允许自行创建 |
| 没有运行时或工具离线 | AI 工具是否安装并登录；守护进程是否在线；当前工作区是否可使用 |
| 运行时在线但执行报错 | 工具自身认证、额度、路径与项目依赖；查看本轮执行错误 |
| 仓库已添加但读不到代码 | URL、分支、运行电脑的认证与网络；本地目录是否绑定了正确电脑 |
| 找不到 AI-SDLC Delivery | 当前部署版本与能力目录是否包含该条目，请管理员核对 |
| Family 已安装但无法选择 | 队长的使用权限、可见性和归档状态 |
| 已分配却没有开始 | 是否还在 `backlog`；运行时是否在线；是否在等待并发或目录锁 |
| 下一阶段说找不到契约 | 上一阶段是否落盘；当前目录、分支与引用版本是否一致 |
| 一直等批准 | 查看具体关口、所需角色与人员配置，确认决定已被明确记录 |
| QA 不通过 | 区分实现缺陷、需求缺口和环境问题，再交回对应阶段 |
| 执行完成却没有上线 | 发布决定与实际部署是不同动作，检查既有发布流程是否执行 |

## 16. 上手完成后，如何持续使用

新任务复用已准备好的工作区、运行环境、Family 和项目规则，重点补充本次目标、责任人、上下文与验收要求。

在每轮交付中持续检查三个问题：

1. 当前是在等待执行，还是等待人的决定？
2. 结论能否追溯到对应版本的事实和证据？
3. 本次经验是否值得验证后复用？

团队可以逐步引入更多仓库、专业评审与运营反馈。是否连接额外 MCP、Ontology 或 Intelligence Space，按真实任务需要决定；它们不是完成首个 AISDLC 任务的通用前置条件。

**完成本指南，意味着你已经能在 Enact 中组织一次有目标、有边界、有独立验证、有人工责任的交付，并知道怎样继续确认它的业务效果。**
