**学び**は、すでに終わった仕事を読み直したうえで書かれる、[スキル](/skills)への変更提案です。採用するか却下するかを決めるのはメンバーです。採用するとスキルはその場で変わり、そのスキルを使うすべてのエージェントに反映されます。

大事なのはこの循環です。スキルを手で書くだけのワークスペースは、誰かが戻って直そうと思い出した分だけ良くなります。学びを回しているワークスペースは、仕事を終わらせた分だけ良くなります。

## 学びが登録されるまで

すべてのワークスペースには **Lesson Learner** というエージェントがいます。学びを登録できるのはこのエージェントだけで、登録以外のことはしません。

これは意図的な設計です。ルールにする価値のある兆候は、複数の仕事にまたがって現れるパターン —— 同じ確認質問が二度出てくる、同じ箇所で手戻りが繰り返される —— であり、1 回の実行の内側からは見えません。目の前の仕事のために動いているエージェントに、自分の実行が長く効くルールを意味するかどうかまで判断させても、そのための視野も距離もありません。

Learner は**振り返り**を起点に動きます。振り返りとは、完了した仕事のまとまりを一度スキャンすることです。開始方法は 3 つあります。

| きっかけ | 範囲 | 開始方法 |
|---|---|---|
| **提案される** | タスク 1 件 | エージェントが関わったタスクが done ステータスになると、Enact がそのタスクの画面とインボックスで振り返りを提案します。 |
| **手動で開始** | タスク 1 件、またはワークスペース全体 | 学びの記録ページ、またはタスクから**振り返りを実行**します。 |
| **スケジュール実行** | ワークスペース全体 | Lesson Learner を担当に設定した[オートパイロット](/autopilots)。 |

振り返りは Learner を担当とする通常のタスクとして実行されます。そのため、読める実行記録があり、指示を出せるコメント欄があり、見つけたことを報告する場所があります。

<Callout>
タスク完了後の提案は、どう答えても 1 つのタスクにつき一度きりで、二度目はありません。見送るのも普通の答えです。この提案が煩わしいワークスペースは、ワークスペース設定でオフにできます。手動やスケジュールで始める振り返りには影響しません。
</Callout>

## 提案に含まれる内容

次の 4 項目は必須で、どれか 1 つでも欠けていると API が提案を受け付けません。

| 項目 | 答えること |
|---|---|
| **何が起きたか** | 実際に起きた出来事。どの実行、どのタスク、どのコメントで起きたかを添えて書きます。 |
| **当てはまる場面** | このルールが成り立つ条件。 |
| **当てはまらない場面** | それに従うと間違いになるケース。 |
| **変更の概要** | スキルに加える具体的な変更。 |

省略したくなるのは反例ですが、いちばん効いてくるのもそこです。どこで成り立たなくなるかを書き手が言えないルールは、たいていまだ見つかっていません。1 件の事例を一般化しただけです。最初に書かせるほうが、そのルールが 1 か月かけて静かにすべての実行を形づくった後で気づくより安く済みます。

## 学びをレビューする

**学びの記録**ページかインボックスから学びを開きます。ページには次の順で表示されます。

1. その提案を今も採用できるかどうか
2. 何を観察したか、当てはまる場面、当てはまらない場面
3. 対象のスキルを今使っているエージェント —— つまり挙動が変わる全員
4. 現在のスキルとの差分

採用はすぐに反映されます。別のロールアウト手順はないので、決定とスキルの状態が食い違う瞬間は生まれません。

そのスキルを編集できる人は、そのスキルを対象とする学びを決定できます。スキルの作成者か、ワークスペースの `owner` / `admin` です。新しいスキルの作成を提案する学びには `owner` か `admin` が必要です。**エージェントは学びを決定できません。自分で登録した学びも同じです。** Enact は該当のエンドポイントでエージェントの認証情報を拒否します。

### 内容が古くなった提案

提案には、それが書かれた時点のスキルのバージョンが記録されています。その後にスキルが変更されていると、提案は内容が古いものとして扱われ、採用できなくなります。

これは形式のための手間ではありません。この仕組みがないと、レビューする人が誰も使っていないテキストへの差分を承認できてしまいます。現在のバージョンに合わせて書き直してもらい、そのうえで読み直してください。今のスキルの内容の上では、その変更がもう筋の通らないものになっているかもしれません。

## バージョン履歴と取り消し

スキルの内容の変更は、原因が何であれすべてバージョンとして記録されます。アプリでの編集、インポート、ソースからの更新、採用した学び、復元のいずれもです。スキルページの**バージョン**一覧には、そのすべてと、それぞれを生んだ操作が表示されます。

戻る方法は 2 つあります。

- スキルページから**バージョンを復元する**。復元した内容は履歴を巻き戻すのではなく新しいバージョンとして追加されるので、復元自体も取り消せます。
- 学びのページから**学びを取り下げる**。スキルは以前の状態に戻ります。ただしその後にスキルが変更されている場合、その変更はそのまま残し、学びだけを取り下げ済みにします。取り下げには理由が必要です。

取り下げた学びも記録として残ります。試して戻したルールと、そもそも提案されなかったルールは別ものです。同じことを次に思いついた人が、どちらだったのかを調べられる必要があります。

## CLI から

```bash
enact lesson list --status proposed
enact lesson get <id>

# 対象とするバージョンを確認してから提案する。
enact skill versions <skill-id>
enact lesson propose \
  --skill <skill-id> --base-version <version-id> \
  --title "引き継ぎでランタイムを明示する" \
  --observation "2 回続けて、どのマシンを使うか質問された。" \
  --applies-when "ローカルリポジトリを扱うタスク。" \
  --counterexample "クラウドのみの作業はランタイムが 1 つで、書いてもノイズになる。" \
  --change-summary "引き継ぎチェックリストに 1 行追加する。" \
  --content ./proposed-SKILL.md

enact lesson approve <id> --reason "2 回観測、境界も明確"
enact lesson reject <id> --reason "発生は 1 回だけ"
enact lesson withdraw <id> --reason "クラウドのみの作業でも発動してしまった"

enact retrospective start --scope workspace --since-days 14
enact retrospective list
```

`--base-version` にデフォルト値はなく、今後も持たせません。提案は、それが書かれた時点のバージョンを指し示すものです。「現在」を代わりに解決してしまうと、この項目が閉じているはずの競合を静かに呼び戻すことになります。
