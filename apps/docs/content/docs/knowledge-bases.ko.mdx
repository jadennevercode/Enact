지식 베이스는 에이전트가 읽는 문서의 git 저장소입니다. 도메인 배경, 제품 결정, 새 동료에게 한 번은 설명해야 하는 것들이 들어갑니다. 팀이 작업하는 [리소스](/resources) 저장소와 나란히 존재하지만, 워크스페이스 전체가 아니라 개별 에이전트에 연결된다는 점이 다릅니다.

## 지식 베이스와 skill 중 무엇을 쓸까

둘 다 에이전트에게 글을 전달하지만, 언제 로드되는지가 다릅니다.

| | skill | 지식 베이스 |
|---|---|---|
| 답하는 것 | 어떻게 하는가 | 팀이 무엇을 아는가 |
| 로드 방식 | 사용하는 모든 작업에 전문 | 색인은 매번, 문서는 필요할 때 |
| 수정하는 사람 | skill 관리자 | 저장소 권한이 있는 사람과 회고 에이전트 |
| 저장 위치 | Enact 안, skill 단위 버전 관리 | 팀의 git 저장소 |

매번 적용되는 규칙은 [skill](/skills)에 둡니다. skill은 전문이 로드되며, 아무도 읽지 않는 규칙은 아무것도 바꾸지 못하기 때문입니다. 가끔 필요한 배경은 지식 베이스에 둡니다. 매번 전부 로드하면 그것이 필요 없던 작업에까지 컨텍스트 예산을 물리게 되기 때문입니다.

## 에이전트는 어떻게 읽는가

작업이 시작되기 전에 런타임이 저장소를 머신에 체크아웃하고 각 문서의 front-matter를 읽습니다. 그러면 에이전트 브리프에 문서당 한 줄짜리 색인이 실립니다.

```text
## Knowledge

### 도메인 핸드북

- Location: `/…/.knowledge/…/docs`
- Source: https://github.com/acme/handbook.git (`main`)
- Documents: 12

- **배포 시간대** — 언제 릴리스할 수 있는가. (`deploy-window.md`)
- **가격 모델** — 등급별 가격 책정 방식. (`pricing.md`)
```

에이전트는 매 작업마다 이 색인을 읽고, 실제로 관련 있는 한두 개만 코드에 쓰는 것과 같은 파일 도구로 엽니다. 문서 본문이 브리프에 붙는 일은 없습니다.

그래서 front-matter는 선택 사항이 아닙니다. `title`과 `description`은 이후 작업이 그 문서를 열지 말지 판단하는 유일한 근거이며, 내용을 말해주지 못하는 description은 그 문서가 발견되지 않는다는 뜻입니다.

```markdown
---
title: 배포 시간대
description: 언제 릴리스할 수 있고 예외는 누가 승인하는가.
updated: 2026-09-05
source: ENA-1234
---
```

<Callout type="info">
문서가 60개를 넘으면 색인은 디렉터리와 문서 수를 나열하는 방식으로 바뀌어, 이 절의 크기가 지식 베이스와 함께 커지지 않습니다. 에이전트는 디렉터리를 나열하고 필요한 것을 읽습니다.
</Callout>

## 지식 베이스 추가하기

**설정 → 리소스**에서 저장소를 추가한 뒤, 읽어야 할 에이전트에 연결합니다. 어떤 에이전트에도 연결되지 않은 지식 베이스는 보이지 않습니다. 받은 편지함만 정리하는 에이전트의 브리프에 도메인 핸드북이 들어가지 않는 이유가 바로 이것입니다.

```bash
# 워크스페이스에 리소스 생성
enact resource add --type knowledge_repo --url https://github.com/acme/handbook.git \
  --path docs/knowledge --label "도메인 핸드북" --output json

# 특정 에이전트가 읽도록 연결
enact agent knowledge add <agent-id> --resource-id <resource-id> --output json
enact agent knowledge list <agent-id> --output json
```

| 필드 | 의미 |
|---|---|
| `url` | 런타임이 접근할 수 있는 모든 git URL |
| `ref` | 읽을 브랜치, 태그, 커밋 (기본값은 저장소 기본 브랜치) |
| `path` | 문서가 있는 하위 디렉터리. 다른 내용과 저장소를 공유할 수 있습니다 |
| `delivery` | `pull_request`(기본) 또는 `commit`. 아래 참조 |

연결을 해제해도 리소스는 워크스페이스에 남아 다른 에이전트가 씁니다. 리소스를 삭제하면 모든 에이전트의 연결도 함께 사라집니다.

## 다시 기록하기

에이전트는 코드를 쓰는 것과 같은 방식으로 문서를 씁니다. 브리프에 있는 색인된 위치는 그 머신의 모든 작업이 공유하며 작업마다 초기화되므로, 에이전트는 그곳을 편집하지 않습니다. `enact repo checkout <url>`으로 자기 몫의 체크아웃을 받아 거기에 쓰고 다음 중 하나로 전달합니다.

- **`pull_request`**(기본)는 풀 리퀘스트를 열고 병합은 사람에게 맡깁니다. 지식 베이스는 연결된 모든 에이전트의 이후 모든 작업이 읽으므로, 검토되지 않은 문서는 나쁜 파일 하나가 아니라 몇 달 동안 계속 인용되는 나쁜 파일입니다.
- **`commit`**은 해당 ref로 바로 푸시합니다. 모든 메모를 검토하고 싶지 않은 팀을 위한 것입니다.

## 회고 에이전트

지식 베이스가 썩지 않고 쌓이는 이유가 이것입니다. [회고 에이전트](/retrospect)는 끝난 작업을 돌아보고 배운 것을 적습니다. 지식 베이스를 연결해 두면 그 문서가 아무도 다시 열지 않는 첨부 파일이 아니라 지식 베이스에 남습니다.

쓰기 전에 색인을 읽으므로, 같은 주제를 이미 다룬 문서가 있으면 그 옆에 두 번째를 만들지 않고 그 문서를 고칩니다.
