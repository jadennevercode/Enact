<Callout type="warn">
The server needs one setting: `ENACT_VCS_SECRET_KEY`, a base64-encoded 32-byte key (`openssl rand -base64 32`). It encrypts every stored token, webhook secret and enterprise CA. Without it the page explains what is missing and refuses to store a credential. Set `ENACT_PUBLIC_URL` too, so Enact can register webhooks at an address the provider can reach.

Everything is configured in **Sources → Code & directories** by a workspace owner or admin. Choose **Connect** and pick one of:

| Option | Use it for | What you enter |
| --- | --- | --- |
| GitHub.com with a token | github.com, when no GitHub App is set up | A fine-grained or classic token |
| GitHub Enterprise Server | A GHES instance, including one on an internal network | Instance URL and a token |
| GitLab | GitLab.com or a self-managed GitLab | Instance URL, an API token and a Git token |
| GitHub App | github.com, when the deployment has an App configured | Nothing; you are redirected to GitHub |

A token connection needs no deployment-level provider setup. The GitHub App remains the stronger credential where it is available: it mints a short-lived token per repository and GitHub registers its webhook.

## Network requirements

The Enact server calls the provider API, and each daemon clones over HTTPS. Both must reach the instance. An Enact server on the public internet cannot reach a GitLab that only exists on an internal network. The server honours `HTTPS_PROXY` and `NO_PROXY`.

Webhooks travel the other way, from the provider to Enact. A self-managed GitLab often blocks requests to internal addresses; ask its administrator to allow the Enact webhook host under **Admin → Settings → Network → Outbound requests**. Each connection card shows the exact address.

## Tokens

**GitHub.** One token authenticates both the API and HTTPS Git. A fine-grained token needs these repository permissions: Contents read and write, Pull requests read and write, Webhooks read and write, Checks read, Commit statuses read, and Metadata read. A classic token needs `repo` and `admin:repo_hook`. If your organization uses SAML SSO, authorize the token for it; otherwise GitHub accepts the token and then refuses every request.

**GitLab.** GitLab splits the two jobs, so it takes two tokens. The API token needs `api` and stays on the Enact server for browsing and merge requests. The Git token needs `write_repository` and is delivered only to an authorized daemon, per repository. Prefer an expiring service account limited to the projects you need. Accounts that sign in through LDAP or SSO can create these tokens from their user settings.

Expiry is optional. Enact records the scopes the provider reports, not the ones entered. A fine-grained GitHub token reports none, and the card says so rather than showing an empty list.

## Enterprise options

These fields appear only for an instance you supply:

- **Clone host**: the hostname Git traffic uses when it differs from the API host. Enact rewrites each attached repository's remote to it.
- **Enterprise CA (PEM)**: added to the trust store for server API calls and daemon Git traffic. TLS verification cannot be turned off.

## Attaching repositories and webhooks

Choose **Browse repositories** on a connection. The picker lists what the credential can reach. Repositories the credential cannot push to, archived repositories, and repositories already attached cannot be selected.

When you attach a repository, Enact registers a webhook on it in the background. The card's Webhook leg then shows one of:

- `registered`: the hook exists. It is not yet proof that a delivery arrived.
- `ok`: a signed delivery was received.
- `manual`: the token may not manage hooks. Add one by hand with the webhook address on the card and the secret shown once at connect time.
- `failed`: registration did not succeed. Choose **Register webhooks** to retry.

Enact subscribes GitHub to `pull_request`, `check_run` and `status`, and GitLab to merge request and pipeline events. It only processes events for repositories attached to that connection.

## Connection health

Each card reports five legs independently: API, Webhook, Git read, Git write, and PR or MR creation. **Test** checks the API leg. Git read and write are reported by each daemon for each repository. A healthy API says nothing about whether a daemon can clone.

## Pushing and pull requests from a task

In a managed repository an agent uses `enact repo push`. The daemon fetches a repository-scoped credential, writes it to a `0600` temporary credential store for the push, and deletes it afterwards. `enact repo change-request --title "…"` then opens the pull or merge request through the Enact server, so the provider API token never enters the agent process.

Repositories saved by older versions as a bare URL appear as **Pending configuration** and stay disabled until an admin binds them to a connection. SSH transport is planned as a separate phase.
