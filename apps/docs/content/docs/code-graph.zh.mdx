代码图谱是一个仓库的结构图：它的文件、类和函数，它们之间的导入与调用，以及这些连接聚成的子系统。Enact 在服务端用 [graphify](https://github.com/safishamsi/graphify)（Apache-2.0 / MIT）从仓库源码构建它，只做 tree-sitter 解析，不调用任何模型。所以构建不花 token，仓库也只在你的 Enact 部署内部被克隆。

智能体用它在打开文件之前先找对子系统；人用它看一个仓库是怎么拼起来的。

## 按仓库启用

代码图谱按仓库选择启用，除此之外没有别的要配。

- 在 **设置 → 资源** 里 **从 GitHub 选择** 或粘贴 Git URL 时，勾选 **为所选仓库构建代码图谱**。这一次勾选作用于该对话框里添加的全部仓库。
- 之后，在仓库行的菜单里把 **代码图谱** 打开或关闭。

打开即排队第一次构建；关闭会删除这个仓库的全部构建，包括服务端上的数据。

部署没有代码图谱服务时（见[部署](#部署)），复选框禁用并附一句说明。本地目录不提供这个选项：服务端读不到你机器上的目录。

## 状态 chip 的含义

启用后，仓库行末尾多一个 chip：

| chip | 含义 |
|---|---|
| **就绪 · a1b2c3d · 2 小时前** | 该 commit 的图谱可以查询。点 chip 打开代码图谱页面。 |
| **构建中…** | 有一次构建在排队或运行。这期间智能体照常用文件工具工作。 |
| **已跳过 · 文件数超限** | 仓库超过文件数上限。什么都没建，也没有半截的图。 |
| **失败 · 原因** | 克隆或构建失败。**重试** 会再排一次。 |
| *（没有 chip）* | 这个仓库没有启用代码图谱。 |

## 代码图谱页面

每个启用的仓库在 **智能中心 → 代码图谱** 下有一页，从 chip 也能进。页头写着图谱基于哪个 commit、何时构建、多大；工作区所有者和管理员可以点 **重新构建**。

| Tab | 展示什么 |
|---|---|
| **概览** | 构建报告：最大的几个子系统、连接最多的节点、意料之外的跨子系统连接，以及相比上一次构建的变化。 |
| **子系统** | 每个子系统的规模与内聚度、一篇生成的说明文章、主要文件，文件链到 GitHub 上构建时的 commit。 |
| **图谱** | 子系统作为节点，边的粗细表示相互引用的多少。点子系统展开，点节点看邻域和 `文件:行号`。投影过大时按度数截断，并明确标出。 |
| **结构树** | 文件和符号的层级，折叠树展示。 |
| **调用流** | 每个子系统一张图，画出把它连在一起的调用。 |

<Callout type="info">
子系统是图聚类找出来的社区，以连接最多的成员命名。它是结构分组，不是目录：一个子系统可以跨多个包，一个包也可能被拆成几个子系统。
</Callout>

## 智能体怎么用

检出了已启用仓库的智能体，都能通过 `enact` CLI 用到图谱。内置 skill 让它先跑 `enact graph status`，图谱就绪时先读报告、先查图，再打开文件。

```bash
enact graph status                 # 就绪 / 构建中 / 未启用，以及 commit
enact graph report                 # 与概览 tab 相同的报告
enact graph query "webhook 投递在哪里重试"
enact graph path "IssueHandler" "TaskQueue"
enact graph explain "WebhookDeliveryWorker"
enact graph affected "EnqueueTask"  # 什么依赖这个符号
enact graph communities
```

每个命令都接受 `--repo <url>`；不给时用当前目录检出的那个仓库。图谱未启用、还没建好，或部署没有代码图谱服务时，命令以退出码 2 结束并只打印一行原因，智能体接着用普通文件工具干活。见 [CLI 参考](/cli#enact-graph)。

`calls` 边是从语法树推断出来的，每条回答里都会标出来；把它当强线索，不当证据。跨文件解析对 Python 最完整，对 Go 和 TypeScript 偏稀疏，所以"图里没有"从来不等于"代码里没有"。

## 保持最新

一张图谱基于默认分支的某一个 commit，chip 上一直写着它。

- GitHub 上**默认分支有 push** 就排一次重建，每个仓库五分钟内只排一次。
- 没有 webhook 的仓库**每六小时轮询**一次，分支头变了才排。
- 一次读取发现图谱落后于已知的分支头，就标记为**过期**并排一次重建。旧图谱在这期间仍可查询。

重建是增量的：只重新解析上次构建以来变过的文件。

## 限制

- 默认每个仓库最多 20,000 个源码文件（`CODEGRAPH_MAX_FILES`），超过即跳过。
- 图谱 tab 每次投影最多 500 个节点、1,500 条边，截断时会说明。
- 不支持本地目录。
- 只解析源码。仓库里的 Markdown、PDF 和图片会被忽略——那是[知识库](/knowledge-bases)的事。

## 部署

代码图谱服务是一个可选容器。没有它，复选框禁用，其他功能不变。

```bash
docker compose -f docker-compose.selfhost.yml -f docker-compose.codegraph.yml up -d
```

| 位置 | 变量 | 含义 |
|---|---|---|
| Enact 服务端 | `ENACT_CODEGRAPH_SERVICE_URL` | 服务的内部地址，compose 里是 `http://codegraph:8767`；留空即关闭该功能 |
| Enact 服务端 | `ENACT_CODEGRAPH_SERVICE_KEY` | 每次请求都带上的共享密钥 |
| 容器 | `CODEGRAPH_SERVICE_KEY` | 必须与服务端一致；没有密钥时服务拒绝一切请求 |
| 容器 | `CODEGRAPH_ALLOWED_HOSTS` | 允许克隆的主机，默认 `github.com`；自托管 Git 要把自己的主机加进来 |
| 容器 | `CODEGRAPH_MAX_FILES` | 每个仓库的文件数上限，默认 `20000` |
| 容器 | `CODEGRAPH_BUILD_TIMEOUT_S` | 单次构建超时，默认 `900` |

服务把每个仓库的检出和图谱放在 `codegraph_state` 卷上。卷丢了，Enact 数据库里的状态和报告还在，图谱、结构树、调用流三个 tab 和智能体查询会返回"未构建"，下一次重建——手动点，或者一次 push 触发——就从仓库把一切重新建出来。没有任何东西需要迁移。

克隆私有仓库用的是短期的 GitHub App installation token，或自托管 Git 集成里保存的 token。它只为这一次克隆传给服务，不写盘、不进日志。

## 代码图谱与 Ontology

两者回答的问题不同，也不共享数据。代码图谱描述一个仓库的代码是怎么组织的；Ontology 描述一个业务领域——实体、行动、策略——并在人工审批下把它绑到真实系统上。文档放[知识库](/knowledge-bases)，代码图谱从不读它们。
