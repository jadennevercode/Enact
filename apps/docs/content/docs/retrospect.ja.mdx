**振り返りエージェント**は、すでに終わった仕事を読み、その結果として何を変えるべきか — あるいは何も変えなくてよいか — を判断します。出力は次の 2 種類だけです。

- **設定の変更** — [スキル](/skills)、[エージェント](/agents)の指示、[スクワッド](/squads)リーダーの指示に対する変更提案。一度起きた失敗を、二度目からは起こしようがなくするためのものです。
- **ナレッジドキュメント** — プロダクトやドメインについての markdown。エージェントに紐付いた[ナレッジベース](/knowledge-bases)に書き、それがなければワークスペースのリポジトリの `docs/knowledge/` に置き、そのワークスペースがコードを届けているのと同じ方法で届けます。

大事なのはこの循環です。スキルを手で書くだけのワークスペースは、誰かが戻って直そうと思い出した分だけ良くなります。振り返りを回しているワークスペースは、仕事を終わらせた分だけ良くなります。

## 有効にする

このエージェントは自動では作られません。**新規エージェント**ページで誰かが設定したときに、ワークスペースはこのエージェントを 1 体持ちます。動かす[ランタイム](/daemon-runtimes)と書く言語を選ぶと、Enact は **Retrospect** という名前のエージェントを 1 体作ります。ワークスペース全体から見え、どのメンバーでも実行できます。

設定することがスイッチのすべてです。ワークスペース側にもう 1 つの設定は意図的に置いていません。設定とエージェントが食い違うと、そのワークスペースがある仕事から学んだのかどうかを誰も説明できなくなるからです。

止めるにはエージェントをアーカイブします。戻せば循環も戻ります。アーカイブ済みのエージェント、またはランタイムが外れたエージェントは、何も登録しません。二度目の設定は、すでにあるエージェントを返すだけで、2 体目は作りません。

<Callout>
振り返りエージェントの**指示**フィールドには、このワークスペース独自の補足を書きます — ナレッジドキュメントの置き場所、対象となるスキルやエージェント、このチームが書き残す価値があると考えるもの。これらは組み込みの契約の下に重ねられ、足すことしかできません。設定変更の前に同意を得るという関門、提案の前提となる「繰り返し起きたか」という基準、却下したものを報告する義務は、いずれも取り除けません。
</Callout>

## 振り返りが起きるきっかけ

| きっかけ | 開始方法 |
|---|---|
| **イシューの完了** | エージェントが実際に手を入れたイシューが done 系のステータスに入ると、Enact がその下に振り返りの子イシューを作り、このエージェントに割り当てます。 |
| **割り当て** | 任意のイシューを振り返りエージェントに[割り当て](/assigning-issues)ます。 |
| **メンション** | コメントで[@メンション](/mentioning-agents)します。 |
| **スケジュール実行** | [オートパイロット](/autopilots)の実行者に指定します。 |

4 つのうち 3 つは通常の割り当てです。振り返りエージェントもエージェントなので、普段エージェントに対してしていることはそのまま通用します。

自動のものには、知っておく価値のある条件があります。

- **エージェントが動いた仕事だけ。** タスクが 1 度も走っていないイシューには読むべき実行記録がなく、振り返りは推測を結論の形で書いたものになります。
- **1 イシューにつき 1 回だけ。** 再オープンして再度完了しても、二度目の振り返りは行われません。
- **振り返りの振り返りはしません。** 子イシューを完了しても、何も登録されません。

子イシューは完了したイシューの下に、優先度 low で作られます。作成者は完了したイシューの持ち主で、そのため誰かの購読に入り、提案が出たときにスレッドに答える人がいる状態になります。

## ほとんどの振り返りは何も変えません

変更を提案する基準は、繰り返し起きたかどうかであって、気に障ったかどうかではありません。二度起きていて、次にどこで起きるかを言えること。1 回だけでは足りません。誰も検証していない好みも足りません。プロダクトの不具合も違います — それは書くべきルールではなく、立てるべきイシューです。

そのため、よくある結果は「何も変える必要はない」という結論とその理由を書いたコメントです。これは立派な結果であり、そう報告することがこの仕事そのものです。毎回何かを見つけてくる振り返りは、いずれ誰にも読まれなくなります。

報告には、**検討したうえで却下したもの**も並びます。むしろこちらのほうが役に立ちます。次の振り返りが同じ論点を蒸し返さずに済む記録だからです。

## 同意という関門

このエージェントが自分の判断だけで設定を書き換えることはありません。変えたいものがあるときは提案コメントを投稿し、子イシューを `in_review` にして、そこで待ちます。

提案はこの順で構成されます。

| 項目 | 何を答えるか |
|---|---|
| **何が起きたか** | 具体的な場面。id かリンク付きで、最低 2 件。 |
| **何を変えたいか** | 対象を明確に。どのスキル、どのエージェント、どのスクワッド、どのファイルか。 |
| **変更前** | 現在の文面をそのまま引用。 |
| **変更後** | 提案する文面をそのまま。 |
| **どこで効き、どこで効かないか** | 境界 — 新しいルールが発動す**べきでない**ケース。 |

境界は省略したくなる項目であり、いちばん効いている項目でもあります。どこで止まるかを書き手自身が言えないルールは、たいていまだ見つかっていません。1 件の事例が一般化されただけです。

同意とは、人がそう返信することです。**ステータスの変更は同意ではなく、沈黙も同意ではなく、エージェント自身のコメントも同意ではありません。** 同意を得たら、エージェントは現在の文面を読み直し — 待っている間に誰かが変更していれば、上書きせずに提案し直します — 変更を適用し、何を適用したかを書き、子イシューを done にします。

ナレッジドキュメントはこの関門を通りません。純粋な追加であり、ドキュメントが 1 つ増えても挙動は何も変わらないため、出来のよくないドキュメントの代償は限られています。スキルの変更はそうではありません。

## 変更を取り消す

スキルの変更にはバージョンが残ります。振り返りエージェントが適用した変更も、他の書き込みと同じように[スキル](/skills)ページの**バージョン**一覧に並びます。古いバージョンの復元は履歴を巻き戻すのではなく新しいバージョンとして追加されるので、復元そのものもやり直せます。

```bash
enact skill versions <skill-id>
```

エージェントとスクワッドの指示にはバージョンが**ありません**。提案コメントにそのまま引用された**変更前**が唯一の戻り道であり、提案の形式がそれを必須にしているのはこのためです。変更が入ったあともスレッドは消さずに残してください。
