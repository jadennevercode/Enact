**复盘智能体**读的是已经结束的工作，判断这次工作应该带来什么改变、或者不需要任何改变。它只产出两种东西：

- **配置改动** —— 对 [skill](/skills)、对某个[智能体](/agents)的指令、或对某个[小队](/squads) leader 指令的改动提议，让犯过一次的错不再有机会犯第二次。
- **知识文档** —— 关于产品和业务的 markdown，写进挂在这个智能体上的[知识库](/knowledge-bases)；没有知识库时写进工作区仓库的 `docs/knowledge/` 目录，并按这个工作区交付代码的方式交付。

关键在于这个循环：只靠手写 skill 的工作区，改进速度取决于有没有人想起来回去修改它；做复盘的工作区，改进速度取决于它完成了多少工作。

## 开启

这名智能体不会自动创建。工作区要有它，得有人在**新建智能体**页面配置一次：选好它使用的[运行时](/daemon-runtimes)和它书写的语言，Enact 就会创建一名叫 **Retrospect** 的智能体，整个工作区可见，每位成员都能运行它。

配置它就是唯一的开关。这里刻意没有第二个工作区级开关 —— 开关和智能体可能互相矛盾，那时就没人说得清这个工作区到底有没有从一件工作里学到东西。

要关掉，把这名智能体归档；恢复它就重新开启。已归档、或者没有绑定运行时的智能体，不会提交任何东西。重复配置只会把工作区已有的那名智能体返回给你，不会创建第二名。

<Callout>
复盘智能体的**指令**字段放的是这个工作区自己的补充说明 —— 知识文档放在哪里、哪些 skill 和智能体在范围内、这个团队认为什么值得写下来。它们叠在一份内置约定之下，只能做加法：不能取消改配置前必须取得同意这一关，不能降低"要重复出现才提"的门槛，也不能免掉汇报被否掉了什么的义务。
</Callout>

## 什么时候会发生一次复盘

| 触发方式 | 怎么开始 |
|---|---|
| **完成一条 issue** | 智能体确实参与过的 issue 进入 done 状态后，Enact 会在它下面创建一条复盘子 issue，分配给复盘智能体。 |
| **分配** | 把任意一条 issue [分配](/assigning-issues)给复盘智能体。 |
| **@ 提及** | 在评论里[提及它](/mentioning-agents)。 |
| **定时执行** | 用一条[自动化](/autopilots)指向它。 |

四种里有三种就是普通的分配。复盘智能体是一名智能体，你平时对智能体做的事在它身上都成立。

自动触发的那种有几个前提值得知道：

- **只复盘智能体做过的工作。** 没有跑过任何执行任务的 issue 没有执行记录可读，对它做复盘只是把猜测写成结论。
- **每条 issue 只复盘一次。** issue 被重新打开又再次完成，不会被复盘第二次。
- **绝不复盘一次复盘。** 完成这条子 issue 不会再触发任何东西。

子 issue 创建在已完成 issue 的下面，优先级为低，并挂在这条 issue 所属的人名下 —— 这样它会进到某个人的订阅里，提议提出来时线程里有人回答。

## 大多数复盘什么都不改

提改动的门槛是重复出现，不是让人不舒服：某件事发生过两次，而且你说得出它下次会在哪里再发生。只发生过一次不算，没人验证过的偏好不算，产品缺陷也不算 —— 那应该提一条 issue，而不是写成规则。

所以常见结果是一条评论，说明什么都不需要改，以及为什么。这是真实的结论，把它汇报出来就是这份工作本身；每次都能找出点什么的复盘，最后没有人会看。

汇报里还会列出它**考虑过并否掉**的东西。这半部分反而更有用：有了这份记录，下一次复盘不会把同一个问题再吵一遍。

## 审阅这一关

这名智能体绝不自己改配置。它想改什么的时候，会发一条提议评论，把子 issue 改成 `in_review`，然后等待。

一条提议按这个顺序包含：

| 部分 | 回答什么 |
|---|---|
| **发生了什么** | 具体发生的场合，附 id 或链接，至少两次。 |
| **想改什么** | 明确的对象：哪个 skill、哪个智能体、哪个小队、哪个文件。 |
| **改动前** | 当前内容，原样引用。 |
| **改动后** | 提议的内容，原样写出。 |
| **什么时候适用、什么时候不适用** | 边界 —— 一个新规则**不**该生效的情形。 |

边界是最容易被跳过的一项，也是最吃重的一项。一条连作者都说不出边界在哪里的规则，通常还没有真正被找到 —— 只是把一个个例推广了。

同意指的是有人回复表示同意。**状态变化不是同意，沉默不是同意，它自己的评论也不是同意。** 拿到同意后，这名智能体会重新读一遍当前内容 —— 如果在它等待期间有人改过，它会重新提议，而不是覆盖别人的改动 —— 然后应用改动、说明它改了什么，并把子 issue 置为 done。

知识文档不走这一关。它们是纯增量的：不会因为多了一份文档而有任何行为改变，所以一份写得不好的文档，代价是有限的，而一次 skill 改动不是。

## 怎么撤回一次改动

skill 的改动有版本。复盘智能体应用的改动会和其它写入一样出现在 [skill](/skills) 页面的**版本**列表里；恢复某个旧版本是把它作为新版本追加，而不是回退历史，所以恢复本身也可以再撤销。

```bash
enact skill versions <skill-id>
```

智能体和小队的指令**没有**版本。提议评论里原样引用的**改动前**是唯一的回退依据，这也是提议格式里必须写它的原因 —— 改动落地之后，把那条线程留着，不要清掉。
