# 步骤 · factor-tree/derive —— 在锁定的骨架上推导 L3/L4 与候选指标

产出 `artifacts/s1/factor-tree.yaml`（照 `../templates/factor-tree.yaml` 填）
与给人看的 `artifacts/s1/factor-tree.xlsx`（工作簿应用生成，没人手改）。

这一步做两件事，别的都不做：

1. **识别冲突** —— 基线（客户的树或行业包）里有哪些行跟这个品牌对不上，标出来交人裁决
2. **往下扩展** —— 在 L1/L2 不动的前提下补 L3/L4 与候选指标

**类型：C 为主。** 判断哪一条与这个品牌相关是判断；读客户的树、算增删幅度是计算。

## 1 · 读齐输入（M）

只读下面这些，如实记录字数：

| 读什么 | 拿它做什么 |
|---|---|
| `artifacts/s1/knowledge-package.md` | 召回到的行业先例、锁定的 L1/L2、什么没有先例 |
| `artifacts/s1/materials-index.md` | 起底方式 `baselineChoice`、`gapFillPack`、有哪些材料可用 |
| `artifacts/s1/project-profile.yaml` | 时间颗粒度、模型范围三轴（每行 `dimension` 的默认值）、响应指标 |
| `artifacts/s1/factor-tree.yaml` | **重跑时接续用**。已经有人裁决过的行不重算 |
| `inputs/industry-reference/**` | 补 L3/L4 与候选指标的材料依据 |
| `inputs/client-factor-tree/**` | 仅当起底方式是 `client-tree` |
| 网络检索 | 只有这一步可以联网，见第 5 节 |

## 2 · 取基线行（M）

看材料索引里的 `baselineChoice`：

**`client-tree` 分支（客户上传了树时的默认）** —— 用脚本读，不要自己看着 Excel 抄：

```bash
~/.local/bin/mmm script read_client_tree <workspace>
```

它按固定规则解析：表头必须在**前 6 行**内、必须含指标列以及 L1 或 L4 之一、
L1–L4 **前向填充**（某一级取到新值时会把它下面所有级清空）。
最后那条最容易漏，漏了上一个 L4 的名字会挂到下一个 L3 的第一行上——
这种错在一张几十行的表里几乎看不出来，所以它是脚本不是提示。

解析出来的行标 `source: upload`、`status: baseline`，`evidence` 用脚本给的
"文件名 :: 表名 第 N 行"。**保留客户的措辞**，哪怕你会换个叫法——
改名这件事留到确认时当面谈，不在解析时悄悄做。

脚本报出来的 `skipped` 要看一眼：读不了的文件和找不到表头的表都在那儿，
它们要么是无关的表，要么是这次解析漏掉的东西，两种都得说一句。

**`template` 分支** —— 从知识包把行业包的 L3/L4 与指标全量取过来，
每行 `source: template`、`status: baseline`。
召回为空（`knowledgeRecall: none`）时**这条分支不成立**：没有一行可以标 `template`。

三份都没解析出行时，说出来并停下，不要拿模板顶上去凑一棵树。

## 3 · 任务一 · 识别冲突（C）

基线是**别人的树**——上一个项目的行业沉淀，或者客户自己维护了很久的一份表。
它和这个品牌一定有对不上的地方。逐行看，四类要标出来：

| 冲突 | 例子 |
|---|---|
| 这个品牌没有这条业务 | 基线里有"自有冰柜"，但这个品牌全渠道分销，不投冰柜 |
| 口径与这个项目的档案打架 | 基线的指标只有年度，档案要月度 |
| 说的是同一件事的两行 | 客户树的"电商投放"与行业包的"电商平台媒体"，留一行，另一行标重复 |
| 已经停做的 | 客户树里 2023 年的线下路演 |

标出来的行 `status: proposed`，`rationale` 写清楚冲突在哪、建议怎么处理。
**不许静默删行。** 基线里的每一行都是有人放进去的，剔掉它是一个要人签字的决定，
不是推导时顺手做掉的清理。剔除的裁决在确认那一步做。

## 4 · 任务二 · 往下扩展（C）

**每一条都必须落在已有的 L1/L2 下面。** 这两层在上一步就锁定了，这一步不新增。

三层的分工：

- **L3 = 一族一起动、一起规划的东西**（"品牌传播""渠道执行""促销优惠"）→ 数据需求的一个工作簿
- **L4 = 这一族里的一个具体杠杆或条件**（"TV""冰柜""PPI"）→ 工作簿里的一张表，也是模型变量挂载的地方
- **指标 = 这个 L4 怎么被量化** → 表里的一列。一个 L4 可以有多个候选

指标必须是**可测量的序列**，不是概念："KOL 投放金额（元，月度）"是指标，"KOL 效果"不是。
实在想不出可测量序列的 L4，**照样留在树里**：写一个你会去要的指标，
在 `rationale` 里说清楚难在哪。那正是访谈和数据需求存在的理由。

`dimension` 取自档案的模型范围三轴——这个指标真能按哪些轴报出来。只有全国口径的指标
照样是一行合法的行，它后面会被共享进每个模型，不是被丢掉。

**每个 L4 推荐一个主指标**（`primary: true`），这只是推荐，确认那一步才定。

### 每一行都要定聚合方式（`aggregation`）

客户给的数几乎不会正好是建模颗粒度：周数据要滚成月，省份要滚成大区，SKU 要滚成产品线。
**滚的时候怎么合并，是这个指标自己的属性，不是数据的属性**——所以它在这里定，
在指标被定义的同一刻定，而不是等数据到了再猜。

判断只有一句话：**把两行加起来，得到的数还有没有业务含义？**

| 有 → `sum` | 没有 → `average` |
|---|---|
| 花费、销量、订单量 | 铺货率 ND / WD、货架份额 |
| 曝光量、GRP、点击、KOL 发帖数 | PPI、售价、折扣率 |
| 已投放冰柜台数（当期新增） | 品牌力指数、心智份额、渗透率 |
| | 温度、降水量、消费者信心指数 |
| | 已投放冰柜台数（**存量口径**，见下） |

- **口径决定归属，名字不决定。** 同一个"已投放冰柜台数"，记的是当期新增就 `sum`，
  记的是期末存量就 `average`。拿不准就在 `rationale` 里写下你按哪种口径理解的，
  它会变成访谈的一个问题。
- **`weighted_average`** 用于按体量加权才正确的比率（例如跨地区的加权铺货率）。
  用了它，就要在 `rationale` 里说清权重是什么——说不清权重的加权平均是一个假精确。
- `min` / `max` 只用于定义本身就是极值的指标（"当月最高气温"）。
- 响应指标那一行同样要填。

**对比例类求和会造出一个没有意义的数，而模型拟合的就是那个数。** 这条在统计检验、
业务校验、模型输入三处都成立，所以它在这棵树上只定一次，下游各处都读这一份。

## 5 · 三种依据，各自留痕（M）

**新加的每一行都要说得出它站在什么上面。** 三种依据都作数，但它们的可信度不一样，
所以在树上必须分得开——分不开，人在确认时就没法把注意力放在最该看的那一批上。

| 依据 | `source` | `evidence` 必须写 |
|---|---|---|
| 知识库召回到的行业先例 | `template` | 包 id + 文件 + 命中的那一段，例 `food-bev/beverage :: factor-tree.yaml › 品牌传播` |
| 客户上传的树 | `upload` | 文件名 :: 表名 第 N 行（脚本给） |
| 客户给的报告材料 | `report` | 文件名 + 页码/章节 |
| 网络检索 | `websearch` | URL + 访问日期 + 一句原文摘录 |
| 你自己的行业知识 | `ai` | `模型先验（无外部出处）` + 一句为什么可信 |
| 访谈带来的 | `interview` | 原话（那是 `amend` 那一步的事） |
| 人在确认时当场加的 | `manual` | 人的原话（那是 `confirm` 那一步的事） |

关于**网络检索**：这是整套流程里唯一允许联网的一步。用它去补客户材料没覆盖、
知识库也没有的外部口径——品类大盘、竞品动作、平台规则变化。
每条网络依据都要在信息块的 `grounding` 里单独记一条：

```yaml
grounding:
  - { url: "https://example.com/report", accessed: "2026-08-08", chars: 4200, truncated: true }
```

没有 `accessed` 的网络引用会被验收挡下来——一个查不到日期的网页引用，
半年后没有人能确认它当时说的是什么。

关于**模型先验**：它可以落行，这是有价值的直觉，不该被丢掉。但它没有外部出处，
所以要在确认时被单独点出来给人重点看（工作簿的「来源」列会显示成"模型先验"）。
`rationale` 里那句"为什么可信"要具体：说"这个品类通常这么投"是没说，
说"月度模型里不控制温度，夏季投放会被系统性高估"才是说了。

**召回为空时没有一行可以是 `template`。** 这条比什么都硬。

## 6 · 填 L4 组级属性（C）

`groups` 里一个 L1/L2/L3/L4 路径一条。这些属性填在组上，不在每行重复，
和客户那张实盘表的写法一致（一个 L4 只填一次）。

| 属性 | 谁填、什么时候填 |
|---|---|
| `timeGrain` | 客户能给到的时间颗粒度。访谈里客户说"大部分数据能到周"，这里就写 `By year, by week` |
| `modelGrain` | 建模颗粒度，**以档案里的分析颗粒度为最低标准** |
| `drilldown` | 下钻颗粒度，例 `By Platform`。它是后面定位异常时往下钻的入口，能填就别空着 |
| `team` | 相关业务团队，例 `BI&CMI`。它是访谈数据类问题的出题依据，也是数据需求里这张表的负责人 |
| `dataSource` | 数据来源，例 `NielsenIQ`、`抖音 Ads 后台` |

ROI 与贡献度的参考区间**不进这棵树**。它们在知识库里按 `(L4, 指标)` 精确查，
本项目不算这两个数，也不在这里存第二份：
```bash
~/.local/bin/mmm tool knowledge.range --workspace <工作区> --l4 <L4> --indicator <指标>
```

### 五项数据准入标准（`admission`）

每一组都要填，这五条是**这一组数据够不够格进模型**的判断标准。它们有两个下游用途：
访谈时按它们出题，收到数之后按它们打分。标准写法（可按组调整，但不要留空、不要写"同上"）：

| 项 | 标准 |
|---|---|
| `completeness` 数据完整性 | 数据时间跨度多于两年，理想状态需要 3 年最优 |
| `accuracy` 数据准确性 | 可被业务团队确认 |
| `granularity` 数据颗粒度 | daily/weekly/monthly，不接受 yearly 数据 |
| `variability` 数据波动性 | 因子需要有变化才能估计回归系数 |
| `consistency` 数据一致性 | 数据统计逻辑一致且年与年数据可比 |

## 7 · 响应指标那一行（M）

档案的 `responseMetric` 在树里占**一行**：`role: response`，
**不挂在任何 L1–L4 下面**，不参与主指标唯一性，`primary` 不填。

它要在树里，是因为数据需求得把它单独要过来；它不能当因子，是因为模型会把因变量当自变量。
它照样要 `definition`、`unit`、`owner`——客户得知道该发什么过来。

## 8 · 统计增删幅度（M）

把 `meta.delta` 算出来：基线的 L4 个数、新增几个、剔除几个、比例、是否超过 0.2。

**超了不硬拦。** 超出通常说明基线和这个客户对不上，那是知识库该更新的信号，
不是把变更压回去的理由。做法是记下数字，确认时报一行"新增 N 条、剔除 M 条，相对基线 ±X%"。
基线为 0 时比例写 `0.0`，并在正文说明基线为空、比例无意义。

## 9 · 生成工作簿并交验收

```bash
~/.local/bin/mmm app workbook factor_tree -w <workspace>
```

工作簿是渲染出来的，**永远不要手改它**——改了下一次生成就没了，
而且验收时 `workbook_current` 会发现它和树对不上。

验收时会查：信息块完整、取材没有超出白名单（网络引用要带访问日期）、
树里有行且没有重复身份（`tree_has_rows`）、工作簿与树同步（`workbook_current`）。

做完说一句：**因子树已推导完成，共 N 行、其中 M 行待裁决，请验收 `factor-tree/derive`。**
然后停下。**不要顺手把自己刚推的树评审一遍**——确认这一步存在的意义就是换一双眼睛看。
