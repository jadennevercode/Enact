# 步骤 · factor-tree/confirm —— 逐行采纳或剔除，每个 L4 定一个主指标

每一行离开这一步时非 `accepted` 即 `rejected`，每个被采纳的 L4 下恰好一条主指标。
除此之外没有别的通过条件。

**类型：H。** 判断是人做的，你做的是**把判断需要的东西摆好**，以及把人的裁决如实写回去。
**拍板本身交给编排层**——它呈现问题、收下答复、记下裁决。

## 1 · 读（M）

只读 `artifacts/s1/factor-tree.yaml`、`artifacts/s1/factor-tree.xlsx`、
`artifacts/s1/knowledge-package.md`、`artifacts/s1/project-profile.yaml`。

**这一步不取新材料，也不联网。** 人是在你给他看的东西上做决定的，中途去捞一份新报告进来，
他批的就不是他看见的那份了。

## 2 · 把 Excel 摆到人面前（M）

**逐行确认在 Excel 上做。** 先确认工作簿是新的：

```bash
~/.local/bin/mmm app workbook factor_tree -w <workspace>
```

四张表，人要用的是前两张：`因子树`（全量，保持树的顺序）、`待裁决`（这一轮真正要判的行）、
`统计`（总量与增删幅度）、`说明`（每列什么意思）。

## 3 · 在对话里说三行，然后让人去看表（C）

顺序固定：先结论，再明细。**第一屏三行：**

1. 总量：N 行 · 待裁决 U · 已剔除 R
2. 增删幅度：新增 X 个 L4、剔除 Y 个，相对基线 ±Z%（超过参考幅度就直说超了，一并说明为什么）
3. 背书：`knowledgeRecall` 是哪个版本；是 `none` 就明说**这棵树没有行业背书**

**然后按 L3 分组走，不要一行一行地走完一个 200 行的文件。** 每组给：
这一组有哪些 L4、每个 L4 的候选指标、推荐哪一个当主指标、依据是什么。

**这五类必须单独点出来**，它们是人真正要看的东西：

| 点出来 | 为什么 |
|---|---|
| `source: ai`（模型先验）的行 | 它们没有外部出处。这批是最该被人过目的 |
| 推导时标出来的冲突行 | 基线里跟这个品牌对不上的行，剔还是留，是这一步的必答项 |
| 聚合方式是 `sum` 的比例类指标 | 一眼就能看出的错：铺货率、份额、指数求和会造出一个没有意义的数。按 L3 分组过一遍聚合方式那一列 |
| 所有候选指标都不可测量的 L4 | 要么留给访谈去解（推荐），要么剔掉并记原因 |
| 看着重复其实不同的两行 | 一个因子的两种度量，两行都留：一条主指标，一条备选 |
| 知识包里列在"什么没有行业先例"下的 | 这些行只有客户能确认 |

呈现的形式永远是**候选 + 推荐 + 每项后果 + 证据**，不是开放式问答。62 行的树不要问 62 次：
按组给整组建议，让人只改例外。

**人一条都没剔，要当面说出来。** 一次没剔任何东西的评审通常是没人真读的评审，
现在问的代价，比数据需求发出去之后再发现要小得多。

## 4 · 按裁决回写（M）

编排层把裁决交回来之后，逐条写进树：

| 写什么 | 怎么写 |
|---|---|
| `status` | `accepted` 或 `rejected`，**不留中间态** |
| `decidedBy` | 拍板的人 |
| `decidedAt` | 时间，带时区。知识回流要按时间线读这些变更 |
| `rationale` | 人给了理由就用人的话，别改写成你的话 |
| `primary` | 每个 L1–L4 路径下恰好一条被采纳的行为 `true`。人换了主指标，同一次编辑里把旧的清掉 |

**这一步只翻自己这一批的行**——`template`、`ai`、`websearch`、`report`、`upload` 来源的行。
访谈来的行不归这一步管。**已经被人手动改成 `rejected` 的行不会被翻回来**：
"批准"的意思是"接受我没有手动否掉的那些"，不是"全部通过"。

**顺手把四个字段补齐**：`definition`（要客户给什么，用客户听得懂的话）、`unit`、
`owner`（哪个团队握着它）、`aggregation`（往上滚的时候怎么合并）。
现在是唯一便宜的时刻——人就在这儿，答案在他脑子里。
一份 owner 空着的数据需求发到客户手上，回来的是谁看见谁填了一半的表；
一个聚合方式填错的指标，要到模型跑出一个说不通的系数时才会有人回头找。

人当场要加的行：`source: manual`、`status: accepted`、`decidedBy` 写人，`rationale` 用他的原话。

## 5 · 人要改 L1/L2 的时候（H）

L1/L2 是锁定的，但**人可以改**——只是在改之前必须知道自己在动什么。
不要直接照做，也不要直接拒绝，先把代价摆出来：

```
【要确认】你要把「渠道成交驱动」下面新开一个 L2「即时零售」
这一层动了会连带：
  · 数据需求的分册会重排 —— L3 是一册工作簿，它的上一层变了，整套册子重新分
  · 跨项目不可比 —— L1/L2 是全行业共用的一层，这个项目改了，就和别的项目对不上了
  · 已经基于旧骨架做过的判断要重新看一遍

  A. 就在现有的「渠道/终端营销」下面加 L3「即时零售」（推荐）—— 不动骨架，同样装得下
  B. 确实要新开这个 L2 —— 我改，并记一笔谁在什么时候因为什么改的
```

人坚持要改，就改。改完三件事一件不能少：`decidedBy` / `decidedAt` 写在受影响的行上、
把新的 L1/L2 同步回 `knowledge-package.md` 的骨架表（否则知识包会继续声称一个已经不成立的骨架）、
在变更账本上记一笔。

## 6 · 变更账本

**这一步不直接写账本。** 账本只能由编排层追加（`state.py record-change`，见
`../../shared/change-ledger.md`）——你的任务是把每一条增删改的理由、来源、证据
在呈现裁决时说清楚，编排层拿到裁决之后据此记账，挂在 `factor-tree/confirm` 这次确认上。

## 7 · 收尾（M）

在 `meta.reviewedAt` 写上确认时间——**不要动 `meta.step` 和 `meta.generated`**，
那两个记的是"谁产出了这份文件"，重新盖章会让推导那一步的取材记录对不上。

重新生成工作簿：

```bash
~/.local/bin/mmm app workbook factor_tree -w <workspace>
```

验收时会查：树里有行且没有重复身份（`tree_has_rows`——人当场加的行也要过这一关）、
没有未裁决的行（`no_undecided_rows`）、每个 L4 恰好一条主指标（`primary_indicator_per_l4`）、
工作簿与树同步（`workbook_current`）、人的裁决已记录。

做完说一句：**因子树已逐行裁决完，采纳 A 行、剔除 R 行，请验收 `factor-tree/confirm`。**

还有行没裁决就不要往下走，也不要绕过去解释。把它们逐条摆到人面前，
这正是这道确认存在的全部理由。

## 之后

树从这里开始冻结，直到访谈带着改动回来（`factor-tree/amend`）。
绕过那一步直接改树，会让所有已经作数的判断描述一个不存在的东西。
