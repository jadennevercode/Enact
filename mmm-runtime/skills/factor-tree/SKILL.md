# 因子树

这门生意受什么影响，每个影响因子拿什么衡量。**这个 Skill 只产出这一份交付物**，
但它是整个项目的主数据——数据需求按它生成，数据质量按它打分，最后的模型输入按它装配。

**开始前：** 读 `../../shared/conventions.md` 定位工作区，读项目档案拿到行业、颗粒度和模型范围。

## 五个步骤

| 步骤 | 类型 | 做什么 | 详细 |
|---|---|---|---|
| `materials` | H | 按项目行业匹配知识包，收客户报告与自有因子树，定这棵树从哪起底 | `references/materials.md` |
| `knowledge` | C | 召回可引用的行业先例，以及**什么没有行业先例** | `references/knowledge.md` |
| `derive` | C | 识别基线与这个品牌的冲突；在锁定的 L1/L2 上扩展 L3/L4 与候选指标 | `references/derive.md` |
| `confirm` | H | 在 Excel 上逐行采纳或剔除，每个 L4 定一个主指标 | `references/confirm.md` |
| `amend` | H | 访谈之后，把访谈带来的改动写回树里 | `references/apply-proposals.md` |

另有 `inspect`（`references/inspect.md`）：回答关于这棵树的问题——覆盖了什么、某一行从哪来、
为什么被剔除。它只读不写。

`amend` 要等访谈消化完才能做。因子树在访谈之前是**做完了但还没定**，这不是卡住，
这是设计如此：客户的话本来就该改这棵树。

## 第 0 步 · 澄清（先读完再问）

先读完项目档案、材料索引、知识包。**已经写在里面的不要问**——尤其行业和起底方式，
它们一个来自 scoping、一个由材料索引推出来，都不该在这里重新问一遍。

| 澄清点 | 什么时候必须问 | 推荐 |
|---|---|---|
| 行业和客户自有的树两头都空 | 匹配不到知识包，`inputs/client-factor-tree/` 也是空的 | 停下来，先补行业或请客户给一棵树 |
| 响应指标那一行怎么进树 | 每次 | 单独一行，不挂在任何分组下 |
| 要动 L1/L2 | 人提出来时 | 先给不动骨架的替代方案，再让人拍板 |
| 增删超出参考幅度怎么办 | 增删明显超出 10%–20% 时 | 记下来在确认时讲，不硬拦 |

## 三条硬规矩

**没有行业先例时，不许有一行标成来自知识库。** 召回是空的，就说是空的——
`knowledgeRecall: none`，并且在确认时明确告诉人"这棵树没有行业背书"。
假装有先例比没有先例危险。

**每一行都要说得出它站在什么上面。** 知识库召回、客户上传的树、客户材料、网络检索、
你自己的行业知识——五种依据都作数，但要分得开：`source` 标类别，`evidence` 落到具体出处
（包与行 / 文件与页码 / URL 与访问日期 / 原话）。分不开，人在确认时就没法把注意力
放在最该看的那一批——没有外部出处的那一批——上面。

**响应指标不是因子。** 它单独一行，标成响应，不挂在任何 L1–L4 分组下，不参与主指标的
唯一性检查。它要在树里，是因为数据需求得去把它要过来；它不能当因子，是因为模型会把
因变量当自变量。

## 三层的分工

| 层 | 是什么 | 在数据需求里是 |
|---|---|---|
| L1 / L2 | 全行业通用的骨架，**锁定** | — |
| L3 | 一族一起动、一起规划的东西（"品牌传播""渠道执行""促销优惠"） | 一个工作簿 |
| L4 | 这一族里的一个具体杠杆或条件（"TV""冰柜""PPI"） | 工作簿里的一张表 |
| 指标 | L4 怎么被量化。一个 L4 可以有多个候选，**只能有一个主指标** | 表里的一列 |

L1/L2 在 `materials` 那一步随行业包（或客户上传的树）定下来，之后推导不再新增。
**人可以改它**，但改之前要看清代价：数据需求的分册会重排，跨项目的可比性会丢失，
已经基于旧骨架做过的判断要重看一遍。所以做法是先给一个不动骨架的替代方案，
人仍然坚持就改，并且记清楚是谁、什么时候、为什么改的。

## 增删幅度

基线带出来的 L3/L4 与指标默认全量保留，允许 10%–20% 的增删。超出这个幅度**不要硬拦**——
它通常说明基线和这个客户对不上，那是知识库该更新的信号。做法是：记下数字，
在确认时报一行"新增 N 条、剔除 M 条，相对基线 ±X%"，让人知道自己在批什么。

真正的硬要求是：**每一条增删都有理由、都有出处**，并且都写进变更账本
（`../../shared/change-ledger.md`）。

## 取材范围

| 步骤 | 只能读 |
|---|---|
| materials | `inputs/industry-reference/**`、`inputs/client-factor-tree/**`、项目档案、`mmm.yaml` |
| knowledge | 项目档案、材料索引、上面两个输入目录、行业知识召回 |
| derive | 知识包、材料索引、项目档案、现有的树、上面两个输入目录、**网络检索** |
| confirm | 树、工作簿、知识包、项目档案 |
| amend | 访谈的改动建议、访谈纪要、树 |

**只有 `derive` 可以联网。** 确认与访谈回写那两步在人已经看过的东西上做判断，
中途去捞新材料，人批的就不是他看见的那份了。网络引用要记 URL 和访问日期，两样缺一不可。

## 产出

- `artifacts/s1/factor-tree.yaml` —— 树本身，照 `templates/factor-tree.yaml` 填
- `artifacts/s1/factor-tree.xlsx` —— **给人看的形态，逐行确认就在它上面做**。由工作簿应用生成：
  `~/.local/bin/mmm app workbook factor_tree -w <workspace>`，**没人手改它**
- `artifacts/s1/materials-index.md`、`artifacts/s1/knowledge-package.md` —— 中间产物，
  不作为交付物示人，但参与取材记录

做完任何一步，交给编排层验收。**你不自己关确认。**

## 说话的规矩

1. 先说结论，再说依据，不铺垫。
2. 只说业务语言：说「确认」「检查项」「交付物」，不说 gate、predicate、artifact。
3. 每步三句话内交代：做了什么 / 结果是什么 / 需要你什么。
4. 要人拍板时永远给选择题：候选 + 推荐 + 每项后果。62 行的树不要 62 次提问——
   按 L3 分组呈现，给出整组建议，让人改例外。
5. 数字要报出处。说不出出处的数字就不说。
6. 拿不准就问。"大致""可能""建议进一步确认"通常是该问没问留下的痕迹。
