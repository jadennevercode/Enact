# 记一条反馈

用户纠正你的时候，当场记一条。这一步不属于收尾——它贯穿整个项目，
而且不只这个 Skill 做：任何 Skill 在自己的工作里被纠正，都记在同一本账上。

## 为什么要当场记

用户的纠正是顺口说的，说在别的事情中间，一句就过去了。等到收尾再回忆，
回忆出来的已经不是原话，而是我们希望他说过的话。两者差别不大的时候正是最危险的时候——
照着后者改出来的 Skill，下次会被同一个人以同样的理由再纠正一次。

## 什么该记

| 情形 | 类型 | 例子 |
|---|---|---|
| 用户说做法不对 | `correction` | 「谁让你直接改因子树的，先给我看清单」 |
| 用户表达一贯偏好 | `habit` | 「以后先给我表格再给结论」 |
| 少了一步、少问了一句 | `missing` | 「你没问我地区口径就往下走了」 |
| 说法让人误解 | `wording` | 「别跟我说什么判定式，说人话」 |

还有一种不出声的信号也要记：**因为流程被误解而返工**。用户没有开口批评，
但你重做了一遍，说明有一步的说明不够清楚——那就是一条 `missing`。

## 什么不该记在这里

- **客户业务口径的判断**（加了哪个因子、某个指标怎么定义）→ 变更账本，
  写入方式见 `../../../shared/change-ledger.md`。
- **工具报错、脚本崩溃** → 那是仓库的问题，不是 Skill 的说明写得不好。
- **一次性的数据决定**（这个月的数据用哪一版）→ 变更账本。

分界线是一句话：**换个客户还成立吗？** 成立的是做法，记在这里。

## 怎么记

```bash
~/.local/bin/mmm script state record-feedback <工作区> \
  --skill scoping --kind habit \
  --quote "以后先给我表格再给结论" \
  --expected "澄清项先出表格，结论写在表格后面" \
  --step project-profile/clarify \
  --where skills/scoping/references/clarify.md
```

| 参数 | 写什么 |
|---|---|
| `--skill` | 哪个 Skill 的行为被纠正。这是修的单位，写不准就写你当时正在执行的那个 |
| `--kind` | `correction` · `habit` · `missing` · `wording` |
| `--quote` | **用户的原话**，不许转述。不能空 |
| `--expected` | 他期望的做法，一句话说清。不能空 |
| `--step` | `<交付物>/<步骤>`；说不准就留空 |
| `--where` | 你猜该改哪个文件。只是线索，收尾时会重新判断 |

`--quote` 和 `--expected` 都不能空，写入时直接拒绝。理由写在
`../../../shared/skill-feedback.md`：没有原话的是转述，没有期望的改不成任何东西。

## 记完说一句话

记完告诉用户你记下了什么，一句：

> 记下了：「以后先给我表格再给结论」——收尾复盘时会拿出来问你要不要改进 scoping。

不要展开讨论要不要改、怎么改。**记录是观察，不是决定。**
用户当场说"现在就改"，那也不是这本账的事——现在能改的现在改，
这条记录留着，是为了收尾时判断这件事该不该固化进 Skill。
