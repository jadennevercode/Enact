# Skill 优化

把用户教过我们的做法，固化进 Skill 文件本身。

## 一条一张卡

```
【改进 2/5】scoping 澄清那一步的呈现顺序
  原话：「以后先给我表格再给结论」（2026-08-03，共 2 次）
  期望：澄清项先出表格，结论写在表格后面
  提议改：skills/scoping/references/clarify.md 的呈现段，加一条"先表后文"
  影响：所有项目的项目档案澄清环节立即改变；这一条不影响产出物内容，只影响呈现顺序
  ○ 改   ○ 不改
```

**影响面那一行必须自己写，不能省。** 用户看到的是一句小小的措辞调整，
实际发生的是所有后续项目的行为改变——这两件事在卡片上看起来一样，只有你知道不一样。

出现过两次以上的，在原话后面标出次数：反复出现是最强的信号，
它说明这不是某一天的临时偏好。

## 改哪里

| 反馈的性质 | 改哪个文件 |
|---|---|
| 措辞、语气、说法让人误解 | 那个 Skill 里说这句话的地方——多半在 `references/` |
| 少了一步、少问了一句 | 那一步对应的 `references/` 细则文件 |
| 呈现顺序、给不给选择题 | 同上；`SKILL.md` 只在这条是这个 Skill 的主干规矩时才动 |
| 跨多个 Skill 的同一种毛病 | `shared/conventions.md`——影响面最大，卡片上要单独说明 |
| 用户想要一个新的产出物 | **不在这里改**。那是加交付物，回去走流程定义 |

**细节往下推，`SKILL.md` 保持薄。** 入口文件有行数上限，不是排版讲究：
它每次都被整份读进上下文，长到一定程度，后面的规矩就等于没写。

## 改完必须做的三件事

1. **跑一次静态检查：**

   ```bash
   ~/.local/bin/mmm script check_suite
   ```

   **结果原样报出来**，通过多少条、失败哪几条，不要挑着说。
   失败了就改到过为止；改不动就把这条改进退回去，如实说明为什么退。

2. **把裁决填进复盘报告**，连同实际改了哪个文件的哪一段。
   人批准的是提议，落地的是 diff，两者不一定一样——不一样的地方要写出来。

3. **告诉用户改动在 git 里**，diff 就是复核面。**提交留给用户**，
   不要替他提交：这次改的是所有项目共用的插件，最后一道人眼要留着。

## 什么不该改

- **用户没批准的。** 哪怕你觉得那条反馈明显对。
- **只有情绪没有期望的抱怨。** 「这做得真差」改不成任何东西。
  记在报告里，说明为什么没法落地，请他补一句具体期望。
- **和现有硬规矩冲突的。** 有一条规矩挡着，先说清楚那条规矩为什么在那儿，
  再问要不要连它一起改。悄悄绕开一条写着理由的规矩，是这套东西最容易坏掉的方式。
- **这次项目的一次性变通。** 为一个客户的特殊情况改所有项目的做法，
  下一个项目会莫名其妙地继承一条它不需要的规矩。
