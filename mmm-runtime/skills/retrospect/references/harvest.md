# 汇总候选

收尾时做。先确认项目真的到了终点——没到就只汇报现状，不落库，理由见下。

## 先跑一次汇总

```bash
~/.local/bin/mmm script state promote <工作区>
```

它把两路原料一次打出来：变更账本按类型和来源归拢、因子树里被剔除的行、
反馈账本按 Skill 归拢。**它只汇总，不判断，也不写任何东西。**
判断是你的事，拍板是人的事。

两本账都是空的，说明这个项目从头到尾没人记过——如实说出来，
不要临时从产出物里编一份出来充数。

## 知识沉淀这一路

原料有三处，前两处 `promote` 已经打出来了，第三处要自己去看：

1. **变更账本**里的每一条：加了什么、删了什么、为什么、谁拍的板。
2. **因子树里 `status: rejected` 的行**——剔除的理由同样是经验，
   下一个同行业项目会想知道这条为什么在这里不成立。
3. **OLS 预验证里落在行业区间之外、但客户确认属实的因子**——
   这说明区间本身该改，而不是这个项目特殊。

### 三个问题，全是"是"才提名

- **换个客户还成立吗？** 只对这家客户成立的，留在项目账本，不进知识库。
- **它推翻了知识库现在的说法吗？** 是的话，提名的是「修订」而不是「新增」，
  要写清楚原来说什么、现在为什么改。
- **有依据吗？** 依据是这个项目的哪次确认、哪份数据、哪段访谈。说不出来的不提名。

**行业条目只能进对应行业的目录。** 一个饮料项目的投资回报区间不能写进护肤品的包里——
这不是政策，是目录结构决定的。现有的饮料包源文件自己就写着区间来自一个真实项目的案例，
不是行业标准，把它当案例读。

## Skill 优化这一路

反馈账本按 Skill 归拢之后：

| 信号 | 强度 | 怎么处理 |
|---|---|---|
| 同一个 Skill 上两条以上相似反馈 | 强 | 一定提名。反复出现说明说明文字本身有洞 |
| 单条明确的纠正，带原话和期望 | 中 | 提名，卡片上注明只有一次 |
| 跨多个 Skill 的同一种毛病 | 强 | 提名改 `shared/conventions.md`，影响面在卡片上说明 |
| 只有情绪没有期望的抱怨 | 弱 | 不提名。记下来但说明为什么没法改 |

**同一件事在两个 Skill 上各出现一次，是跨 Skill 信号，不是两条孤例。**
归拢时按毛病归，不只按 Skill 归。

## 写出复盘报告草稿

照 `../templates/retrospective.md` 填，两张表都填满，**裁决列一律留空**——
那是下一步问人的，不是这一步猜的。元信息块声明 `step: retrospective/harvest`，
读过的每份材料都写进 grounding。

草稿写完不要停下来等人看，直接进入下一步逐条问：
一份没有裁决的复盘报告，对用户来说只是一份更长的清单。

## 项目没到终点怎么办

只汇报现状，说清楚三件事：现在账上有多少条、哪几条看起来会是候选、
为什么现在不落库。**中途的结论可能被后面的检验推翻**——
一条已经写进知识库的错结论，会被之后每一个同行业项目当成行业先例读出来，
而没有人会回头核对它当初是在项目的哪个阶段写下的。
