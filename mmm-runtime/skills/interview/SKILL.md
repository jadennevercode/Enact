# 访谈

因子树上还剩下的问题，只有客户能回答。这个 Skill 有**五个能力**，它们是并列的，
不是一条流水线——**用哪个取决于你手上有什么材料，不取决于走到了哪一步**。

**开始前：** 读 `../../shared/conventions.md` 定位工作区，读项目档案与已确认的因子树。

## 五个能力

| # | 能力 | 手上要有什么才能用 | 产出（真相） | 产出（给人看） |
|---|---|---|---|---|
| 1 | **起草提纲** `interview/outline` | 已确认的因子树 + 组织架构或关键受访人名单 | `outline.md` | `outline.docx` |
| 2 | **先答一版** `interview/pre-answer` | 提纲 | `pre-answers.md` | `pre-answers.docx` |
| 3 | **整理纪要** `interview/minutes` | 逐字稿或原始纪要 | `minutes-<来源>.md` | `minutes-<来源>.docx` |
| 4 | **提因子改动** `interview/digest` | 纪要 + 因子树 | `proposals-<来源>.yaml` | 校正版因子树工作簿 |
| 5 | **提洞察与假设** `interview/insights` | 纪要 | `insights.yaml` `assumptions.yaml` | `insights.docx` |

**能力 2 和 5 是可选的**（流程定义里标了 `optional`）：用不用得上取决于项目，不做也不拦着
交付物走完。能力 3 不依赖能力 1 和 2——**一份逐字稿不需要先有提纲才能整理**，
没有提纲时纪要就不挂题号，如实说明即可。

**唯一的交付物级前提是因子树已确认。** 数据题是从树上逐行派生的，改动建议是对着树提的，
树没定之前这两件事做出来都是错的。树一确认，五个能力任意顺序、任意子集。

**Word 是渲染出来的视图，Markdown 与 YAML 才是真相。** Word 里改的东西下次重新生成就没了。
生成方式：`~/.local/bin/mmm app report <报告名> --workspace <工作区>`，报告名是
`interview-outline` / `interview-pre-answers` / `interview-minutes` / `interview-insights`。
**这台机器要装 Node**，缺了就报错，不降级成 Markdown——一份"因为没装 Node 所以变成
Markdown"的交付物，收件人不会知道它本该是别的样子。

## 澄清（先读完再问）

先读完因子树、项目档案、知识包、材料索引、`inputs/org-structure/`。
**这些文件里已经写了的，一个字都不要问。**

| 澄清点 | 什么时候必须问 | 推荐项 |
|---|---|---|
| 访谈对象名单与档期 | `inputs/org-structure/` 是空的时候。有组织架构就只问档期 | 按三层全量出，客户自己删 |
| 有没有独立的数据团队 | 每次。数据题的去处只有两种：一个数据团队，或分散到各业务团队 | 有就单列一个数据团队 |
| 数据类问题问到多细 | 因子行数 × 4 明显超过一场会能问完的量时 | 全量出题，按预答置信度标重点 |
| 纪要以什么形式回来 | 要用能力 3 之前。**这里不做录音转写** | 文字纪要或逐字稿 |
| 没覆盖到的题怎么算 | 每次 | 逐条列出 + 为什么 + 下一步 |

细则与话术见 `references/clarify.md`。问不到人时按推荐项走，在提纲的 `meta.assumed`
里写清楚是哪几条、为什么——假设要登记出来，不能沉默滑过去。

## 每个能力怎么做

| 能力 | 里面分几步 | 细则 |
|---|---|---|
| 1 · 起草提纲 | 召回题库（M）→ 排访谈对象（M）→ 业务题（C）→ **数据题（M，不许调模型）** | `references/outline.md` |
| 2 · 先答一版 | 逐题出一版带置信度与依据；数据题用固定模板句；可联网，但只对业务题 | `references/pre-answer.md` |
| 3 · 整理纪要 | 一份原稿一个文件，保留原话，段标签挂题号，必写「没覆盖到」 | `references/minutes.md` |
| 4 · 提因子改动 | 一份纪要一次消化，每条改动带逐字原话；人裁决后归档校正版工作簿 | `references/proposals.md` |
| 5 · 提洞察与假设 | 只出 gap 与 conflict 两类洞察；关键假设一问一答，每条挂一个建模决策 | `references/insights.md` |

做完一个能力就交：说一句「交付物已写好，请验收 `interview/<步骤>`」，交给编排层。
**你不自己收尾**——检查与状态流转是编排层的事，做完就交，不自评通过。

## 七条硬规矩

**题号 `Q<n>` 是跨文件主键。** 提纲、预答、纪要按它对齐，全文唯一。题号重复，材料会被
静默合并成一条——文件看起来是齐的，其实少了一题。

**每题挂到具体因子行上**：题干行末尾写 `[factor: f-0041]`。挂行 id 不挂路径字符串——
路径会因为改名而失配。一道决定不了树上任何一行的问题，是寒暄，不是提纲条目。

**数据题是算出来的，不是想出来的。** 每个 `status: accepted` 的因子行（含响应行）按
路径去重后生成同样的四问，题干前缀是它的因子路径。四问原文在
`knowledge/methodology/interview-framework.yaml` 的 `dataSubQuestions`，**逐字不改**。
题数必须等于 4 × 去重后的行数，写进 `counts.dataQuestions`——`data_questions_complete`
会对着树重算一遍，对不上就报出漏了哪几条路径。这一段的体量远大于业务题——
一次真实交付是 42 道业务题对 168 道数据题。

**没依据就说没依据。** 预答的置信度落 `none`，写"没有依据"，不要编一句像样的。
一条自信的错预答比空白危险：访谈者以为已经知道了，就不再听那个答案。
**联网查来的最高只能到 `low`，而且数据题一律不许联网**——可得性、颗粒度、拆分维度、
口径是关于这个客户内部系统的事实，网上搜到的一定是编的。

**提纲上的每一题都要有下落。** 答了就在纪要的段标签里挂题号，没答就列进
「## 没覆盖到」。两处都没有，就是这一题在提纲和纪要之间消失了。

**空是一个发现。** 没覆盖到的题、没带来任何改动的纪要、一条洞察都没有——都要写下来
并说明原因。一份看起来完整的空交付物能过审，因为里面没有可反对的东西。

**这里不动因子树。** 改动建议是文件，由因子树的 `amend` 步骤逐条采纳或驳回。
**也不做录音转写**——拿到音频就明说，请人先转成文字。

## 说话的规矩

1. 先说结论，再说依据，不铺垫。
2. 只说业务语言：说「确认」「检查项」「交付物」，不说 gate、predicate、artifact。
3. 每步三句话内交代：做了什么 / 结果是什么 / 需要你什么。
4. 要人拍板时永远给选择题：候选 + 推荐 + 每项后果，不给开放式提问。
5. 数字要报出处。说不出出处的数字就不说。
6. 拿不准就问。"大致""可能""建议进一步确认"通常是该问没问留下的痕迹。
