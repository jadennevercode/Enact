# 能力 1 · `interview/outline` —— 起草访谈提纲

类型 **A**（数据题那一段是 **M**）。产出 `artifacts/s1/interview/outline.md`，
照 `../templates/outline.md` 填，再渲染成客户拿得走的 Word。
一份提纲同时是三样东西：客户排会的日程表、访谈者的问题清单、数据团队的填报清单。

**前提两样：** 已确认的因子树（数据题从它逐行派生），加上组织架构或关键受访人名单
（决定提纲分几节）。名单先看 `inputs/org-structure/`，那里有东西就不要再问一遍。

---

## 0 · 先召回，不要凭空写（M）

两份知识文件在插件里，出题前先读：

| 文件 | 里面有什么 | 怎么用 |
|---|---|---|
| `knowledge/methodology/interview-framework.yaml` | 四层 × 时长、三类问题标签、**数据类问题的固定四问**、参考角色切法 | 跨行业通用，每次都读 |
| `knowledge/industry/<行业锚点>/interview.yaml` | 该行业真实问出口的题库（饮料包 94 题，按层级/角色/标签分好） | 按项目档案的 `industry` 锚点找；命中就召回，写进 `knowledgeRecall` |

**召回到了就照抄题干**，只把 `{brand}` 占位符换成本项目的品牌，并按客户的实际组织重排角色。
题库里标了 `flag: untagged-note` 的条目是源表里的内部笔记，**出提纲时过滤掉**。

**召回不到就诚实说没有**：`knowledgeRecall: none`，业务题全部从这个项目自己的材料里出，
并在交付时明确告诉人"这份提纲没有行业题库背书"。假装有先例比没有先例危险。

## 1 · 排访谈对象（M）

先分组，再出题。**没有分组的提纲排不了会**，而排会是这份文件的第一用途。

**先读 `inputs/org-structure/`。** 客户给过组织架构图或关键受访人名单的，按它分组，
只需要问档期。那里是空的才走澄清 1。因子树的 `owner` / `team` 字段和材料索引里的
组织信息只能给出一个草稿——它们记的是"谁提出了这个因子"，不是"谁能回答关于它的问题"。

分组方式：**层级 × 团队**，一组一节。层级只有四种，时长是查表得来的，不是估的：

| 层级 | 谁 | 只有他们知道的事 | 时长 |
|---|---|---|---|
| 高层 | 总经理、品牌负责人 | 痛点与生意战略、投资策略这三年怎么变、什么不在桌面上 | 60 分钟 |
| 管理层 | 市场、销售、财务 | 预算实际怎么分、年中怎么调、数据大致拿不拿得到 | 60 分钟 |
| 执行层 | 媒介、活动、电商、渠道、市场洞察 | 数字是什么意思、数据在哪个系统、去年哪里断过 | 90 分钟 |
| 数据团队 | 数据/IT 对接人 | 每个指标能不能给、给到什么颗粒度、口径是什么 | 90 分钟 |

「数据团队」这一层是从因子树派生出来的，客户的组织图上不一定有这个名字。
澄清 2 说没有独立数据团队时，把数据题按 L3 拆进对应的执行层团队。

每节的抬头写四件事：层级、团队、时长、题数。参与人和档期留空给客户填。

## 2 · 业务类问题（C）

五个出题来源，按这个顺序找：

1. **靠惯例留下的因子行** —— `rationale` 很薄的 accepted 行，树是按行业常规留的，不是按证据。
2. **没有可测指标的 L4** —— 访谈是查清"到底有没有这个数、谁手里有"的地方。
3. **知识包里"没有行业先例"的那一段。**
4. **材料索引里文档没覆盖的部分。**
5. **项目档案的未决问题。**

**不要问文档已经回答的问题。** 访谈很贵，而且客户认得出自己的 PPT 被念了一遍。

问题分三类，按层级取用：业务现状理解、关键业务问题与期望、分析/数据颗粒度与范围。
问该层的人只有他们能答的事——问媒介采购负责人战略，得到的是意见；
问他一次跨屏活动的花费怎么记账，得到的是"这个因子到底可不可测"。

## 3 · 数据类问题（M —— 这一步不许调模型）

数据题是**算出来的，不是想出来的**。这一段没有模型的份：给定同一棵树，任何人跑出来的
数据题必须一模一样，否则收数时就没有一份可以机械核对的清单。

对每一个 `status: accepted` 的因子行（**包含响应行**），按
`L1 › L2 › L3 › L4 › 指标` 组成的路径去重，每条路径生成**同样的四问**，逐字照抄
（原文以 `knowledge/methodology/interview-framework.yaml` 的 `dataSubQuestions` 为准）。

> **只取 `accepted`，不要按平台的 `{baseline, accepted}` 去改。** 平台在树确认之前就
> 出题，所以它要连 baseline 一起取。这里不同：提纲依赖 `factor-tree/confirm`，而那道门
> 的 `no_undecided_rows` 保证过关之后树上只剩 `accepted` 和 `rejected`——把 `baseline`
> 加回来只会捞到零行，或者在树还没确认时捞到一堆还没定的行。

```
1. 该指标当前是否可获得？主要来源系统 / 供应商是什么？
2. 可提供的最小时间颗粒度与可回溯的历史区间是什么（周度 / 月度，起止时间）？
3. 可按哪些业务维度拆分（品牌 / 区域 / 渠道 / 平台），各维度的颗粒度如何？
4. 数据口径是否已与业务现实对齐？是否存在已知缺口、口径调整或可比性问题？
```

这四问就是数据准入四个维度的提问形态：**可得性 / 颗粒度 / 拆分维度 / 口径**，
和数据需求工作簿要客户填的东西一一对应。

题干格式：`[路径] 四问之一`，行末挂它探的那一行。

```markdown
- Q43 [消费者需求驱动 › 品牌广告 › 品牌媒体 › Digital Display › 曝光量] 该指标当前是否可获得？主要来源系统 / 供应商是什么？ [factor: f-0041]
```

四条不能破的规矩：

- **不改措辞、不合并、不裁剪。** 四问是数据准入的四个维度（可得性 / 颗粒度 / 拆分维度 /
  口径），少问一条，收数时就少一个能对账的地方。
- **题数是算出来的**：数据题数 = 4 × 去重后的行数，写进 `counts.dataQuestions`。
  对不上就是漏了行，回去重数，不要改数字。`data_questions_complete` 会对着树重算一遍，
  并把漏掉的那几条路径原样报出来——这一段是提纲里唯一可以被机械核对的部分。
- **一行一题号**，接着业务题往下编，全文唯一。
- **实盘量级心里有数**：42 个业务题对 168 个数据题。这份提纲的体量在数据题上，
  这也说明访谈的主要产出是**数据可得性**，不是业务洞见。

数据题多到一场会问不完是常态。做法不是删题，是**标重点**：预答那一步会给每题一个置信度，
`none` 和 `low` 的就是现场必问的，其余随提纲交给数据团队书面回填。

## 4 · 写文件

照 `../templates/outline.md`。校验会盯住四件事：

- 每一条 `- Q<n>` 行都带 `[factor: f-xxxx]`；
- 题号全文唯一（预答和纪要都按它对齐，重号会让材料静默合并）；
- 数据题按因子树全覆盖，题数与 `counts.dataQuestions` 都是真的；
- 取材只来自因子树、知识包、项目档案、材料索引、组织架构和插件里的访谈知识文件，
  且如实记字数。

一道问题同时探几行因子：挂**它能定下来的那一行**。一道定不了任何一行的问题，
是寒暄，不是提纲条目。

## 5 · 渲染成 Word

客户拿到手的是 Word，不是 Markdown：

```bash
~/.local/bin/mmm app report interview-outline --workspace <工作区>
```

Markdown 是真相，Word 是照它渲染出来的视图，指纹记在 Word 的文档属性里，
`doc_current` 会比对。**改内容改 Markdown，不要改 Word**——下次重新生成就覆盖掉了。
这台机器没装 Node 就会报错并说清楚怎么装；不要退回去只交一份 Markdown。

## 6 · 交付

告诉编排层：**访谈提纲已写好，请验收 `interview/outline`。** 同时报三个数：
多少个访谈对象、多少道业务题、多少道数据题。

要一份客户能直接排会的表格：`~/.local/bin/mmm app workbook interview --workspace <工作区>`。
