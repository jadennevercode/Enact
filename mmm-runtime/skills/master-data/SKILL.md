# 模型输入

收口。整个数据阶段决定的一切变成一张表，和一个对"**模型建在什么之上**"的回答——
因为这个问题曾经被三个地方各答一遍，在同一个案例上给出三个不同的数：7、5、8。
**这个 Skill 只产出这一份交付物。** 锁定即 runtime 全流程结束；建模与报告不在范围内。

**开始前：** 读 `../../shared/conventions.md` 定位工作区，确认 OLS 预验证已确认。
数据阶段的工具从统一入口进：`~/.local/bin/mmm tool <id> …`。

## 硬规矩

**每个数都来自一次真实的工具运行。** 漏斗计数、收口计数、表里的每一个值来自
`data/derived/selection.json` 与逐对象的表，产出文档要声明它读的是哪份计算结果。**逐字照抄：
不四舍五入、不换单位、不心算、不重算。** 漏斗计数尤其如此——那是客户会背回来的数字。

**过滤是物理的，而且只有一个来源：账本。** 表里带的是账本报告为已采纳的指标，
跑在人确认过的响应上，限制在人勾选过的变量里。
**在这一步重新推导上述任何一项，就是这张表与人真正签过字的那次拟合产生分歧的原因。**

**响应在已采纳集合里，而且它没有账本行。** 没有任何一层裁决过它——驱动解释它，没人筛它——
所以每个按账本过滤的地方都会悄悄把它滤掉。导出的"模型输入"曾经就这样少了因变量本身，
而其它检查全都通过了。

**全国行跟着留下它的那个模型走，不跟并集走。** 渠道类型为空的行属于每一个模型，
拿全部对象排除集的并集去筛它看起来是安全方向，其实不是：曾经一个渠道用某个驱动拟合出 43% 的贡献，
而主数据表把它删了，因为另外两个渠道否掉了它。**按"品牌 + 渠道类型"切看起来等价、其实不是**——
那样会丢掉每一条全国行和每一条竞品行，而那恰好是模型真正拟合用的共享行。

**一个因子行只要任一供给它的数据键被采纳即为采纳，且只计一次。** 两个兄弟因子被钉到同一个
数据键时，所有权只归一个，另一个报"未建模"——两边都计会让参考表比收口多认一个采纳因子。

**收口的五种归宿是故意分开的：** 采用 / 部分采用 / 否决 / 未建模 / **从未拿到数据**。
"从未拿到数据"不是"否决"——后者意味着有人做了判断。混在一起会告诉客户他的因子被否了，
而事实是根本没人把数据发过来，两种情况的补救办法完全不同。
**五种归宿之和必须等于因子树的活跃行数**，对不上就报告并停下，不猜。

**建模编号是这一步相对上游数据集唯一的新增物。** 没有它，这张表只是上游数据集的一个子集，
建模阶段的贡献分解只能靠指标名字符串回溯。见 `references/numbering.md`。

**锁定要冻结快照。** 锁定的是"建模将要训练在其上的那张表"。只记一条批准而不冻结
已解析的选择（响应、变量集、排除集、参数），上游任何一次重跑都会让建模训练在
一张与人签过字的表不同的表上。

## 说话的规矩

1. 先说结论，再说依据，不铺垫。
2. 只说业务语言：说「确认」「检查项」「交付物」「计算结果」，不说 gate、predicate、artifact。
3. 每步三句话内交代：做了什么 / 结果是什么 / 需要你什么。
4. 要人拍板时永远给选择题：候选 + 推荐 + 每项后果，不给开放式提问。
5. 数字要报出处。说不出出处的数字就不说。
6. 拿不准就问。"大致""可能""建议进一步确认"通常是该问没问留下的痕迹。
