# 模型输入的澄清点

**先读完裁决表、账本和因子树再问。** 已经在里面的不要问。一次全部问完。

---

## 1 · 时间颗粒度（缺失）

**什么时候问：** 项目档案没写，或者数据支撑不了档案写的那个。

```
【澄清 1/5】这张表按什么颗粒度出
  A. 月度（推荐，也是最低颗粒度）
  B. 年度 —— 数据太短时的退路。
     代价：季节性被彻底抹掉，建模阶段拿不回来。
```

## 2 · 编号规则的分组依据（缺失，每次必问）

**为什么非问不可：** 编号一旦发给建模阶段就成了引用键，改不动。

变量编号是整数，指标编号是 `<变量编号>.<序号>`。要定的是**同一个变量下挂哪些指标**：

```
【澄清 2/5】建模编号按什么分组
  A. 按 L4 因子分组（推荐）—— 一个 L4 一个变量编号，它名下的每个入模指标一个指标编号。
     贡献分解可以直接回溯到具体的 L4 因子，这正是编号存在的理由。
  B. 按数据源分组 —— 便于追溯数据从哪来。
     代价：同一个因子的指标可能散在几个变量下，分解回溯要多跳一层。
  C. 按英文机器名分组 —— 与真实交付物的形态最接近。
     代价：机器名本身还没定，等于把这个问题推给下一个澄清点。
```

真实交付物里出现过 `1.1` 和 `32.1.1` 两种深度，说明层级不止两级。
**本 runtime 目前只产出两级**（`<变量>.<指标>`）：第三级要等到一个变量下的指标本身还要再分组
才有意义，而这条流程还产不出那种结构。要三级就说清楚第三级分的是什么，并作为一次显式的扩展。

## 3 · 异常处置 `cap` 在这张表里生不生效（越界）

**什么时候问：** 有已被客户接受的 `cap` 卡片。

```
【澄清 3/5】表里的响应列是原值还是缩尾值
  A. 不生效，表里是原值（推荐，也是平台现状）—— 缩尾只作用于拟合。
     代价：表和拟合用的响应序列不完全一致，必须在表上标注。
  B. 生效，表里是缩尾后的值 —— 表与拟合完全一致。
     代价：交出去的表里，那几个月的销量不是客户账上的数。
```

**无论选哪种，表上必须标注响应列是原值还是缩尾值。** 建模阶段拿到的响应序列不同，
而这件事从表面上看不出来。

## 4 · 某因子全部候选指标都不达标时怎么交代（缺失）

平台明规则：**不纳入，并在交付说明中预警该因子缺数据。**

```
【澄清 4/5】<因子名> 的全部候选指标都不达标
  A. 不纳入 + 交付说明预警（推荐）—— 建模阶段的结论不覆盖这个因子，而且这件事被写在明处。
  B. 回流找替代指标 —— 模型不会对这块生意失语；代价是要重开上游，工期后拖。
```

选 A 时确认预警写在哪：交付说明**和**因子树收口表都要有，还是只写交付说明。
推荐两处都有——收口表是给团队看的，交付说明是给客户看的。

## 5 · 英文机器名谁来命名（岔路）

真实交付物里有这一列（例 `NAB_All_Channel_Offtake_Value`）。

```
【澄清 5/5】变量的英文机器名怎么定
  A. 按规则自动生成（推荐）—— 由因子路径生成；生成不出可读名字的（例如全中文）落到 Var<n>。
     代价：客户可能不认这个名字。
  B. 人指定 —— 名字客户认，但要一份命名登记，而且每次新增指标都要有人补。
```

选 B 时**当前引擎不支持命名登记**：名字仍由规则生成，人指定的名字要记在项目的口径备忘里，
并在交付时说明"表上的机器名是自动生成的，客户命名待引擎支持"。不要假装它已经生效。
