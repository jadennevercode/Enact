# 步骤 plan —— 定这次用哪些数据、切成几个模型（H）

```bash
~/.local/bin/mmm tool ols.plan --workspace <工作区>
```

写出 `artifacts/s2/ols-plan.yaml`，照 `../templates/ols-plan.yaml` 填。

## 工具只测量，不替人选

它把每一种切法都算一遍，给出决定所需的全部事实，然后停下。
**哪种粒度对，是生意上的判断**——两个产品是不是一回事、某个渠道值不值得单独看——
算术定不了，所以选哪个记成人的裁决，理由必填。

| 切法 | 是什么 | 典型适用 |
|---|---|---|
| `total` | 不切，全体数据一个模型 | 月数少、只要总量结论 |
| `by-brand` | 按品牌 | 多品牌、渠道结构相近 |
| `by-channel` | 按渠道类型 | 单品牌、渠道行为差异大 |
| `channel-x-brand` | 渠道 × 品牌 | 默认推荐 |

候选受项目档案的模型范围矩阵约束，不在范围里的维度不出现。

## 要看的那两个数

```
可负担驱动数 = max(1, 月数 − 控制项数 − 1 − 10)
按住几个     = max(0, 存活驱动数 − 可负担驱动数)
```

**切得越细，能回答的问题越多，每个模型能识别的驱动越少。** 这就是全部的权衡。
`heldOutCount` 逐格报，不只报总数——一个格子饿着、其余宽裕，看总数是看不出来的。

**推荐的是「可行的最细那一档」，不是「按住最少的那一档」。**
后一条规则错在 `totalHeldOut` 跨切法不可比：4 个模型各按住 2 个（共 10）
并不比 1 个模型按住 4 个更差，因为前者回答 4 个问题、后者只回答 1 个。
真实项目上照那条规则会推荐 `total`，而 `total` 恰恰是唯一对任何单个渠道都说不出话的切法。

## 时间窗与排除时段

`window` 默认取发布数据集的全窗。`excludedPeriods` 是**删数据**，每段必须写理由。

**它和业务校验的异常窗口在同一段上只能选一个。**
异常窗口是加一列 0/1 把这段建进模型，排除时段是把这段行删掉；
两个一起用，等于在已经不存在的月份上估一个控制项。

## 模型对象怎么编号

`*` 表示「这一维不切」：`*::*` 全体、`*::某品牌` 不分渠道、`MT::某品牌` 渠道 × 品牌。
选这种写法而不是加方案前缀，是因为**同一个格子必须只有一个 id**——
变更账本、配置、以及人已经签过的确认都在逐字引用它，两种拼法会把它们全部悬空。

## 空也是结论

没有响应、或者有响应但没有驱动的格子会被跳过，逐个点名写进 `skippedObjects`，连同原因。
被跳过的格子是交付物的一部分，不是省略。
