# 开一道人工确认

规矩本身在 `../../shared/gate-protocol.md`，这里是怎么做。

## 呈现：四段，按这个顺序

1. **在定什么** —— 流程定义里那句问题，用人话说一遍。
2. **依据** —— 证据文件，加一份能据以决策的摘要：各状态多少条、这次变了什么、
   跟上次比新增了什么。不要让人自己去翻文件。
3. **还没定的** —— 每一条处在中间状态的行，逐条列出。**这才是确认的正文**：
   规矩二要求这些必须全部有结论才能过。
4. **选项** —— 每个候选写清楚**后果**，标出推荐项和推荐理由。

还有没定的行时，**不要把"通过"设成默认推荐**——先把那些行解决掉。

行数多的时候（几十行的因子树、上百个指标的评分卡）**按组呈现**：给整组的建议，
让人改例外。62 行不要问 62 次。

## 落裁决

```bash
~/.local/bin/mmm script state decide <工作区> <交付物>/<步骤> <裁决> \
  --evidence <证据路径> --note "<理由>"
```

只有 `approve`、`signoff`、`accept` 能关闭确认；`rework`、`reject`、`reopen` 只记录不关闭。

**裁决必须先落日志再跑验收**——验收里的检查会一直失败到日志里有这一行为止，
这个顺序不是偏好。

驳回会按流程定义里写的退回目标，把那一步和它的下游退回未完成。退回目标有时跨交付物：
OLS 结果反常识退回的是业务校验，不是重新拟合——数字是症状，怎么读数据才是病因。

## 记账

**这次确认改动了因子或指标的，同时落一笔变更账本**（`../../shared/change-ledger.md`）：

```bash
~/.local/bin/mmm script state record-change <工作区> \
  --what add --target factor --subject "<改了什么>" \
  --why "<为什么>" --source interview --evidence <出处> \
  --who <谁拍的板> --gate <交付物>/<步骤>
```

`--why` 和 `--who` 都不许空，写入时直接拒绝：一条没有理由的变更，一年后没人敢用也没人敢删；
一条没有署名的变更，就是一个悄悄变成项目决定的 AI 提案。

这份账本是项目收尾时 `promote` 唯一的原料。不记，这个项目学到的东西就随目录一起躺着，
下一个同行业项目从零开始，把同样的弯路再走一遍。

## 客户签核类的确认

客户不直接操作这套东西，签核由顾问在线下拿到之后代录。`--who` 写**实际签的人**，
`--note` 写凭证在哪（会议纪要、邮件、签字扫描件）。代录不留凭证的签核，等于没有签核。
