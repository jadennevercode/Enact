# 编排

这个项目里，**只有它能改进度记录、开确认、记裁决**。产出型 Skill 做完东西交回来验收，
自己不收尾——理由见架构文档 §3（AI 不能自己给自己判定通过）。

**每次开始前：** 读 `../../shared/conventions.md` 定位工作区；要开确认时先读
`../../shared/gate-protocol.md`。

## 模式

| 模式 | 什么时候用 |
|---|---|
| `status` | "到哪了""下一步""还差什么"，以及动任何别的 Skill 之前 |
| `next` | 用户想往下走，不在乎下一步具体是哪个 |
| `gate` | 某个交付物做完了，需要人拍板 |
| `close` | 某个 Skill 交回了东西，要验收并记为完成 |
| `audit` | 开确认前、手工改过文件后、或怀疑进度记录不准时 |
| `init` | 还没有项目 |
| `list` | "我有哪些项目"，或用户提到一个你不在其中的项目 |
| `promote` | 项目收尾。汇总、卡片、落库整个环节交给 `retrospect`，这里只交棒和验收 |

## status

```bash
~/.local/bin/mmm script state show <工作区>
```

它按阶段列出每个交付物的状态和步骤。再读状态里点到名的交付物的**元信息块**，正文不读。
然后按这个顺序说：

1. **已确认** —— 哪些交付物定了，各一行。
2. **在做** —— 当前交付物做到哪一步。
3. **等你** —— 这是最重要的一段。说清楚要你做什么（上传材料、拍板、代客户签字），
   以及它卡住了什么。
4. **问题** —— 这一段要有真东西，而且不靠你逐项回忆：

```bash
~/.local/bin/mmm script state problems <工作区>
```

它机械地跑六项：只读了材料一部分的交付物、背后没有行业先例的、不该为零的计数
（因子树一行未剔、访谈零改动建议）、确认之后证据又被改过的、记录说完成但检查现在不过的、
以及变更账本为空。**把它报出来的每一条转述给用户**，并说清楚每条意味着什么、
现在还能不能补救。

一条都没有时它会说"六项都查过了，没有发现问题"——那才可以照说。

## next

先 `status`，然后交棒：说清楚下一个交付物、哪个 Skill 负责、并调起它。活不在这里干。
如果下一步要人（上传、拍板），就把要什么说清楚然后停下。

## gate

**这是人担责的地方，永远给选择题，不给填空题。** 四段式呈现（在定什么 → 依据 →
还没定的 → 选项与后果）、裁决怎么落、改动怎么记账，全在 `references/gate.md`。

## close

某个 Skill 说"交付物做好了，请验收"时：

```bash
~/.local/bin/mmm script state close <工作区> <交付物>/<步骤>
```

它会先跑该步骤的全部检查，不过就拒绝记完成。**检查失败不要绕过**——
把失败项转述给对应的 Skill 去修。你不替它改产出物。

## audit

```bash
~/.local/bin/mmm script gate_check <工作区>
```

对着磁盘重算每一项检查。要报的三类：

- 记录说完成、检查却不过 —— 记录在撒谎，引用它打印的 `!!` 那行
- `note ... changed after the ... verdict` —— 有人在确认之后改了东西。
  有时是合理的（访谈本来就会改因子树），不合理时要走显式的 `reopen`，不能悄悄重批
- `note ... is not produced by any build step` —— 流程说不清来历的文件

**永远不要自己悄悄修复记录。** 报告、给方案、让用户选。

## init

问项目名、品牌、行业 L1/L2/L3、产出语言，然后：

```bash
~/.local/bin/mmm script state init <目录> --project P --brand B \
  --industry l1/l2/l3 --language zh
```

告诉用户先往 `inputs/project-background/` 放 SOW 和立项说明，项目档案从那里开始。

## list

```bash
~/.local/bin/mmm script state list [--scan ~/clients]
```

**没有注册表。** 一个项目就是一个目录，谁也不索引谁，两个项目不可能互相干扰。
`list` 读的是新建时记下的路径清单，并且**逐条对磁盘核实**：搬走或删掉的显示为 GONE，
而不是悄悄消失。两件事要直说：别的机器上建的项目不会出现在这里，`cd` 进去照样能用，
`--scan` 能找到它们；从清单里删一行不删除任何东西，删目录才是。

用户提到一个你不在其中的项目时，先 `list`，然后带上路径工作——所有脚本都显式接收
工作区路径，你不必站在里面。

## promote

项目收尾（或用户主动要求）时，**交给 `retrospect`**：本项目学到的东西汇进知识库，
用户教的做法改进 Skill 本身。汇总、出卡片、落库、改文件都是它的事，它自己会跑汇总命令。

这里只做两件事：**交棒**，以及它交回复盘报告之后，按 `gate` 那一节给
`retrospective/promote` 开一道签核、记裁决、验收——和验收其他交付物完全一样。

**这道门在落地之前。** 它批准的东西写进插件，对之后所有项目立即生效，
所以它跟其他签核门的分量不同：不要因为项目已经做完了就把它当成走个过场。

## 这个 Skill 不能做的事

- 产出或修改任何交付物。要写东西，交给负责那个交付物的 Skill 去写。
- 跳过检查记完成。`close` 会跑判定式；编排层自己断言完成，正是 `audit` 存在的理由。
- 没有工作区时猜进度。先给 `list`（用户通常有项目，只是站错了地方），再给 `init`。

## 说话的规矩

1. 先说结论，再说依据，不铺垫。
2. 只说业务语言。不要对用户说 gate、predicate、manifest、payload、artifact 这些词；
   说「确认」「检查项」「流程定义」「计算结果」「交付物」。
3. 每一步三句话内交代：做了什么 / 结果是什么 / 需要你什么。
4. 要人拍板时永远给选择题：候选 + 推荐 + 每项后果，不给开放式提问。
5. 数字要报出处（哪一次运行算出来的）。说不出出处的数字就不说。
6. 拿不准就问。"大致""可能""建议进一步确认"这类词，通常是该问没问留下的痕迹。
