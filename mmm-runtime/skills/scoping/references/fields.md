# 项目档案的字段

模板在 `../templates/project-profile.yaml`。这里说每个字段为什么存在。

**验收时怎么查这份档案，写在 `shared/manifests/checks.yaml`** —— 看 `profile_complete`、
`profile_locked`、`scope_advisories`、`granularity_matches_profile` 这几条。这里不复述。

以前这份文档自己抄过一份，抄完就不再跟着实现走：它声称档案有六项要查的字段，
实际跑起来只有两项，半年没人发现。所以那份说明只留一处，别处引用它。

## 谁在读这份档案

| 字段 | 谁读它 |
|---|---|
| `timeGranularity` | 数据需求工作簿的第一列；数据阶段的目标表结构要与它一致 |
| `modelScope` 的轴名 | 数据需求工作簿的维度列名 |
| `timeWindow` | 数据需求工作簿 README 的期间行；数据发布后回头对账实际拿到多少 |
| `responseMetric` | 因子树里 `role: response` 那一行，一字不改地抄 |
| `brand` · `industry` | 知识包锚定、因子树召回 |
| 其余字段 | 人。它们进 Word，不进代码 |

分清这两类很重要：给机器用的那几个字段错了，是后面每一层都跟着错；
给人看的字段错了，是评审时被指出来。

## 为什么响应指标住在档案里

它是 Y，不是因子。放在档案里，是因为数据需求要同时做两件事：把它**单独**建一张表要过来，
以及把它**排除**出因子表。这两件事都要读档案，所以它不该住在别处。

## 范围矩阵为什么分成两块写

`modelScope` 是轴和轴上的取值，`scopeRows` 是真正被选中的格子。

分开写，是为了让人一眼看见"叉乘全集有多少格"和"实际做多少格"的差。合成一块写，
这个差就没了，而它恰恰是最该被看见的东西——多出来的格子意味着多出来的收数和多出来的模型。

## 三轴为什么是固定的

`Brand × Channel × Geo`，轴名不可改。这不是风格偏好，是 2026-07-16 客户会上定的
（平台代码里编号 BIZ-001）：**地区必须是干净的地理维度**，线上平台不能顶替地区，
也不能并进地区里。

混装的后果很具体：`地区和平台` 这样一列，线下装省市分组、线上装平台名，于是
"华东" 和 "天猫" 成了同一层的东西。之后任何一次"我们覆盖了几个地区"都是错的，
而错的方式是看不出来的——数出来的数字永远合理。

轴名确实要改的项目（比如生意根本不按地区分），改动要走澄清、记进 `assumptions`，
并在 Word 里写清楚为什么与默认不同。

## scopeAdvisories 是提醒，不是约束

三条规模建议——1 条产品线或产品线组、渠道 ≤4、地区分组 ≤6——的理由是**工期**，
客户原话是「为了聚焦项目的时效」。不是模型质量。

所以超了**不要自己收窄范围**。如实记下实际值，在拿给人确认时把多出来的收数量和
建模工作量说清楚，让客户决定。客户完全可能愿意为了覆盖面接受更长的工期，那是客户的决定。

## sourceOrigin：档案是抽出来的还是问出来的

`uploaded` 表示从 SOW 与立项简报里抽取的；`elicited` 表示这个项目没有正式 SOW，
范围是通过问答一轮轮推导出来的。

两者都是正当的来路，但它们的可靠程度不一样，所以要写出来——`elicited` 的档案里，
`assumptions` 通常长得多，而读档案的人有权知道这一点。

## assumptions 与 openQuestions 的区别

- `assumptions` —— **已经定了**，但不是客户亲口说的，是按推荐项走的。每条都要能回答
  "谁在什么时候按什么理由定的"。
- `openQuestions` —— **还没定**，留给访谈或数据需求去解决。

拍板时这两块要分开报：假设是可以带着往下走的，未决问题会决定下一步做什么。
`openQuestions` 非空时，不要把"通过"报成默认推荐。

## metadata/granularity.yaml

档案锁定的同时，把时间颗粒度与范围三轴另写一份到 `metadata/granularity.yaml`。
数据阶段的清洗读的是这一份，不读档案。

内容就是档案里那三样的副本：`timeGranularity`、`modelScope`、`scopeRows`。
它存在的理由是数据阶段不该为了拿一个颗粒度去读一份满是叙述的交付物；
它必须与档案一致，这一点有检查在盯着。
