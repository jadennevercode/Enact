# 项目档案的澄清点

**先读完 `inputs/project-background/**` 再问。** SOW 里已经写清楚的，不要问。

每条的形式固定：先说读到了什么、缺的是什么，再给候选 + 推荐 + 每项的后果。
一次全部问完，按影响面排序，不要挤牙膏。

---

## 1 · 建模时间颗粒度

**什么时候问：** SOW 只写了汇报节奏（"月度汇报"），没有说建模用什么颗粒度。这两件事经常被混在一起。

**为什么非问不可：** 它是全链路的契约——数据需求表的第一列、因子树每行的默认颗粒度、
后面数据面板的时间轴，全都读它。定完再改，等于整个项目重来。

```
【澄清 1/4】建模时间颗粒度
读到：SOW 写了"按月向管理层汇报"，但没说模型本身按什么颗粒度建。

  A. 月度（推荐）—— 与绝大多数客户的收数和汇报节奏一致。
     代价：周内的促销脉冲会被平滑掉，看不出"哪一周起量"。
  B. 周度 —— 能抓住促销和上新的脉冲。
     代价：要求客户按周提供**所有**因子数据，收数难度上一个台阶；
           媒体以外的因子（铺货、价格、竞品）通常给不出周度。
  C. 年度 —— 只有多年趋势型的委托才成立。
     代价：样本量通常不足以识别出各因子的系数。
```

## 2 · 模型范围三轴取什么值

**什么时候问：** 地区分组几乎总是缺的；或者 SOW 把"平台"和"地区"混成了一列。

**为什么非问不可：** 范围表的每一行后面都要落一个模型。列了数据支撑不了的组合，
就是若干个空模型。

```
【澄清 2/4】模型范围
读到：SOW 列了 4 个渠道和 1 条产品线，但地区只写了"全国"。

  A. 按 SOW 字面列（推荐）—— 只收 SOW 明确说在范围内的组合。
     代价：范围可能偏窄，后面要补要走一次重新确认。
  B. 三轴叉乘取全集 —— 覆盖最全。
     代价：会把客户从没承诺给数据的格子带进来，到收数时才发现要不到。
```

这一条要额外单独确认两件事：

- **产品线排除了哪些 SKU。** 实际项目里常见"除某某系列外全部"这种写法，
  排除项必须写进档案，否则收数时才发现口径对不上。
- **地区和平台不是一回事。** 线上平台（天猫、京东、抖音…）是渠道内部的细分，
  不是地区。地区维度里出现平台名，就要在这里问清楚。

## 3 · 响应指标口径

**什么时候问：** SOW 一般只写"提升销量"，不写口径。

**为什么非问不可：** Y 定错，整个模型答的是另一个问题。而且数据需求要把 Y 单独成表、
并且**排除出因子表**——不定下来，这一步无从做起。

```
【澄清 3/4】模型要解释的是哪个数
读到：SOW 说目标是"提升销量"，没有说是出货还是售出。

  A. 售出量 sell-out volume（推荐）—— 消费者实际买走的量，MMM 的常规响应。
  B. 售出金额 sell-out value —— 关心收入而非销量时用。
     代价：价格变动会混进来，价格因子的系数更难解释。
  C. 出货量 sell-in —— 只有客户确实只能给出货数据时才选。
     代价：模型解释的是渠道压货，不是消费者需求。
```

## 4 · 建模时间窗

**什么时候问：** SOW 只写了项目周期，没写数据要回溯多久。

```
【澄清 4/4】数据回溯多久
  A. 三年（推荐）—— 季节性有三个完整周期，趋势项和季节项能分开。
  B. 两年 —— 数据准入的下限。
     代价：季节只有两个周期，季节项与趋势项容易纠缠在一起。
  C. 客户能给多少算多少 —— 不推荐。
     代价：等于把风险推到收完数之后，那时改口径的代价最大。
```

## 问不到人的时候

按推荐项走，在档案的 `assumptions` 里写清楚：问题、采用的答案、`assumed: true`、
以及为什么这样假设。然后在交付时**主动说出来**："这四项里有两项没问到人，
我按推荐走了，分别是……"

假设本身不是问题，沉默才是。
