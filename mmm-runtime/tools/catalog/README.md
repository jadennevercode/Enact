# 工具目录

这个目录是 25 个计算工具的对外表达。**一个工具一份卡**，文件名就是工具的 id。
Skill 要用某个工具时引它的卡，不要在自己的文档里另写一段散文描述——
两份描述迟早会不一致，而不一致的那一份不会有人发现。

卡片格式见任意一份 `.yaml`：`id / kind / purpose / when / inputs / output / stdout / example / notes`。
其中 `output.shape` 是最重要的一节：它是字段级的，读完应该能直接写出消费这份产物的代码。

`scripts/check_suite.py` 的「工具目录」分节会核对目录卡与已注册工具一一对应——
注册了没有卡、或有卡没注册，都算失败。

## 统一调用契约

每个工具都长同一个样子，没有例外：

```
~/.local/bin/mmm tool <id> --workspace <工作区> [--task <步骤>] [--out <路径>] [工具自己的参数]
```

三件事每次运行都会发生，三件都是承重的：

1. **产物落盘**——结果写到 `--out`（不给就用这个工具的默认落点，见各卡的 `output.path`）。
   计算出来的数字只能由工具写，Skill 不写。
2. **摘要有界**——屏幕上只打决策需要的东西：计数、极值、以及需要人裁决的那几行。
   永远不打整张表。这是「两万三千行涌进上下文」的答案。
3. **一行运行记录**——写进 `state/tool-runs.jsonl`，连同产物的 sha256。
   一个交付物里的数字如果在这里没有对应的一行，它就不是算出来的。
   依据见 `shared/numbers-provenance.md`。

还有一条铁律：**空结果也要带原因**。零个异常、一条指标都没剩、一批交付合并出零行——
每一种都会把原因写进产物并判失败或明说，绝不会输出一个看起来完成了的空成功。

未知参数是错误不是耸肩：拼错的 `--sources` 如果被默默忽略掉，
它会在错误的输入上产出一份自信满满的结果。

查看用法：

```
~/.local/bin/mmm tool list                 全部工具
~/.local/bin/mmm tool <id> --explain       这个工具做什么，以及它的实现源码
```

## 按类型分组

`kind` 是徽章不是层级——目录是一张平表。同一个工具会被好几个步骤调用，
按类型分组只是方便找。

### schema — 结构先于数据

| id | 一句话 |
|---|---|
| `schema.init` | 铺出目标表结构的初稿，供人改成这家客户的样子 |
| `schema.check` | 判定这份结构自己讲不讲得通：必填列、取值清单、身份列、颗粒度对不对得上项目档案 |

### data — 客户文件 → 清洗 → 发布长表

| id | 一句话 |
|---|---|
| `data.extract` | 把一个客户文件原样拆成表，一个字不改 |
| `data.profile` | 给每一列出体检单——起草清洗脚本时唯一允许看的依据 |
| `data.cluster-enum` | 找出同一列里其实是同一个东西的不同写法，提出合并建议（只是建议） |
| `data.clean` | 在只读沙箱里执行清洗脚本，产出目标结构的长表 |
| `data.conform` | 判定清洗结果合不合声明过的结构 |
| `data.reconcile` | 判定清洗结果还是不是原来那批数据——行数、数值合计、时间跨度 |
| `data.publish` | 把通过检查的交付合并成项目唯一的建模长表 |
| `data.claim` | 把发布出来的每个指标挂到它供给的那一行因子上，两头挂不上的都点出来 |
| `data.factor-map` | 把因子树每一行判成：有数据供给 / 明确不做 / 还没定 |

### ledger — 每个指标的归宿

| id | 一句话 |
|---|---|
| `ledger.derive` | 算出每个指标在六层筛选里的最终归宿，以及最后进模型的那一份名单 |

### quality / statistical — 打分

| id | 一句话 |
|---|---|
| `quality.scorecard` | 数据质量：10 项子检查 → 4 个维度 → 总分是四者相乘 |
| `stat.scorecard` | 统计筛查：变异度 × 相关性 × 共线性，一项不合格总分归零 |

### validation — 业务校验

| id | 一句话 |
|---|---|
| `validation.series` | 把每个因子按月汇总成曲线，和响应放在一起 |
| `validation.facts` | 从曲线里算出叙述必须引用的那些数——解读只能引这里的数 |
| `validation.anomalies` | 找出曲线自己打破自己规律的月份，做成待裁决的卡片 |

### model — OLS 预验证

| id | 一句话 |
|---|---|
| `ols.propose` | 提出这次预验证怎么建：响应、变量、参数，全部算出来 |
| `ols.fit` | 按渠道 × 产品各拟合一个模型，给出拟合优度与每个驱动的贡献度、投资回报 |
| `ols.scorecard` | 逐因子对照行业区间给出接受/否掉的建议，并钉住人已经下过的判定 |

### knowledge — 查基准

| id | 一句话 |
|---|---|
| `knowledge.range` | 查一个因子的行业投资回报与贡献度区间，精确匹配，查不到就是「这项检查没跑」 |

### assemble / export / render — 成品

| id | 一句话 |
|---|---|
| `master.assemble` | 用活到最后的指标装配每个模型对象的特征表 |
| `master.funnel` | 给因子树收口：每一行的下场，以及在哪一层定的 |
| `export.xlsx` | 把模型输入导成工作簿，一个模型对象一个工作表 |
| `render.html` | 把一份算好的曲线结果渲染成自带一切的 HTML 页面 |

> `export.xlsx` 与 `render.html` 按架构文档 §2.3 属于组装线错位成了工具，
> 后续会迁去 App 层。在那之前它们仍按上面的统一契约调用，卡片也照常维护。
