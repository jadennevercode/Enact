# 通用约定

每个 Skill 开工前先读这份。它规定活儿在哪里干、进度怎么记、什么算做完。

## 1 · 工作区

**一个客户项目就是一个目录。** 没有数据库，没有服务器，这个目录就是全部。

**目录树的权威版本在 `shared/workspace-layout.md`**，这里不重复——同一份目录清单抄两份，
第一次改动就会打架。一行概括：

```
<工作区>/
├── mmm.yaml       身份：项目 · 品牌 · 行业 · 产出语言
├── state/         进度 progress.yaml · 决策日志 decisions.log · 运行记录 tool-runs.jsonl
├── metadata/      契约：目标表结构、取值范围、颗粒度、变更账本
├── inputs/        人提供的原始材料，按类别分。任何工具都不许往这里写。
├── data/          原始 → 清洗 → 发布 → 派生。工具写的，可以重算。
├── artifacts/     分阶段的交付物
└── exports/       要送出门的副本
```

**怎么找到它。** 工作区就是含有 `mmm.yaml` 的那个目录：当前目录，或者用户在请求里点名的那个。
`state.py list` 列出这台机器知道的所有项目——用户提到一个你不在其中的项目时用它，
因为所有脚本都显式接收工作区路径，你不必站在里面。

一个都没有时，**只有编排 Skill 能新建**。别的 Skill 停下来说明情况——
一个自己造项目目录的 Skill，已经把审计线索弄丢了。

**版本。** `workspaceVersion: 3` 是上面这个形状，进度按交付物记。老工作区用
`scripts/migrate_workspace.py` 平移过来，那是改名不是重写。

## 2 · state/progress.yaml

```yaml
steps:
  project-profile/intake: { status: done, produced: ["inputs/project-background/sow.md"] }
  project-profile/build:
    status: done
    produced: ["artifacts/s1/project-profile.yaml"]
    gate: { verdict: approve, at: "2026-08-08T10:04:00+08:00" }
  factor-tree/materials: { status: pending }
```

**只记进度。** 项目是谁在 `mmm.yaml` 里，不放这儿：身份不变，进度天天变，
放一起会导致每完成一步就重写一次行业锚点。

`status` 只有 `pending` 和 `done` 两个值。`done` 要求该步骤 `verify:` 里的每一条检查都通过。

**交付物的状态不在这个文件里**——它是从步骤推导出来的，六态见
`shared/deliverable-states.md`。记下来的状态会和磁盘分叉，推导出来的不会。

**这个文件是索引，不是事实。** 它指向的文件才是事实。编排层的 `audit` 之所以要对着磁盘
重算每一条检查，就是因为记录可能声称"完成"，而那份产出物压根没写、或者后来被改成不合格了。

## 3 · state/decisions.log

只能追加，一次人工裁决一行，竖线分隔，方便直接 grep：

```
2026-08-08T10:04:00+08:00 | project-profile/build | approve | 张三 | artifacts/s1/project-profile.yaml | 档案与 SOW 一致，月度颗粒度确认
```

字段：时间 · 确认点 · 裁决 · 谁 · 证据路径 · 说明。**任何一行都不许改、不许删。**
撤回一次确认的做法是追加一条 `reopen`，然后重新走一遍裁决。

## 4 · 流程定义

`shared/manifests/deliverables.yaml` 就是流程：11 个交付物、各自的构建步骤、
谁产出、依赖谁、取材范围、检查项、人工确认点、退回目标。

**走流程要读它，不要凭记忆。** 你正要做的事在里面没有对应条目，说明你在即兴发挥——停下来。

## 5 · 调用工具

**依赖是放开的。** 这套东西一度规定业务理解阶段只用标准库，理由是"顾问的笔记本上
只有一个裸 Python"。这条规定的代价比它省下的多：为了绕开它，`shared/lib/xlsx.py`
手写了一个 Excel 写出器，而给客户看的 Word 档案根本写不出来。现在该用什么库就用什么库，
**代价是环境要先备齐**——`~/.local/bin/mmm doctor` 会把这台机器缺什么、
怎么装，一次报清楚。

缺件的正确反应是报错说清楚，不是降级产出一份形状不一样的东西。一份"因为没装 Node
所以变成 Markdown"的交付物，收件人不会知道它本该是别的样子。

**入口只有一个：`~/.local/bin/mmm`。** 计算、成品、脚本都从它进：

```bash
~/.local/bin/mmm tool data.profile --workspace <工作区> --step published-dataset/clean --asset media-spend
~/.local/bin/mmm app workbook factor_tree --workspace <工作区>
~/.local/bin/mmm script state list
```

**为什么写全路径而不是 `mmm`。** PATH 是从启动进程那里继承来的，服务器上可能根本不含
用户的 bin 目录；而 `$HOME` 一定是真的。所以这个拼法在任何机器上都成立，你不需要先确认
什么。**也不要给它起别名**（`MMM=…` 那种写法）：shell 不展开变量里的 `~`，别名一定跑不起来。

**不要自己拼插件路径，也不要 `cd` 到插件里去。** runtime 装在哪、该用哪个解释器、
以模块方式跑一条生产线需要什么，这三件都是**这台机器的属性，不是方法的属性**，入口自己知道。
想看它解析到了哪个 runtime、依据是什么：`~/.local/bin/mmm where`。

**不要退回到裸 `python3` 去跑数据阶段的工具。** 系统解释器既没有引擎也没有它锁定的
数值库版本，一定失败——而失败是对的，因为另一种结果是在一套与基准向量不同的数值栈上出数。
入口没装好时 `mmm where` 会说清楚为什么，装它的是 `enact mmm setup`。

**脚本是例外**，它们自己处理：`gate_check.py` 和 `state.py` 在引擎不可导入时会自动切到
插件的虚拟环境重跑（要指定切到哪个解释器就设 `$MMM_ENGINE_INTERPRETER`）。否则一台装好
引擎的机器会把所有数据阶段的检查都报成失败，读起来像项目出了问题，其实只是路径问题。

每个工具的用途、参数、产出结构、示例，在 `tools/catalog/<工具id>.yaml` 里——
**引用目录卡，不要另写一套说明**。

## 6 · 开工前的固定动作

1. 定位工作区（§1）。没有就停下，先给 `~/.local/bin/mmm script state list`。
2. 读 `mmm.yaml`（项目是谁）、`state/progress.yaml`（做到哪了）、以及流程定义里你这一步的条目。
3. 依赖都完成了吗？没有就说清楚缺哪一步然后停下。**这一条对"被描述匹配自动触发"同样适用**——
   自动触发不能绕过人工确认。
4. **只读**流程定义里你这一步 `reads:` 列出的路径。那是唯一权威的取材范围，
   Skill 自己文档里的表只是方便查阅的副本。裁剪了什么要如实记下来（§7）。
5. **澄清**：把该问的一次问完（架构文档 §4.0）。已经写在输入里的不许问。

## 7 · 诚实截断

**没有字符上限。** 曾经有一条 60,000 字的取材预算，超了就检查不过。它挡下的从来不是
"读太多"，而是"读完了但不敢如实写"——一个上限只要存在，申报的数字就有了往小了写的理由，
而申报的数字正是这套东西唯一能验的东西。所以上限撤掉，如实申报留下。

`grounding` 要记：读了哪些文件、各保留了多少字、有没有截断。**永远不要静默裁剪。**
一份 200 页的材料和它的前六千字，能产出看起来一模一样的交付物，事后唯一能看出区别的地方，
就是你写下来的那一行。

**记的是判断吃进去多少材料，不是磁盘上有多少字节。** 访谈的数据类问题是按因子行机械
生成的（一行四问，逐字照抄同一个模板），行数一多，提纲和预答本身轻松超过十万字。
**M 类步骤套模板生成的内容，产出时不经过判断，读它作为下一步的输入时也不经过判断**——
套用模板不需要"理解"这份材料才能进行，那正是"机械"这个词的意思。诚实的声明是：
只把真正被读进判断的部分算作 `chars`（提纲的名单、业务题这类需要理解与挑选的部分），
机械生成的那一段照样 `truncated: true`，但不必假装它被逐字读过。

## 8 · 一步做完之后

1. 按模板写出产出物，带元信息块（`shared/artifact-frontmatter.md`）。
2. 告诉编排层：**"<交付物> 的 <步骤> 已完成，请验收 <交付物>/<步骤>"**。
3. 就这样。

**你不跑检查、不记裁决、不流转状态。** 那些是编排层的事，理由见架构文档 §3：
AI 不能自己给自己判定通过。有一条静态检查在盯着这件事。

需要人拍板的地方，你负责**把选择题摆出来**——候选、推荐、每项的后果、依据——
但拍板本身和记录裁决都交给编排层。

## 8.5 · 用户纠正你的时候

当场记一条，不管你正在做哪个交付物：

```bash
~/.local/bin/mmm script state record-feedback <工作区> \
  --skill <被纠正的 Skill> --kind correction|habit|missing|wording \
  --quote "用户原话" --expected "他期望的做法"
```

这条不需要等人拍板——记录一句他说过的话不需要审批。字段与判断标准见
`shared/skill-feedback.md`；收尾复盘时 `retrospect` 读它，逐条问人要不要改进 Skill。

**只认记下来的。** 顺口说的纠正说在别的事情中间，一句就过去了；等到收尾再回忆，
回忆出来的已经不是原话，而是我们希望他说过的话。没记的那条，下一个项目会原样再犯一次。

客户业务口径的判断（加了哪个因子、某个指标怎么定义）不记在这里，那是变更账本的事。

## 9 · 产出物的语言

**字段名用英文，给人看的东西用中文。** 存进 YAML 的键与固定取值（`timeGranularity`、
`Brand` / `Channel` / `Geo`、`status: locked`）一律英文——它们是给代码认的，翻译一次
就多一套别名，而别名是所有对不上的开始。面向客户的产出物按 `mmm.yaml` 的
`outputLanguage` 渲染。

工程内部的文字（Skill 正文、脚本注释、检查项说明、日志）中英文都可以，按现有文件走。

数据本身的名字不翻译——`本品销量` 是一个指标名，不是要翻译的句子。

### 固定取值的中文说法

渲染给客户时按这张表转，别处不要另起译名：

| 存进文件 | 给客户看 |
|---|---|
| `Brand` | 品牌 |
| `Channel` | 渠道 |
| `Geo` | 地区 |
| `Year` / `Month` / `Week` | 年度 / 月度 / 周度 |
| `uploaded` / `elicited` | 来自上传材料 / 由问答推导 |

## 10 · 空结果也是结论

一个步骤什么都没产出——纪要里没提出任何改动、某个问题答不上来、知识库里没有这个行业——
**把这件事和它的原因写进产出物**。

一份看起来完整的空交付物，比一次明确的失败危险得多：它能通过评审，因为里面没有东西可反对。
