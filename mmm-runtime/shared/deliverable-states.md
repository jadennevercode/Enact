# 交付物的六种状态

流程的单位是交付物。一个交付物在任何时刻处在下面六种状态之一，状态由它的**步骤**推导出来，
不是谁写上去的。这一份是判定规则的唯一副本，`scripts/state.py` 按它计算。

| 状态 | 含义 | 推导规则 |
|---|---|---|
| `locked` | 还轮不到它 | 它依赖的上游交付物还没 `confirmed` |
| `queued` | 可以开工了，还没动 | 依赖齐了，但一个步骤都没完成 |
| `building` | 正在做 | 有步骤完成了，剩下的下一步不需要人 |
| `needs-you` | 卡在你这儿 | 下一个可做的步骤是 `H` 类，或者它带着一道没关的门 |
| `ready` | 做完了，等确认 | 全部步骤完成，但最后一道门还没有生效判定 |
| `confirmed` | 定了 | 全部步骤完成，且最后一道门有生效判定 |

## 为什么是推导而不是记录

记录下来的状态会和磁盘上的事实分叉——这正是 `audit` 存在的原因。推导出来的状态没有这个问题：
它只可能反映步骤的真实完成情况，而步骤完成与否由判定式对着磁盘算出来。
文件是事实，状态是对事实的读数。

## 可选步骤

有些交付物是**能力式**的：它由几个并列的能力组成，用哪个取决于这个项目手上有什么材料，
不取决于走到了哪一步。访谈是第一个这样的交付物——五个能力里的「先答一版」和
「提洞察与假设」都标了 `optional: true`。

规则一句话：**推导状态时只看必做的步骤。**

- 可选步骤没做，不拦着交付物走到 `ready` / `confirmed`；
- 它照样出现在「下一步能做什么」里——"你还可以先答一版"值得提一句；
- 一个从没做过的可选步骤身上的门，不会把交付物卡在 `ready`：没人要求过的活儿，
  不需要有人来批。

**没有 `skipped` 这个状态，而且不会有。** "这个能力用没用过"是从磁盘上读出来的——
那份产出物在不在。写下来的 `skipped` 会和磁盘分叉，而这一整节的前提就是不允许那件事。

## needs-you 是产品的主线

一个交付物停在 `needs-you`，说明系统已经把能做的都做完了，剩下的是**只有人能担的责**——
确认口径、处置边缘分值、代表客户签字。编排层的 `status` 首先要回答的就是"哪些交付物在等我"，
其余状态都是背景信息。

`H` 类步骤永远不呈现空白问答，而是候选项 + 推荐 + 每项后果 + 证据，理由见架构文档 §4.0 与
`gate-protocol.md`。

## 回流

访谈会改因子树，统计检验发现某因子无可用指标会退回业务理解找替代——回流是流程的正常组成部分，
不是异常。回流表现为：一个已经 `confirmed` 的交付物因为一道后置的门（如 `factor-tree/amend`）
重新变回 `needs-you`。这是设计如此。

未经设计的回退要走显式的 `reopen`，它会留痕并把受影响的下游步骤退回未完成，
理由见 `gate-protocol.md` 规则四。
