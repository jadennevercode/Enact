# 契约卡：因子映射

**阶段：** 数据
**平台出处：** 2.1 Data Validation 的准入环节（平台把它并在 2.1 的 intake gate 里，没有独立任务号）· 2.22 的 `KBQ因子对应task` 页 · 2.24 归属声明
· 代码（最高权威）：`backend/app/agents/factor_link.py`、`backend/app/agents/intake_status.py`、`backend/app/dataeng/mapping.py`、`mapping_suggest.py`、`mapping_auto.py`、`indicators.py`、`orphans.py`、`backend/app/agents/ledger.py`、`backend/app/agents/reconcile.py`
· 实盘：`reference/02.数据智能体/【MMM AI】数据智能体-Data Process_2.22.xlsx` sheet `KBQ因子对应task`（71 行因子 ↔ Task 对应表）

**产出 Skill：** `factor-map`（原 `data-intake`，改名——旧名字指向"收数"，而这个交付物根本不碰数据文件）

---

## 这个交付物解决的问题

因子树用 `(l4, indicator)` 说"要收什么"。数据用 `(l4, metric)` 落地，标签是源文件自己高兴怎么叫就怎么叫的。**没有任何东西会自动把这两个键空间接起来。**

平台在这上面栽过一次，值得原样记下：**一个人明确忽略掉的 123 行因子，在数据侧一个键都没匹配上**——于是"已忽略"这个过滤器过滤了零行，一个被人亲手否掉的因子照样在质量评分里被打分、在统计检验里被筛、在 OLS 里被拟合。这就是这张卡存在的全部理由：**这里记下的一次忽略，被它下游的每一层继承。它是决定，不是备注。**

## 构建过程

| # | 步骤 | Class | 执行者 | 说明 |
|---|---|---|---|---|
| 0 | **澄清** | C→H | Skill 提问，人回答 | 见下节 |
| 1 | 取活跃因子行 | M | Tool `data.factor-map` | 遍历因子树，过滤 `status ∈ {baseline, accepted}`。`proposed` 行不进映射表——一个还没被采纳的因子谈不上有没有数据 |
| 2 | 建双向桥 | M | Tool | 对每一行，把**三种标签**都注册到该行的 `l4` 下：行自己的 `indicator`、它已有覆盖记录的每个 `metric`、以及行上的 `metric` 字段。再把数据侧的 `(coverage.l4, coverage.metric)` 注册进来。**冲突规则：先注册者胜，但"已绑定"压过"已声明"** |
| 3 | 判定每行状态 | M | Tool | 三态：`mapped` / `ignored` / `pending`。判定顺序见「打分与判定规则」 |
| 4 | 找 orphan | M | Tool | 已发布但没有供给任何活跃行的指标。**响应指标（`metric_type = Y`）永远不算 orphan** |
| 5 | 为待定行找候选 | A | Tool `mapping.suggest`（runtime 待建） | 对每个 `pending` 行，在 orphan 指标里打分排序，取分数 ≥ 0.30 的前 5 个作为候选。见「打分与判定规则 · 候选打分」 |
| 6 | **逐条裁决待定行** | C→H | Skill 呈现候选，人裁决 | 每个 `pending` 行只有三种诚实的归宿，见 Gate 表 |
| 7 | 结算选择 | M | Tool `ledger.derive` | 写 `data/derived/selection.json`：每个指标在六层里的命运 + 唯一一份已解析的选择集 |
| 8 | 渲染台账 | A | Skill | 从 payload 渲染 `artifacts/s2/ledger.md`，meta 块里写明引用的 payload 与它的哈希。**数字一律引用，不许重打** |
| 9 | **Gate：签核映射** | H | 人 | 见 Gate 表最后一行 |

**这个交付物不写因子树。** orphan 的采纳/驳回属于因子树交付物（`/mmm:factor-tree apply-proposals`）。一个东西有两个写入者，就是"一行的身份"和"一行的裁决"开始分家的地方。

## 澄清点

1. **一个因子行可以由几个源供给吗**（岔路类）
   读到：TV 花费被拆在两个文件里，是一个因子两条供给记录。
   - A. 允许一行多供给、但一个指标只能供给一行（推荐）—— 平台的规则。一个指标同时声明两行是发布环节的 bug，退回上游修，不在这里解
   - B. 一行一供给 —— 会逼着上游先合并文件，把清洗逻辑推给客户

2. **"忽略"的门槛**（越界类）
   读到：一次忽略被下游每一层继承，2.6 的漏斗里它会显示为 `rejected at mapping`。
   - A. 只有"本项目确实不建模这个因子"才忽略，并且必须写理由（推荐）
   - B. 把所有找不到数据的行批量忽略掉好让检查通过 —— **不接受**。检查报错是它在做它的工作

3. **待定行找不到数据时，是追数还是忽略**（越界类，逐行问）
   这是本交付物的主要澄清量。对每个 `pending` 行给出三选一（见 Gate），不要开放式提问。

4. **重跑时，之前被忽略的行现在有数据了怎么办**（冲突类）
   读到：重算会重新推导 `status`，但会把 `ignoreNote` / `decidedBy` 原样带回来。
   - A. 显式提示"这 N 行原本被忽略，现在有数据了，要不要恢复"（推荐）—— 不能当成"改善"悄悄放过
   - B. 自动恢复 —— 会把人写下的理由无声丢掉

5. **指标角色（Y / X / excluded）与聚合方式（sum / average）在哪一步定**（缺失类）
   读到：平台在这一步解析并允许人覆盖；runtime 在 schema 里声明 `metric_type`，但本交付物没有落盘位置。
   - A. 保持在 schema 声明，本交付物只读不改（推荐）—— 单一写入者
   - B. 允许在这里覆盖 —— 那必须在产出物里有字段承载，否则改了等于没改（这正是 runtime 现在的 bug，见差异表）

### 最终裁决（下游 2.6 消费，此处只定义枚举）

一个因子行在整条链走完之后的五种归宿：

| verdict | 含义 | 触发 |
|---|---|---|
| `adopted` | 进了模型 | 所有模型对象都采纳 |
| `partial` | 部分模型对象采纳、部分被否 | 混合 |
| `rejected` | 被某一层否掉 | 记 `rejectedAt`（层名）+ `rejectedAtTask`（任务号）+ `reason`（忽略理由或该层的判据） |
| `notSupplied` | 树声明了，没有任何已发布资产供给 | 供给为空 |
| `notModeled` | 有数据但没进模型 | 两种：① 同一数据键被兄弟行认领了（记 `claimedBy`）② 历史太短或没有波动 |

层的顺序（**忽略的继承路径就是这个顺序**）：
`mapping (2.1) → quality (2.2d) → signoff (2.3) → statistical (2.4d) → selection (2.5) → range (2.5)`

## 打分与判定规则

### 一、行状态判定（确定性，M 类）

```
默认                                          status = pending
if 该行 id 在忽略集里:                          status = ignored     ← 优先级最高
elif 存在供给该行的覆盖记录:                     status = mapped
```

**"显式忽略压过自动映射"是一条载重规则，不是风格选择。** 反过来的话，一个**有**数据的因子在这一步根本无法被否决——忽略只对"没人供给的行"可达，于是"把这个留在模型外"这句话，在某个资产碰巧覆盖到它的那一刻就蒸发了。

**无论判定成什么，覆盖信息都要填上**（资产名、指标名、覆盖区间）。一个正在考虑要不要恢复某个被忽略行的人，需要看见现在到底有什么数据。

**多供给与唯一认领：**
- 一行可以有多条 `suppliedBy`（TV 花费拆在两个文件里 = 一个因子两条供给）
- **一个指标至多供给一行**。绑定操作会先释放该行上原有的覆盖；一个指标同时认领两行是发布环节的 bug，退回上游修
- 同一行多条候选覆盖时的主选：**人钉的胜出**，否则取行数最多的那一条（序列最长）
- **绑定操作同时清除忽略**——"一个被忽略的行，一旦被绑上就不再是'主动不解决'了"

### 二、行身份 = 路径 + 指标，绝不是路径本身

一棵树在同一条 L1–L4 路径下常带好几行（一个因子同时声明花费和门店数）。只按路径查找会把指标绑到任意一个兄弟行上，标成"自动绑定"，而真正该被供给的那行看起来无人供给。**在参考树上这曾把 16 个指标里的 8 个绑错，并且每一个看起来都完全正确，一路正确到模型里。**

平台的四级查找（由细到粗，越界即停）：
1. `treeRowId` 已显式设置（发布时匹配上的，或人钉的）—— 权威，直接用
2. `(l1,l2,l3,l4, indicator) == (l1,l2,l3,l4, metric)` —— 全路径 + 名称
3. `(l1,l2,l3,l4)` —— 仅路径
4. `(l3, indicator) == (l3, metric)` —— L3 + 名称

第 2–4 级只在"该候选行还没被别的指标认领"时才生效（`claimed_metric` 锁）。平台的注释记着这条锁修掉的真实 bug：路径查找曾把 `温度` 绑到声明 `降水量` 的行上、把 `竞品ND` 绑到声明 `竞品WD` 的行上。

**归一化**：`str.strip().lower()`，中日韩场景下再去掉全部空白。平台里同时存在**六个不同的归一化函数**（保留内部空白 vs 去掉全部空白），这是它自己的技术债；runtime 应当只有一个。

### 三、候选打分（A 类：确定性打分 + 可选的一句话解释）

```
score = 0.45 × name + 0.35 × path + 0.12 × unit + 0.08 × covered
```

| 分项 | 计算 |
|---|---|
| `name` | 词元集合的 Jaccard 相似度 `|A∩B| / |A∪B|`。词元 = 按 `空格 _ - / · | , ， 、 () （） [ ]` 切分，**再加上中日韩字符的 2-gram**（"冰柜"→`冰柜`；"冰柜台数"→`冰柜`,`柜台`,`台数`）。比较对象是候选的 `metric` 对因子行的 `indicator`（没有 indicator 就用 `l4`） |
| `path` | 逐级相等，权重 `L1=0.5, L2=0.75, L3=1.5, L4=2.0`，除以 `4.75` 归一。**一级都不匹配就返回 0.0** |
| `unit` | 候选的单位与因子行的指标名落进同一个词汇组则 1.0，否则 0.0。三组：**金额** `元 rmb cny value 金额 spend gmv 花费 费用 投放 成本 cost budget`；**销量** `箱 ton volume 销量 units 件 出货 销售量`；**比率** `% 率 rate pct share 占比` |
| `covered` | 候选同时有 `coverageStart` 和 `coverageEnd` 则 1.0 |

| 阈值 | 值 | 含义 |
|---|---|---|
| `MIN_SCORE` | **0.30** | 低于此分**根本不呈现给人**。一个 0.2 分的建议消耗的注意力比它值的多 |
| 候选条数上限 | **5** | 排序后取前 5 |
| 自动绑定下限 | **0.45** | 只有全自动模式才用。有人在场时不自动绑 |
| 措辞分档 | `≥0.6` "很可能匹配" · `≥0.45` "可能匹配" · 其余 "弱匹配" | **只影响措辞，不影响分数** |

**分数是确定性的，只有那一句解释可以由模型改写。** 平台允许模型把 `reason` 重写成一句 ≤20 词的话，且明确要求"看起来不对就直说"；改写失败就原样返回。**匹配与分数本身永不经过模型。**

### 四、orphan 的判定

一个已发布指标是 orphan，当且仅当：
- 它没有被任何活跃因子行的覆盖解析所认领（四级查找全部落空），**且**
- 它不是响应指标

**响应永远不是 orphan。** 没有哪个行业因子树会把"销量"声明成一个因子——Y 是被解释的对象。平台早期把响应当成 orphan 提出来给人采纳，结果是把 KPI 采纳成了一个驱动因子。

**"歧义"不是 orphan。** 参考树上有 50 行都声明了 `花费`；一个叫 `花费` 的指标在 L4 上匹配不到任何行时，它是**歧义**不是孤儿——按孤儿去采纳会凭空造出一个和已有因子重复的行。

**orphan 的两个出口**（都在因子树交付物里，不在这里）：
- **采纳** —— 用覆盖记录自己的 `l1..l4` 与 `metric` 造一行新因子（`source: data_upload`, `status: accepted`），并把覆盖的 `treeRowId` 指向它、`boundBy: human`。**拒绝采纳 `metric_type = Y` 的指标**
- **驳回** —— 若该覆盖已经有 `treeRowId`，驳回失败并提示"先在因子映射里释放它"

### 五、完成判定（Gate 前置）

```
complete  ⇔  total > 0  ∧  pending == 0
```

平台的完整闸门还要多两层：
1. `total == 0` → 阻断，理由 **"因子树没有任何活跃行。先完成业务理解阶段。"**
2. `pending > 0` → 阻断，理由 **"177 行里还有 54 行未解决。请为每一行绑定一个已发布指标，或标记为忽略。"**
3. 即使前两条都过了，**数据侧的阻断项也必须为空**：没有响应指标、没有任何非空渠道类型（于是没有模型对象）、没有驱动指标——这三条在这里挡住，而不是拖到 2.6 才表现为"0 个模型对象"

**`pending` 不是一个能活过 gate 的状态。** 检查项失败时会**点名**是哪些行。那是检查在做它的工作。

### 六、忽略的继承（这张卡最重要的输出）

一次忽略产生两种键，两种都要进继承集：
1. **树侧拼写** `(l4, indicator)` —— 因子行自己声明的名字
2. **数据侧拼写** `(l4, metric)` —— 该行已有覆盖记录用的名字

**只记第一种，就是开头那个"123 行忽略匹配零个数据键"的 bug。** 下游各层是在数据的键空间里工作的。

继承集向下传递的规则：`drops_before(层名)` = **该层之前所有层的忽略/否决的并集**。每一层只能读它，**不许自己拼**（手工 union 两个集合是同一个 bug 的第二种写法）。

具体消费方：

| 下游 | 怎么用 |
|---|---|
| 数据质量评分 | 打分前先按 `drops_before("quality")` 过滤掉，并报告过滤了几个 |
| 统计检验 | 同上，`drops_before("statistical")`；全部被过滤掉时返回空评分表并说明 |
| OLS 预验证 | `drops_before("selection")` 里的指标**显示但不可选** |
| 模型输入 | 在漏斗里显示为 `rejected at mapping`，理由就是 `ignoreNote` 原文 |
| 台账 | 第一次否决胜出；之后各层一律记 `inherited` |
| 台账合成行 | 被忽略的因子行根本进不了长表，所以要**额外补一条合成记录**，否则它会从漏斗里整个消失 |

**一个必须存在的自检：** 如果 2.1 记录了忽略而下游的继承集是空的，**说明连接断了，立刻停下来说出来**——一个什么都没过滤掉的过滤器，看起来和一个干净的项目一模一样。

## Gate

| 触发条件 | 判定者 | 候选处置 | 路由 |
|---|---|---|---|
| 存在 `pending` 行（逐行） | 人（数据 Owner） | ① **客户有数据但没发过来** → 保持 pending，登记，去追这次交付 ② **数据到了但标签没人认领** → 回上游修归属声明，重跑映射 ③ **本项目不建这个因子** → `ignored` + `decidedBy: human` + **必须写 `ignoreNote`** | ①→ 回「数据需求与验收」追交付，本 gate 不关；②→ 回「发布数据集」的归属步骤；③→ 就地解决。**没有第四种**。"先放着看看"解析成 pending，而 pending 活不过这个 gate |
| 某行原本 `ignored`，重跑后变成 `mapped`（新数据到了） | 人 | ① 恢复为 mapped（接受新数据）② 维持忽略并更新理由 | 必须**显式呈现**，不得当成"改善"静默通过 |
| 存在 orphan | 人 | ① 采纳为新因子行 ② 驳回 | **不在本 gate 裁决**——列在一旁，指向因子树的 apply-proposals。本 gate 只负责让人知道有几个 |
| 一个指标同时认领两行 | — | 不是裁决项，是上游 bug | 退回「发布数据集」，不在这里解 |
| **签核映射** | 人（担责） | ① 签核 ② 打回重做（含理由） | 签核问题原文：*"每一个活跃因子是不是要么有数据供给、要么被显式忽略？这里的一次忽略会被后面每一层继承——它不是备注。"* 证据：`artifacts/s2/factor-map.yaml`。签核后本交付物冻结；要改必须显式重开，重开会把 2.2 之后全部退回待办，**因为它们每一个都是在这份文件定义的人口上打的分** |

**呈现顺序（gate protocol）：**
1. 问题——每个活跃因子是否要么有供给要么被显式忽略
2. 证据——按状态分组的计数，以及**与上一轮相比变了什么**
3. orphan——单独列出，指向因子树，声明它们不在本 gate 裁决
4. **每一条 pending 逐行列出**——L4、指标、这行当初要求客户提供的定义与责任人、最接近的候选（如果有）。一个要在"追它还是忽略它"之间做选择的人，需要知道追它是打个电话还是重来一次交付
5. 后续——2.2 只给活下来的打分，而且**永不重新评估这里忽略掉的**

**不许做的两件事：** 还有 pending 时推荐通过；把"把剩下的都忽略掉"当成一个便利选项提出来——**忽略是换了个友善名字的否决**。

批量忽略本身是合法的，也会被记录；**要明说清楚刚刚有多少个因子离开了模型、都是哪些**。沉默不是决定。

## 备注

**1. 交互式数据网格的替代方案（有意放弃登记）。**
平台在这一步用的是一张 TanStack 网格：`L1·L2·L3·L4·Indicator·Role·Aggregation·Status` 七列，逐行 Release / Restore / Ignore / "用这个"，外加一个"忽略所有待定"的批量按钮。runtime 有意放弃它。文本形态这样承载：

- 网格的真正内容不是"行"，而是**待定行的清单加上每行的候选**。已映射的行不需要人看（它们有供给记录，供给记录有出处），已忽略的行不需要人再看（它们有理由，理由是人自己写的）。**需要人的只有 pending，而 pending 天然是可枚举、可逐条呈现的。**
- 所以文本形态是：① 三个计数 + 与上轮的差异 ② orphan 清单（列而不裁）③ **逐条 pending：L4 / 指标 / 当初要求客户提供什么 / 候选（带分数与一句解释）/ 三选一**。
- 网格能做而文本做不到的：一眼扫完 177 行看整体形状。runtime 用计数 + 按 L1/L2 分组的忽略摘要（平台自己也这么做：*"因子树中被忽略的领域（本轮不进模型）"*，按 `L1 › L2` 分组）替代。
- **平台网格自己的一个缺陷值得记下**：它把状态渲染成二值——`mapped→"已匹配"`，`ignored` 和 `pending` **都渲染成"未匹配"**。三态的区分只活在接口数据里，界面上看不见。也就是说，这张网格恰恰看不见本交付物最重要的那个区分。文本形态在这一点上不是降级，是升级。
- 登记进 `docs/specs/deliberate-omissions.md`：**平台有什么** = 因子映射交互式网格；**为什么不要** = 需要人的只有 pending 行，它天然可枚举；且平台网格把 ignored 与 pending 渲染成同一个"未匹配"，丢掉了本交付物的核心区分；**什么条件下重审** = 当 pending 行常态超过 100 条、逐条呈现变得不可行时。

**2. 平台把这件事藏在 2.1 的 intake gate 里，没给它任务号。**
这正是"交付物驱动"要修的东西：一件既有产出（映射表）、又有人工裁决（逐行）、又被下游继承（忽略集）的事，在平台上却只是另一个任务的准入条件。把它立成独立交付物是 runtime 的判断，不是平台的原文。契约卡的"平台出处"栏因此指向代码而非任务号。

**3. 平台的技术债，不要继承。**
- **六个不同的归一化函数**（`factor_link._norm` 保留内部空白、`indicators._norm` 去掉全部空白、`indicator_metadata._norm` 用正则、`mapping_suggest._tokens` 又是一套、`cluster` 两套指纹）。同一个字符串在不同模块里归一成不同的东西，是这类系统最难查的一类 bug。runtime 应当只有一个，并且写进 `shared/`。
- **对账模块整个被三个裸 `except Exception: pass` 包着**，注释理由是"一份不完整的答案胜过一个渲染不出来的产出物"。这在 runtime 里不成立：runtime 的检查项要么真、要么假，一个吞掉异常后报出的部分计数会让 gate 在错误的证据上关闭。要么算对，要么明确失败。

**4. 这张卡和「发布数据集」的边界。**
凡是"某个指标绑错了行"——回上游。凡是"这一行到底要不要"——在这里。判据：**绑定是数据的解读问题（属于配方），忽略是范围的决定问题（属于人）**。
