## 输入

| 来源 | 内容 | 类型 |
|---|---|---|
| 上游交付物 · 因子树 | `status: accepted` 的每一行——**打分表的行来自这里**。每行的 `dimension`（报出轴）与 `unit`（声明单位）参与判据 | 交付物 |
| 上游交付物 · 因子映射 | 已签核的映射表，特别是**忽略集**——决定哪些行标 `inherited-drop`、不给分 | 交付物 |
| 上游交付物 · 发布数据集 | `data/published/long.parquet`；按 `(l4, metric)` 找到每一行对应的序列 | 交付物 |
| 上游交付物 · 项目档案 | `timeWindow`（缺失率的分母）与 `modelScope`（模型颗粒度的对照） | 交付物 |
| 人手登记 | `metadata/reference-totals.yaml` —— 财务或源系统的对照合计。没有就标「未校验」 | 原料 |
| 知识库规则 | `knowledge/methodology/validation-scoring.json` —— 判据文本（**展示用**；数值阈值在 `scoring/quality.py`，两处必须同步） | Knowledge |
| 上一轮的本交付物（若有） | 已有的 `disposition` / `decidedBy` / `note` | 自身历史 |

**打分对象的粒度：** 一行 = 一个 `(L1 × L2 × L3 × L4 × 指标)`，**不分模型对象**。
一个指标只被裁决一次，每个模型对象继承这个裁决。按对象分行会得出"同一条序列在 MT 能用、
在 EC 不能用"——那是关于模型的陈述，不是关于数据的陈述。

**行来自因子树而不是数据**，这是 2026-08-11 的一处方向性改动。按数据分组出行说不出
「树上要了、一条数据都没到」这句话——那一行压根不存在，读起来和「这个因子没人要过」
一模一样。三种状态：

| dataStatus | 含义 | 四维分 | 谁来处理 |
|---|---|---|---|
| `scored` | 长表里有这条序列 | 有分 | 按判读走 |
| `no-data` | 树上要了，一条数据都没到 | **null，不是 0** | 数据需求与验收（追交付） |
| `inherited-drop` | 因子映射层已判「不做」 | null | 继承，不再打分 |

数据里有、树上没要过的是**孤儿**：不进表，只记 `orphanCount` 并在呈现时说一句。

## 打分与判定规则

**这一整节是 M 类确定性规则。每一条都必须能照着实现，不留判断余地。**

### 一、10 个子项

**Consistency 一致性**（3 项）

| key | 中文 | 1 分 | 0.5 分 | 0 分 | 阻断 | 可计算 |
|---|---|---|---|---|---|---|
| `consistency.dimension` | 维度一致性 | 全部行统一在一个单位上 | 不在主单位上的行 ≤10% | >10%，或与因子树声明的 `unit` 不一致 | 有单位列时**是** | 有单位列时**是** |
| `consistency.time` | 时间一致性 | 全程统一的月度网格 | 偏离主导网格 ≤10% | 偏离 >10%，或粗于月度 | **是** | 是 |
| `consistency.caliber` | 口径一致性 | 全程单一数据源 | 换过源且同比 ≤30% | 换过源且同比 >30% | **是** | 是 |

**Accuracy 准确性**（2 项）

| key | 中文 | 1 分 | 0.5 分 | 0 分 | 阻断 | 可计算 |
|---|---|---|---|---|---|---|
| `accuracy.numeric` | 数值准确性 | 非法值 <5% | 5%–10% | >10% | **是** | 是 |
| `accuracy.business` | 业务准确性 | 与登记合计偏差 <5% | 5%–10% | >10% | 有登记时**是** | 有登记时**是** |

**Comprehensiveness 完整性**（2 项）

| key | 中文 | 1 分 | 0.5 分 | 0 分 | 阻断 | 可计算 |
|---|---|---|---|---|---|---|
| `completeness.field` | 字段完整性 | 响应序列，或字段齐全 | 该 L4 有花费但没有任何表现指标 | 该 L4 名下没有任何范围内字段 | **是** | 是 |
| `completeness.data` | 数据完整性 | 无缺失 | 缺失 >0 且 <10% | 缺失 ≥10% | **是** | 是 |

**Granularity 颗粒度**（3 项）

| key | 中文 | 1 分 | 0.5 分 | 0 分 | 阻断 | 可计算 |
|---|---|---|---|---|---|---|
| `granularity.time` | 时间颗粒度 | 月度及以下 | **无此档** | 粗于月度 | **是** | 是 |
| `granularity.model` | 模型颗粒度 | 要求的轴全都有 | 有一部分，需额外聚合或拆解 | 要求的轴一个都没有 | **是** | 是 |
| `granularity.drilldown` | 下钻颗粒度 | >2 个 L5–L8 维度 | 1–2 个 | 0 个 | 否 | 是 |

**阻断型 7 项 · 建议型 3 项。** 维度一致性与业务准确性在缺对照输入时降为建议型，
料一到位自动升级——它们建议是因为算不出来，不是因为不重要。

**建议型不许拉低维度分。** 这条规则修的是一个真实事故：把一个建议型子项当成阻断型，
导致整个项目每一个指标都被清零。反过来，**阻断型是"封顶"不是"参考"**——它一旦低了，
同维度里没有任何其他子项能把它抬回来。

**为什么下钻颗粒度是建议型。** 它说的是 deep dive 能走多深，不是这条序列能不能建模。
把它当阻断型，会让「没有下钻维度」等于「数据不可用」，而多数项目本来就没有下钻维度。

### 二、三条判据的细节

**缺失率的分母**（`completeness.data`）= 该序列报出的格子数 × **档案时间窗**的月数。
三件事都是有意的：不用序列自己的行数（那样任何序列的缺失率都是 0）；不用合同的完整网格
（"从来没报过某个渠道"是模型颗粒度的问题，在这里再算一次等于让一个全国性投放被罚两次）；
时间窗取自 `profile.timeWindow`，档案没写才退回按序列自身跨度算，并在说明里写清用了哪一个。

**模型颗粒度对照的是合同**（`granularity.model`），不是"有几个省份组"。三样东西比对：
档案 `modelScope` 里有取值的轴（客户可能叫「产品 / 渠道 / 平台与区域」，按名字里的关键词
映射到长表的列）、因子树那一行 `dimension` 声明的轴、长表里这条序列真正有取值的轴。
**要求 = 前两者的交集。** 用因子树声明去收窄是关键的一步：一个全国投放的媒体，
树上就写着它按月×区域报，没有渠道拆分不是缺失，是它本来的样子；反过来，
树上承诺了、数据没交的轴是真缺口。

**口径变化判的是"换过源"**（`consistency.caliber`），不是"多源混合"。稳定的多源混合不算，
一个源出现或消失才算。换源之后再看前后同比：>30% 是断裂，≤30% 是重新打标。

### 三、卷积

```
维度分 = min(该维度全部阻断型子项的分数)      该维度没有阻断型子项时 = 1.0
Total  = consistency × accuracy × completeness × granularity      ← 相乘
```

**为什么是相乘而不是相加。** 实盘 Excel 原文（`2.12数据质量评分` 页）：
`Final score = 完整性评分*颗粒度评分*真实性评分*一致性评分` —— 乘。平台代码：乘。
知识库早期文档写成加，那是转录错误，已就地更正。
相乘的业务含义：**一个维度是 0，整条序列就没法用**——一个在错误口径上完美完整的指标，
不是"75% 可用"。相乘可达的 Total 只有 6 个值：`1 · 0.5 · 0.25 · 0.125 · 0.0625 · 0`。

### 四、Total → 判定

| Total | 判定 | 处置 |
|---|---|---|
| `>= 0.5`（可达值只有 1 与 0.5） | `accept` | 验收通过 |
| `0 < Total < 0.5` | `borderline` | **人进入决策如何处理** |
| `== 0` | `unusable` | 弃用并预警 |

工作簿原文写「0.5–1 验收通过 / ≤0.5 需人工介入」，**0.5 同时落在两档**；
客户裁定 0.5 归验收通过，所以实现是 `>= 0.5`。判读只有一份实现：`scoring.quality.verdict_for`。

### 五、升级预警：两类，路由不同

```
按 (l1, l2, l3, l4) 分组，跳过 inherited-drop 的行，也跳过 l4 为空的行
if 该组内每一个指标的 Total 都 == 0:        → 业务侧 + 客户（寻找替代数据）
if 该组内每一个指标都是 no-data:            → 数据需求与验收（追这次交付）
```

**这不是"多列几行 unusable"，是一个不同的事件。** 三个指标里死了一个，是这个因子少了个
视角；三个全死，是**这个因子在模型里彻底不存在了**。而"全部没数据"与"全部 0 分"的处置
对象又不一样：前者是交付还没到，后者是数据不能用——**0 分找数据 Owner，没数据找交付**。
把它们放进同一张清单，就会有一半的行送错桌子。

`l4` 为空的行不参与分组：预警说的是"这个**因子**将没有任何东西代表它"，
而响应指标按设计不挂在任何 L1–L4 下，它没法做这个陈述，把空值归成一组等于发明了一个叫 `""` 的因子。

### 六、继承与再评分

- 打分前先算 `drops_before("quality")`（= 因子映射层的忽略集），命中的行标 `inherited-drop`
- **列出来可以，打分不行。** 检查项 `layer_inherits_drops:quality` 现在判的是
  "被继承的行身上有没有分"，不是"表里有没有这一行"——列出来是让漏斗可读，给分才是复活
- 反向也检查：因子映射记了忽略而继承集是空的 → 失败。
  一个什么都没过滤掉的过滤器，看起来和一个干净的项目一模一样
- 本层的 drop 被后面每一层继承；被 drop 的指标不画图、不筛、不入拟合
- 若所有指标都已被上游否掉，本层**失败并说明**，而不是产出一张空表通过

### 七、"打不出分"是发现，"全都打成 0 分"同样是

**某个子项在整个项目里从来没有失败过一次 → 怀疑输入，不要怀疑数据。**
平台栽过：在按全国 TOTAL 汇总之后再打分，颗粒度、口径、完整性三个子项**在结构上不可能失败**。

反过来同样响：**18 行里 18 行栽在同一个子项上，通常也是一条关于输入的陈述。**
工具会把这句话直接打出来。实测例子：一个项目档案声明建模 2023-01 到 2025-12，
数据只交到 2024-01 起，于是每一条序列的数据完整性都是 0——那不是数据稀烂，
是窗口与交付没对齐，而逐行读要花一个下午。

## 产出格式

### 1) 五份计算结果 [computed]

`data/derived/quality-{consistency,accuracy,completeness,granularity}.json` —— 各带
`dimension` / `signature` / `rows[]`（每行含 `score` 与该维度的 `subScores[]`）/
`skipped` / `orphanCount`。

`data/derived/quality-evidence.json` —— 卷积结果，见 `tools/catalog/quality.scorecard.yaml`
的 `output.shape`。每个 `subScore` 都带 **`computed`**（false = 没查）与 **`blocking`**
（false = 建议型），每一行都带四句 **`*Note`**（该维度最弱的那个阻断型子项自己的说明）。
这两样此前都不在 payload 里，导致誊抄的人必须自己推断"哪个子项封了顶"、
也无从知道哪两格其实没查过。

### 2) 主产出 —— `artifacts/s2/quality-scorecard.yaml` [store]

结构见 `skills/data-quality/templates/quality-scorecard.yaml`。要点：
`dataStatus` 三态；未打分的行四维分与 `total` 写 **`null` 而不是 0**；
每行 `source` 指回 payload；`escalations` 两类分开写。

### 3) 视图 —— `artifacts/s2/quality-scorecard.xlsx` [view]

```bash
~/.local/bin/mmm app workbook scorecard -w <工作区> --card quality
```

四张表：评分卡 · 统计 · 说明。工作簿带评分表的 `sourceHash` 自定义属性，
`workbook_current` 靠它判过期。**没人手改它。**

表上有两处渲染是硬要求：

- **`computed: false` 的子项渲染成「未校验」**，不能渲染成 1。
  "没查"和"查了没问题"在一张要签字的表上不能长得一样。
- **没有分的行四维分与总分渲染成「—」**，不能渲染成 0（读起来像判死），
  也不能留空（读起来像漏填）。

此前这里是一份 `.md` 视图，而**全仓没有任何东西渲染它**——`deliverables.yaml` 没给它
`computed_by`，`tools/catalog/` 里也没有对应的卡，而 `view_current` 要求它带
`generatedFrom` + `sourceHash`。那道检查没有任何有记载的流程能通过。改成 Excel 之后
这条链是完整的：App 生成、App 盖指纹、检查重算指纹比对。

## Gate

| 触发条件 | 判定者 | 候选处置 | 路由 |
|---|---|---|---|
| `Total >= 0.5` | 自动 | 验收 | 无需人介入；批量接受时**记一次动作 + 条数** |
| `0 < Total < 0.5`（边缘） | 人（数据 Owner） | ① `keep` 带保留意见入模 ② `drop` 弃用 ③ 回上游补数据 | 呈现时必须给出：是哪个阻断型子项把维度封了顶、它算出了什么数 |
| `Total == 0` | 人（确认弃用）+ 预警 | ① 确认 `drop` ② 认为判据有问题 → 回上游查 | 粗于月度常常是清洗时把月份丢了；大面积完整性 0 分常常是档案窗口与实际到数没对齐 |
| `dataStatus == no-data` | 人 | ① 回数据需求追交付（推荐）② 本轮不做 → `drop` ③ 换指标 | **不要混进弃用清单** |
| **某 L4 全部 Total == 0** | 业务侧 + 客户 | ① 找替代数据源 ② 本轮不建模 ③ 换指标重新收数 | 紧急度高（预警） |
| **某 L4 全部 no-data** | 数据需求与验收 | ① 追交付 ② 本轮不建模 | 紧急度高（预警） |
| **质量验收签核** | 人（担责） | ① 签核 ② 打回重做 | 证据：`artifacts/s2/quality-scorecard.xlsx` |

**呈现顺序（例外复核，不是逐行朗读四百行）：** 按档计数 → 阻断型失败点名（带数字）→
「一条数据都没到」单列一节 → 边缘行逐条、最差在前、每条带"是哪个子项封了顶" →
每条的建议与依据 → 后果。80 行栽在同一个子项上是一场对话，不是八十场。

**批量接受干净档是合法的，也会被记录。** 不合法的是：一行走到确认面前还是空的
`disposition`，因为没人看过——那是沉默，检查项会点名拒绝它。
**如果复核者一行都没否，在关确认之前明说出来。**

## 检查项

| 检查 | 判什么 |
|---|---|
| `computed_by_tool` ×5 | 五份计算结果都出自真实运行、之后没被改过 |
| `frontmatter_valid` | 评分表的元信息完整 |
| `scorecard_matches_payload` | **评分表上的每个数都和计算结果对得上**——逐行按 id 比对 `dataStatus`、四维分、总分、判读 |
| `layer_inherits_drops:quality` | 被继承的行身上没有分；反向：映射记了忽略而继承集为空 → 失败 |
| `no_undecided_scorecard` | 每一行都落到 `keep` 或 `drop` |
| `workbook_current` | Excel 与评分表同步 |
| `grounding_within_allowlist` | 只读了这一步允许读的材料 |

`scorecard_matches_payload` 是 2026-08-11 新增的。此前整份交付物 100% 靠模型逐行誊抄，
却**没有任何检查核对抄得对不对**——`computed_by_tool` 证明的是 payload 出自真实运行，
它对"从 payload 里抄出来的是什么"一无所知。于是唯一一份内容全是数字的交付物，
恰恰没有 `shared/numbers-provenance.md` 所声称的那道机械保证。

## 备注

**1. 交互式数据网格的替代方案（有意放弃登记）。**
平台在这一步的界面是一张可编辑评分网格。runtime 有意放弃它，替换为**例外复核**：
`autoVerdict` 在每一行上都预填了，需要人的只有 `borderline` 那一档和 `no-data` 那一档。
网格能做而文本做不到的一件事是**改分**——这是有意取消的：分是算出来的，人改的是**处置**
不是分数。觉得分算错了，那是判据或输入有问题，应该回上游修，
